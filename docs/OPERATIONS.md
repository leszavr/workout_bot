# Operations Runbook

## Локальное окружение: workout-manager.sh

Скрипт в корне проекта поднимает и обслуживает локальное окружение: PostgreSQL,
Redis и MinIO в docker compose, backend, веб-интерфейс, Telegram-бот.

```bash
./workout-manager.sh start        # инфраструктура + backend + веб, логи в терминале, Ctrl+C — стоп
./workout-manager.sh start -d     # то же, но службы остаются в фоне
./workout-manager.sh status       # что запущено и к какой базе подключён backend
./workout-manager.sh doctor       # проверка окружения: .venv, .env, доступность базы, порты
./workout-manager.sh logs backend -f
./workout-manager.sh ai-status    # чек-лист готовности ИИ и последние вызовы
./workout-manager.sh free-ports   # освободить порты, занятые забытыми процессами проекта
./workout-manager.sh help
```

Что скрипт делает не только «для удобства»:

- **не запускает backend без базы.** uvicorn поднимается и без PostgreSQL, но
  тогда все запросы отвечают ошибкой, а в интерфейсе это выглядит как
  `Failed to fetch`. Доступность базы проверяется по `DATABASE_URL` до запуска.
- **не запускает бота без Redis.** Состояние анкеты хранится в Redis; при
  недоступности бот завершился бы при старте, поэтому `REDIS_URL` проверяется
  заранее (`start bot`, `start services`, `doctor`).
- **восстанавливает публикацию порта PostgreSQL.** Контейнер может остаться
  запущенным, потеряв проброс порта на хост; тогда контейнер пересоздаётся
  (данные в именованном volume не затрагиваются).
- **предупреждает о непримененных миграциях**, сравнивая `alembic current` с `heads`.
- **не даёт запустить интеграционные тесты по рабочей базе**: они удаляют свои
  данные, поэтому нужен отдельный `TEST_DATABASE_URL`.
- **отличает свой забытый процесс от чужого**: процессы проекта на занятых
  портах останавливаются, посторонние — нет, о них скрипт сообщает.

Логи служб пишутся в `data/logs/`, PID-файлы — в `data/run/` (каталог `data/`
не под git).

## Основной запуск

```bash
cp .env.example .env
docker compose -f docker/docker-compose.yml --env-file .env up --build
```

После первого запуска выполнить миграции и импорт каталога/медиа согласно `README.md`.

## Зависимости

- PostgreSQL — основные данные;
- Redis — состояние анкеты (FSM) между сообщениями и перезапусками;
- MinIO — бинарные изображения упражнений;
- FastAPI — backend/API;
- Telegram gateway — пользовательский транспорт. Данных не хранит: анкета,
  профили и состояние диалога живут в RU, шлюз общается с Backend только через
  `/internal/v1/telegram/*`. Свой Redis (EU) нужен только для служебного
  состояния aiogram и имеет TTL;
- Worker — повтор transient-отказов генерации и доставки, восстановление
  операций после падения процесса (`python -m apps.worker.main`). Redis ему не
  нужен: очередь повторов и аренда живут в PostgreSQL;
- Next.js — внутренняя админка.

## Обязательные проверки после развёртывания

- `/health` отвечает;
- `/ready` подтверждает готовность зависимостей;
- admin login работает;
- каталог упражнений содержит ожидаемые данные;
- media endpoint возвращает изображение;
- deterministic generation проходит;
- при настроенном AI проходит AI generation;
- при искусственной ошибке AI deterministic fallback работает;
- HTML delivery приходит в Telegram;
- анкета продолжается после перезапуска процесса бота (`restart bot` посреди
  анкеты не сбрасывает вопросы);
- worker запущен и в логах виден `event=worker_started`; после его перезапуска
  обработка возобновляется сама (состояния в процессе он не держит);
- у контейнера шлюза нет `DATABASE_URL` и ключей MinIO:
  `docker compose config` для `telegram-bot` не должен их содержать. Это
  проверяется фактически, а не по коду;
- в Redis шлюза у ключей есть TTL (`redis-cli ttl <key>` > 0) и нет ответов
  анкеты: они лежат в `telegram_sessions` (RU);
- в `generation_jobs` нет записей в статусе `running` с истёкшим
  `lease_expires_at`: такие job worker обязан вернуть в очередь в течение одного
  цикла (`WORKER_POLL_INTERVAL_SECONDS`).

## Переменные

Полный список и примеры — `.env.example`. Критические группы:
- Telegram: `BOT_TOKEN`, `ADMIN_CHAT_ID`;
- PostgreSQL: `DATABASE_URL`/пароли;
- Redis: `REDIS_URL` (обязателен для бота), `REDIS_PORT`;
- admin/JWT;
- MinIO/media;
- `PROGRAM_PRIMARY_GENERATOR`, `PROGRAM_FALLBACK_GENERATOR`;
- `AUTO_GENERATE_PROGRAM_AFTER_FINALIZE`;
- шлюз (отдельный env-файл `staging-gateway.env`): `BACKEND_INTERNAL_URL`,
  `INTERNAL_SERVICE_TOKEN`, `BACKEND_REQUEST_TIMEOUT_SECONDS`,
  `BACKEND_REQUEST_RETRIES`, `BACKEND_RETRY_DELAY_SECONDS`,
  `TELEGRAM_DELIVERY_POLL_INTERVAL_SECONDS`, `TELEGRAM_DELIVERY_BATCH_SIZE`,
  `GATEWAY_STATE_TTL_SECONDS`. `DATABASE_URL` и `MINIO_*` в этом файле быть не
  должно;
- Backend: `TELEGRAM_DELIVERY_LEASE_SECONDS` — аренда задания на отправку;
  должна покрывать рендер HTML и отправку документа, иначе задание отдадут
  второму экземпляру шлюза и пользователь получит файл дважды;
- worker: `WORKER_COMPONENT_ID` (обязан различаться у экземпляров: значение
  попадает в `lease_owner`), `WORKER_POLL_INTERVAL_SECONDS`,
  `WORKER_MAX_ATTEMPTS`, `WORKER_RETRY_INITIAL_DELAY_SECONDS`,
  `WORKER_RETRY_MULTIPLIER`, `WORKER_RETRY_MAX_DELAY_SECONDS`,
  `WORKER_LEASE_SECONDS`, `WORKER_BATCH_SIZE`, `WORKER_DELIVERY_ENABLED`.
  `WORKER_LEASE_SECONDS` должен превышать максимальный бюджет генерации
  (1800 с), иначе job отберут у живого исполнителя и генерация пойдёт дважды.

Секреты не коммитить. Для production требуется отдельная процедура backup/restore и регулярная проверка восстановления.

## Локальная разработка и тесты

Интеграционные тесты используют реальную PostgreSQL из `DATABASE_URL`; без
этой переменной они пропускаются, а не «проходят».

Типовые локальные проблемы, которые не являются ошибками приложения:

- если на хосте уже слушает свой PostgreSQL на 5432, контейнер `postgres` из
  `docker/docker-compose.yml` не сможет опубликовать порт, и приложение будет
  подключаться к хостовой БД. Проверять, кто слушает порт (`ss -ltnp`), прежде
  чем диагностировать «пароль не подходит»;
- пароль в `.env` применяется к контейнеру только при первичной инициализации
  volume. После смены пароля в `.env` существующая БД продолжает ждать старый
  пароль — роль нужно обновить осознанно, а не переинициализировать данные.

Безопасный способ прогнать полный набор тестов, не затрагивая рабочие данные:
поднять отдельную БД на свободном порту, выполнить `alembic upgrade head`,
импортировать каталог упражнений и указать её в `TEST_DATABASE_URL`. После этого
`./workout-manager.sh test` использует именно её и откажется работать, если
переменная не задана или совпадает с `DATABASE_URL`. Часть интеграционных тестов
требует наполненного каталога упражнений.

Тестам устойчивого FSM нужен доступный Redis: без `REDIS_URL` они были бы
пропущены, поэтому `./workout-manager.sh test` проверяет подключение заранее.
Свои ключи такие тесты создают со случайными идентификаторами и удаляют после
себя, поэтому рабочий Redis они не портят; при желании можно указать отдельный
экземпляр через `TEST_REDIS_URL`.

Тесты рассчитаны на общую БД разработки, в которой есть посторонние записи:
они вычищают только свои данные по префиксу и не удаляют чужие. Проверки
защиты от потери админского доступа считают всех активных администраторов в
базе, поэтому на время таких тестов посторонние админские записи временно
деактивируются и восстанавливаются после теста (фикстура
`sole_database_admin` в `tests/integration/test_admin_users_api.py`). Если
прогон был прерван принудительно, стоит убедиться, что рабочая учётная запись
снова активна.

## Инцидент: бот не отвечает на анкету

Состояние анкеты хранится в Redis, и его недоступность выглядит как «бот
перестал понимать ответы».

1. Пользователь получает сообщение «Сервис временно недоступен, ответ не
   сохранён» — значит хранилище состояния недоступно, а не сломалась анкета.
2. Проверить Redis: `./workout-manager.sh doctor` (строка «Redis из .env») и
   `./workout-manager.sh logs redis`.
3. В логах бота искать `event=fsm_storage_unavailable` и
   `event=fsm_storage_error`: в них только имя операции и класс ошибки, без
   пользовательских данных.
4. Сохранённые профили и программы при этом не затронуты: PostgreSQL остаётся
   source of truth. Потеряться могут только незавершённые анкеты.
5. После восстановления Redis пользователи продолжают анкету с того же вопроса;
   перезапуск бота состояние не сбрасывает.

## Инцидент: программа не пришла

1. Проверить `generation_jobs` для профиля: статус последней генерации, число
   попыток и `last_error_code` сразу показывают, дошло ли дело до генерации.
   `status='succeeded'` вместе с `program_id` означает, что программа
   сформирована и проблема в доставке.
2. Проверить, существует ли программа в `workout_programs`.
3. Если существует — не запускать генерацию повторно автоматически.
4. Проверить `program_deliveries` и число попыток.
5. Повторять только delivery, если генерация уже успешна.
6. Проверить admin alert и correlation ID.
7. Job, застрявший в `running` после падения процесса, автоматически пока не
   восстанавливается (это Phase 1.2-D). Повторный запрос такой генерации будет
   отклонён как «уже выполняется»; до появления recovery запись переводят в
   терминальное состояние вручную, предварительно убедившись, что процесс
   генерации действительно не выполняется.

## Инцидент: AI не работает

1. Открыть `/ai` и посмотреть панель «Готовность AI-генерации» — она называет
   недостающий шаг и следующее действие. Тот же отчёт доступен как
   `GET /api/v1/admin/ai/readiness` (admin-only).
2. Посмотреть «Состояние AI-инфраструктуры»: дерево провайдер → эндпоинт →
   модели со статусами и временем последней проверки. Здесь сразу видно,
   какой провайдер используется, работает ли он, какие модели доступны и где
   именно проблема. Кнопка «Проверить подключения» выполняет короткий тест
   включённых эндпоинтов (не генерацию программы).
3. Различать три вещи: `отключён` — так настроено администратором;
   `не проверялся` — подключение ни разу не тестировали; `недоступен` /
   `работает нестабильно` — фактический сбой.
4. Проверить блок «Эффективная цепочка моделей»: если он пуст, вызывать нечем
   (модель/эндпоинт/провайдер отключены или протокол без адаптера).
5. Проверить секрет и сетевую доступность эндпоинта.
6. Проверить блок «Стратегия генерации»: при `PROGRAM_PRIMARY_GENERATOR`,
   отличном от `ai`, AI не будет основным генератором независимо от настроек.
7. Посмотреть журнал «Вызовы AI» на `/ai` (или `GET …/ai/usage`): статус,
   класс ошибки, задержка, токены.

Не включать новые модели/провайдеры в production без тестовой генерации и проверки validator/fallback.

## Инцидент: программа детерминированная, хотя AI включён

Это ожидаемое поведение при сбое, а не потеря данных: программа сгенерирована
и доставлена. Нужно понять причину.

1. Открыть на `/ai` журнал «Почему AI не сработал (fallback)» (или
   `GET /api/v1/admin/ai/fallback-events`). Для каждого случая видно:
   запрошенный генератор, фактический, причину и признак «AI вызывался».
2. Если «AI вызывался: нет» — это configuration fallback: конфигурация была
   заведомо нерабочей, запрос к провайдеру не отправлялся. Лечится настройкой;
   причина (`провайдер недоступен`, `подключение не проверялось`,
   `задача выключена` и т. п.) прямо указывает шаг.
3. Если «AI вызывался: да» — это runtime fallback: провайдер ответил ошибкой
   или ответ не прошёл валидацию. Смотреть журнал «Вызовы AI» и состояние
   инфраструктуры; при `таймаут AI` проверить `timeout_seconds` эндпоинта и
   задачи.
4. Та же причина хранится в самой программе
   (`GenerationInfo.fallback_reason_code`), поэтому по конкретной версии
   программы всегда можно сказать, почему она детерминированная.

## Удаление AI-конфигурации

Удаление не должно создавать битые ссылки, поэтому сервер проверяет
зависимости заранее.

1. Если модель привязана к задаче, удалить нельзя ни модель, ни её эндпоинт,
   ни провайдера: API вернёт 409, а UI перечислит блокирующие задачи.
2. Штатный порядок — сначала отключить (`Отключить`), затем при
   необходимости убрать модель из конфигурации задачи и только потом удалять.
3. Историю вызовов и audit удаление конфигурации не стирает: запись остаётся,
   ссылка на удалённую модель обнуляется.
4. Секрет удалённого эндпоинта удаляется из хранилища секретов автоматически,
   в том числе при каскадном удалении вместе с провайдером.

## Удаление анкет и программ

Раздел анкет накапливается: анкета остаётся в списке и после того, как программа
по ней собрана и отправлена. Чтобы список не превращался в свалку, неактуальные
записи удаляются — но порядок задан жёстко и защищён сервером.

**Порядок: сначала программы, потом анкета.**

1. Анкету с программами удалить нельзя: `DELETE /api/v1/profiles/{id}` вернёт 409
   со списком блокеров, UI покажет, сколько программ мешает. Причина
   асимметрии — цена ошибки: анкету заполнял человек в боте и восстановить её
   невозможно, а программа производна и собирается заново одной кнопкой.
2. `DELETE /api/v1/programs/{id}` удаляет программу целиком: все её версии и
   записи доставок. Версии по одной не удаляются — `program_id` и есть программа,
   а версии её история; частичное удаление сбило бы нумерацию следующей версии.
3. Удаление анкеты забирает и её записи доставок. `generation_jobs` удаляет база
   каскадом (`ON DELETE CASCADE` на профиль).
4. История операций генерации при удалении программы сохраняется: ссылка в
   `generation_jobs` обнуляется (`ON DELETE SET NULL`), сама запись остаётся.
5. Оба endpoint'а требуют роль admin. Наблюдателю сервер отвечает 403 — не
   только скрытием кнопок в UI.

Целостность обеспечивает приложение, а не СУБД: внешних ключей на
`workout_programs.profile_id` и `program_deliveries` в схеме нет, поэтому «сырой»
`DELETE` в базе оставил бы программы без анкеты. Удалять эти записи вручную
через SQL не следует.

### Маркеры исполнения анкеты

В списке анкет два признака, по ним же работают фильтры и сортировка:

| Маркер | Что означает | Откуда берётся |
|---|---|---|
| «Программа собрана» | по анкете есть хотя бы одна программа | `workout_programs` |
| «Отправлена» | программа ушла пользователю в Telegram | `program_deliveries.status = 'sent'`, дата из `delivered_at` |

Маркера «скачано пользователем» нет и не будет: Telegram Bot API не сообщает,
открыл ли человек присланный документ. Достоверно известен только факт отправки,
и показывается именно он — догадка в этом месте вводила бы в заблуждение при
решении, можно ли удалять анкету.

Признаки вычисляются запросом к фактическим данным, а не хранятся в анкете
флагами: дублирующее поле рассинхронизировалось бы после удаления программы.

## CI

CI (`.github/workflows/ci.yml`) запускается на каждый Pull Request и на push в
`main`. Джобы:

- **backend** — миграции до head, засев каталога упражнений из публичного
  репозитория `leszavr/workout`, полный `pytest` на реальной PostgreSQL и
  реальном Redis (сервис `redis:7`, `REDIS_URL` задан — тесты устойчивого FSM
  выполняются, а не скипаются);
- **migrations** — на чистой базе `upgrade head` → `downgrade base` →
  `upgrade head`, плюс проверка единственного alembic head;
- **frontend** — `npm ci`, lint, `tsc --noEmit`, production build.

При падении CI на Pull Request автоматически создаётся issue с меткой
`ci-failure`: перечислены упавшие джобы, коммит и ссылка на логи.

В CI используются одноразовые значения `JWT_SECRET` / `AI_SECRETS_KEY` — они
нужны только чтобы включить шифрование AI-секретов в тестах и не являются
production-секретами.
