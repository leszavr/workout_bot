# Changelog / История этапов

## 2026-08-23 — Phase 1.2-C: ProgramGenerationOrchestrator

До этого в системе жили два независимых application-level pipeline генерации.
Telegram шёл через `ProgramGenerationOrchestrator` (readiness gate, fallback,
журнал причин), а кнопка `Generate Program` в админке — через
`ProgramService.generate` со своим конвейером фильтр → генератор → валидатор →
репозиторий, без gate и без fallback. Persistent job у обоих путей уже был
общим (1.2-B), но orchestration-логика — разной.

- единственный вход в генерацию — `GenerationRequest`, единственный выход —
  `OrchestratorResult`. Telegram и Admin API приходят в одну точку;
- `ProgramService.generate` и `build_pools` удалены: сервис отвечает только за
  чтение сохранённых версий программ. Второго pipeline в коде больше нет;
- различие вызывающих слоёв выражено только запросом, а не отдельным
  конвейером: автогенерация после finalize берёт стратегию из конфигурации и
  разрешает fallback (`allow_fallback=True`), явный запрос администратора его
  запрещает (`allow_fallback=False`). Молча подменять выбранный администратором
  генератор нельзя — иначе он не узнает, что ИИ не сработал, и получит
  детерминированную программу вместо ответа о причине;
- fallback остаётся строго одним и выполняется внутри того же job: primary →
  fallback → окончательный отказ. Циклов «AI → fallback → AI» нет, второй job и
  вторая программа не создаются;
- наружу больше не выходят внутренние исключения AI Gateway: отказ приходит как
  `GenerationFailedError` со стабильным `GenerationErrorCode`, зафиксированным в
  момент отказа. HTTP-статус выбирается по коду — 409 (уже выполняется),
  422 (данные или валидация), 502 (сбой ИИ). Секреты вычищаются из текста
  отказа перед выходом наружу;
- `classify_error` уважает уже определённый код: причина «ИИ не сконфигурирован»
  больше не превращается в общий `generation_failed` при записи в job;
- ответ `POST /api/v1/profiles/{id}/programs/generate` расширен полями
  `requested_generator`, `actual_generator`, `fallback_used`,
  `fallback_reason_code`; существующие поля сохранены, тип `GenerateResponse` в
  веб-клиенте обновлён;
- `build_program_service` больше не собирает генераторы, `build_generation_orchestrator`
  стал единственным местом сборки generation pipeline;
- границы транзакций, идемпотентность и concurrency взяты из 1.2-B без
  изменений: короткая транзакция на создание/переход job, генерация вне
  транзакции, короткая транзакция на закрытие. Своего lock оркестратор не вводит.

Retry, worker и stale-recovery по-прежнему не реализованы (Phase 1.2-D).
Delivery остаётся отдельной операцией и частью оркестратора не является
(Phase 1.2-E).

Тесты: +38 (621 всего). Ключевое — архитектурный acceptance
`tests/unit/test_generation_boundary.py`: он статически разбирает исходники
Telegram gateway и Admin API и падает, если какой-то слой снова обращается к
генераторам, `ProgramValidator`, `SafetyEngine`, записи программы или переходам
состояния job. Поведенческие тесты закрывают контракт запроса (стратегия на
запрос, запрет подмены явно выбранного генератора), контракт результата и
ошибки, отсутствие утечки секретов, эквивалентность Telegram- и Admin-путей,
fallback без второго job и второй программы, идемпотентность и параллельные
вызовы.

## 2026-08-23 — Phase 1.2-B: persistent generation state + idempotency

До этого генерация была побочным эффектом запроса: её состояние нигде не
хранилось, а от дубликатов защищала только проверка «есть ли уже валидная
программа» в Python. Два параллельных запроса такую проверку проходили оба и
создавали две программы.

- миграция 0008: таблица `generation_jobs` — статус, число попыток, timestamps,
  код и краткое описание последней ошибки, ссылка на созданную версию программы
  (`FK (program_id, program_version) → workout_programs ON DELETE SET NULL`),
  профиль с `ON DELETE CASCADE`;
- домен `src/domain/generation.py`: state machine
  `PENDING → RUNNING → SUCCEEDED|FAILED` с явной таблицей разрешённых переходов;
  запрещённый переход — исключение, а не молчаливая перезапись статуса;
- **одна логическая генерация = (profile_id, бизнес-событие, номер попытки)**.
  `profile_id` как ключ не подошёл: анкета законно имеет несколько версий
  программы, а автогенерация после подтверждения анкеты и явный запрос
  администратора — разные бизнес-события;
- идемпотентность на стороне БД: `UNIQUE(idempotency_key)` +
  `INSERT ... ON CONFLICT DO NOTHING`; переход состояния —
  `UPDATE ... WHERE status = :expected`. Проверок «если нет — создай» в Python
  нет: они не защищают несколько backend-процессов;
- два параллельных запроса одной логической генерации создают ровно один job и
  ровно одну программу; повтор при активной генерации получает HTTP 409, повтор
  после успеха — уже созданную программу;
- AI-вызов вынесен за границы транзакции: состояние меняется короткими
  транзакциями до и после генерации, длительный HTTP-запрос не держит блокировки;
- ошибки разделены на non-retryable (конфигурация, валидация, отсутствующие
  данные) и transient (сеть, таймаут, rate limit, сбой persistence). Сам retry
  НЕ реализован: `RETRY_WAIT` и переход `FAILED → PENDING/RUNNING`
  зарезервированы для Phase 1.2-D, иначе job остался бы в состоянии без
  обработчика;
- в job не попадают промпт, ответ провайдера, ключи и PII: перед записью из
  текста ошибки вычищаются секреты, длина ограничена;
- `POST /api/v1/profiles/{id}/programs/generate` принимает необязательный
  `idempotency_key` и возвращает блок `generation` (статус, попытки, код ошибки,
  `reused_existing`);
- дубликат автозапуска в Telegram больше не будит администратора: pipeline
  отвечает `generation_in_progress`, а не «не удалось сформировать программу».

Тесты: +73 (583 всего) — state machine и запрещённые переходы, классификация и
санитизация ошибок, DB-enforced уникальность ключа, два параллельных запроса
через независимые сессии, rollback без phantom job, сохранение job после
пересоздания engine, отсутствие фиктивной программы при отказе, AI-генерация и
deterministic fallback под job-контуром, идемпотентность через HTTP API.

## 2026-08-23 — Phase 1.2-A: устойчивое состояние анкеты (Persistent FSM)

До этого состояние анкеты жило в `MemoryStorage` внутри процесса бота: при
перезапуске незавершённые анкеты исчезали, а второй экземпляр приложения не
видел прогресс пользователя.

- состояние и черновик анкеты перенесены в Redis (`REDIS_URL`);
  `src/infrastructure/telegram/fsm_storage.py` собирает aiogram `RedisStorage`
  и `RedisEventIsolation` с ключами, включающими `bot_id`;
- изоляция обновлений теперь общая для всех процессов: параллельные сообщения
  одного пользователя не обрабатываются одновременно разными экземплярами;
- `REDIS_URL` обязателен для бота: доступность проверяется до старта polling,
  ресурсы закрываются при остановке, повторный `close` безопасен;
- ошибки Redis нормализуются в `FSMStorageError`; новый error router
  (`apps/telegram_gateway/handlers/errors.py`) отвечает пользователю безопасным
  текстом вместо молчаливой потери ответа. В логах — только имя операции и
  класс ошибки;
- PostgreSQL остаётся source of truth: в Redis лежит только незавершённая
  анкета, и её сбой не затрагивает сохранённые профили и программы;
- инфраструктура: сервис `redis` в docker compose (AOF, healthcheck), сервис
  `redis:7` в CI, поддержка в `workout-manager.sh`
  (start/stop/status/doctor/logs/test) и переменные в `.env.example`;
- роутеры Telegram получили явные имена: порядок обработки стал проверяемым.

Тесты: +22 (510 всего) — restart-safe состояние, изоляция пользователей и
ботов, общий storage двух экземпляров, полный проход анкеты через Redis,
поведение при недоступном Redis, lifecycle storage и сквозной ответ
пользователю при сбое хранилища.

## 2026-08-22 — Управление пользователями и роли доступа

До этого администратор был один, задавался переменными окружения, а пароль
сравнивался в открытом виде.

- миграция 0007: `admin_users` (логин, роль, scrypt-хеш пароля, флаг
  обязательной смены, активность) и `admin_identities` (аккаунты внешних
  провайдеров);
- хеширование паролей через `hashlib.scrypt` из стандартной библиотеки — новых
  зависимостей не добавлено; параметры лежат внутри строки хеша, поэтому их
  можно усилить без инвалидации существующих паролей;
- роли **admin** и **viewer**. Ограничение viewer'а обеспечивает сервер: все
  изменяющие endpoint'ы переведены на `require_admin` (403), чтение — на
  `require_viewer`;
- CRUD пользователей: `GET/POST /api/v1/admin/users`,
  `GET/PATCH/DELETE /api/v1/admin/users/{id}`;
- смена своего пароля (`POST /api/v1/auth/change-password`) и сброс пароля
  администратором (`POST …/users/{id}/reset-password`) с одноразовым показом
  временного пароля;
- обязательная смена пароля: до неё API закрыт (403 `password_change_required`),
  работают только `/auth/me` и `/auth/change-password`;
- защита от потери доступа: нельзя понизить, отключить или удалить последнего
  активного администратора и нельзя удалить собственную учётную запись (409);
- `GET /api/v1/auth/me` — кто вошёл, роль, права; `GET /api/v1/auth/providers` —
  доступные способы входа;
- аварийный вход из переменных окружения сохранён и помечается в интерфейсе:
  при пустой базе или утрате паролей доступ не теряется;
- задел под вход через **Яндекс, VK, MAX**: пользователь и способ входа
  разделены, `authenticate_external` реализован, привязка аккаунтов доступна в
  интерфейсе. Сами OAuth-флоу не реализованы и помечены как недоступные;
- UI: раздел «Пользователи», страница смены пароля, в боковом меню видно кто
  вошёл и его роль; недоступные для роли действия скрыты;
- хеши паролей и временные пароли не попадают ни в API-ответы, ни в журнал.

Тесты: +78 (447 всего) — хеширование, аутентификация, роли, защита от потери
доступа, смена и сброс пароля, привязка внешних аккаунтов.

Исправлено попутно: тестовые модули задавали `ADMIN_LOGIN`/`ADMIN_PASSWORD`
присваиванием на уровне модуля, из-за чего в полном прогоне побеждал последний
импортированный модуль. Значения переведены на фикстуру с восстановлением.

Подробности — `USERS_AND_ACCESS.md`.

## 2026-08-22 — Phase 1.1.1: AI infrastructure management & reliability

Readiness и fallback:
- `AIReadinessService.runtime_gate()`: readiness теперь влияет на генерацию.
  При заведомо нерабочей конфигурации AI-запрос не выполняется вообще,
  оркестратор сразу берёт детерминированный генератор;
- структурированные причины fallback (`AIFallbackReason`) с разделением
  configuration (AI не вызывался) и runtime (AI вызывался и не смог);
- `GenerationInfo.fallback_reason_code` хранит машиночитаемую причину рядом с
  человекочитаемой (миграция не требуется: программа лежит в JSONB);
- fallback пишется в существующий журнал событий AI-контура
  (`ai_generation_fallback`) без персональных данных;
- `GET /api/v1/admin/ai/fallback-events` + раздел «Почему AI не сработал» в
  админке: requested/actual generator, причина, признак «AI вызывался».

Infrastructure health:
- `AIInfrastructureHealthService` и `GET /api/v1/admin/ai/infrastructure-health`:
  дерево provider → endpoint → model → задачи строится динамически из
  конфигурации, собственного реестра нет ни в backend, ни во frontend;
- разделены configuration state (`enabled`), infrastructure health
  (`AIHealthState`) и model availability (`AIModelAvailability`);
- health выводится из сохранённого connection test и последнего реального
  AI-вызова: сценарий «провайдер отвалился» виден без запросов к провайдеру;
- `POST …/infrastructure-health/refresh` — активная проверка включённых
  эндпоинтов через существующий минимальный ping, без генерации программ;
- панель «Состояние AI-инфраструктуры» на `/ai` с manual refresh, last checked,
  loading/error states и авто-обновлением состояния.

Lifecycle конфигурации:
- edit/enable/disable/safe delete для провайдера, эндпоинта и модели в UI
  (раньше в интерфейсе были только create и переключение enabled);
- зависимости проверяются до удаления: 409 с машиночитаемым списком блокеров
  вместо ошибки целостности БД; broken references не создаются;
- секреты удаляемых эндпоинтов вычищаются из SecretStore, включая каскадное
  удаление вместе с провайдером;
- usage/audit-история при удалении конфигурации сохраняется.

CI:
- `.github/workflows/ci.yml` на PR и push в `main`: backend-тесты на реальной
  PostgreSQL с засевом каталога упражнений, проверка цепочки миграций
  (head → base → head) и единственного alembic head, frontend
  lint/typecheck/production build;
- при падении CI на PR автоматически создаётся issue с меткой `ci-failure`.

Тесты: +80 (369 всего) — readiness gate, классификация runtime-причин,
состояния health, safe delete и lifecycle через API.
