# AI Reliability and Prompt Management

**Дата:** 28 августа 2026
**Ветка:** `feature/ai-reliability-prompt-management`
**База:** `main @ cfbd59f`
**Повод:** FINDING-1 из `docs/infrastructure/STAGING_FULL_E2E_ACCEPTANCE_REPORT.md`

---

## 1. Executive Summary

Full STAGING E2E прошёл с вердиктом PASS, но зафиксировал продуктовый дефект:
ИИ не собрал программу, и пользователь получил алгоритмическую. Причина не в
подключении к ИИ и не в качестве модели как таковом — в механике исправления
ответа и в бесполезности настроенной цепочки резервных моделей.

Что изменено:

1. **Repair получает достаточный контекст.** Запрос на исправление теперь несёт
   исходный system-промпт (правила и схему), собственный предыдущий ответ
   модели, ошибки валидации и полный перечень разрешённых
   `exercise_external_id`. Выдуманные идентификаторы называются прямо. Раньше
   уходило одно `user`-сообщение «исправь эти ошибки».

2. **Невалидный вывод переводит генерацию на следующую модель.** Перебор цепочки
   перенесён в `AIProgramGenerator`: только он умеет отличить транспортный успех
   от пригодного ответа. `AIGateway` получил двухшаговый контракт
   `prepare()` + `generate_once()`; прежний `generate()` сохранён без изменений.

3. **Deterministic fallback остался последним рубежом.** Генератор отказывает
   только после исчерпания всей AI-цепочки; решение о переходе на алгоритм
   по-прежнему принимает `ProgramGenerationOrchestrator`.

4. **Телеметрия попыток.** Новое событие `ai_model_attempts` и
   `GET /api/v1/admin/ai/model-attempts` отвечают на вопрос, на который журнал
   вызовов ответить не может: прошёл ли первый ответ, сколько было исправлений,
   почему модель оставлена и дошла ли очередь до резервной.

5. **Управление инструкциями для ИИ.** Полный CRUD через Admin API и новая
   вкладка `/ai/prompts`: список версий с превью, полный текст без усечения,
   создание, правка, безопасное удаление.

Валидатор не ослаблен ни в одном месте: выдуманный `external_id` остаётся
ошибкой `exercise_not_found`. Миграций нет — схема `prompt_templates` уже
содержала всё необходимое.

Проверено: 642 unit-теста и 198 интеграционных на реальной PostgreSQL, плюс
production-сборка веб-интерфейса. Реальные платные AI-запросы не выполнялись:
цепочка моделей и repair проверены сценарными фейками.

## 2. Root Cause

### 2.1 Что произошло на staging

Профиль `REQ-20260828-00002`, цепочка моделей задачи `workout_generation`:

```text
priority 1 (primary): Routerai  / qwen/qwen3.8-flash
priority 2:           Routerai  / z-ai/glm-5.3-flash
priority 3:           Tabitoken / claude-opus-5
```

Разбор по попыткам:

| Попытка | Что было | Вход | Результат |
|---|---|---|---|
| 1 (07:10:08, 121 с) | полный промпт, safe pool из 523 упражнений | 6758 токенов | структурно корректная программа, но `external_id` = `Cable_Lat_Pulldown_(Generic)` — такого упражнения в каталоге нет. `ProgramValidator` отклонил: `exercise_not_found` |
| 2 (repair, 96 с) | «исправь вот эти ошибки» | 120 токенов | фрагмент без обязательных полей (`title`, `duration_weeks`, `training_days_per_week`, `training_days`) и лишний ключ `exercise` |
| 3 (repair, 72 с) | то же | 131 токен | `training_days` списком не-объектов, лишний ключ `exercises` |

Итог: 4 мин 52 с ожидания, затем детерминированный fallback.

### 2.2 Первая причина: repair не мог исправить

`AIProgramGenerator._repair_request` формировал одно `user`-сообщение:

```python
repair_prompt = (
    "Your previous output did not satisfy the required schema or validation rules.\n\n"
    f"Validation errors:\n{error_message}\n\n"
    "Return ONLY the corrected JSON. No explanations, no markdown."
)
```

В запросе не было ни system-промпта со схемой, ни предыдущего ответа модели, ни
safe pool. Вход сжимался с 6758 до ~120 токенов. Модель получала требование
исправить документ, **не видя ни документа, ни целевой структуры, ни того, из
чего выбирать упражнения**.

Исходная ошибка была единичной и легко исправимой: один неверный `external_id`
из ~13. Но исправить его модель не могла — она не знала ни какой ответ правит,
ни какие идентификаторы допустимы. Обе repair-попытки не приблизили результат, а
увели дальше: вывод деградировал от «почти валидной программы» до «фрагмента без
обязательных полей».

### 2.3 Вторая причина: цепочка fallback не задействована

`AIGateway.generate` перебирал кандидатов только при `AIError`:

```python
for candidate in candidates:
    try:
        return await self._execute(...)
    except AIError as exc:
        last_error = exc
        continue
```

Провайдер отвечал `200 OK` — ошибка была валидационной
(`ProgramGenerationError`), возникала **выше** Gateway, уже после возврата
ответа. Поэтому все три вызова ушли в `qwen3.8-flash` (`model_pk=2`), а
`glm-5.3-flash` и `claude-opus-5` не вызывались ни разу. Настроенные резервные
модели в этом сценарии были декоративными.

Архитектурная суть: **транспортный успех не равен пригодному ответу**. Gateway
знает только про транспорт, а решение «этот вывод бесполезен» принимает
генератор — после схемы, safe pool и каталога. Перебор цепочки находился в слое,
у которого не было информации для этого решения.

### 2.4 Третья причина: промпт недостаточно жёстко запрещал изобретать `external_id`

Правила «используй ТОЛЬКО упражнения из safe_pool» и «НЕ придумывай упражнения»
в `prompts/program_generator/v1/system.txt` были, но flash-модель при списке из
523 идентификаторов склонна «достраивать» правдоподобные имена.

Важно: отказ вероятностный, а не детерминированный. Предыдущие генерации на том
же staging с той же моделью завершались успехом (`ai_usage_records` id 2, 6 —
`model_pk=2`, `generation_source=ai`). Модель способна выдавать валидный
результат; не работал механизм восстановления после единичной ошибки.

## 3. AI Repair Changes

### 3.1 Контекст repair-запроса

`AIProgramGenerator._repair_request` формирует три сообщения:

| Роль | Содержимое | Зачем |
|---|---|---|
| `system` | исходный system-промпт задачи | правила и схема ответа; без них модель не знает целевой структуры |
| `assistant` | предыдущий ответ модели целиком (до 20 000 символов) | сам документ, который нужно править |
| `user` | ошибки валидации + выдуманные `external_id` + полный перечень разрешённых + запрет изобретать | что не так, что именно заменить и из чего выбирать |

Текст `user`-сообщения:

```text
Твой предыдущий ответ не прошёл проверку.

Исправь ИМЕННО его: сохрани всё, что прошло проверку, и измени только то,
что вызвало ошибки. Не составляй программу заново.

Ошибки проверки:
exercise_not_found: Упражнение Cable_Lat_Pulldown_(Generic) отсутствует в каталоге

Идентификаторы, которых нет в разрешённом наборе (заменить обязательно):
Cable_Lat_Pulldown_(Generic)

Разрешённые exercise_external_id (используй ТОЛЬКО их, придумывать новые
запрещено):
<перечень>

Верни ТОЛЬКО исправленный JSON по той же схеме, без пояснений и без markdown.
```

### 3.2 Что намеренно НЕ дублируется

Полный исходный `user`-промпт (анкета + описания упражнений с мышцами,
оборудованием, сложностью) в repair не передаётся. Обоснование: он в разы больше
всего остального контекста, а для точечного исправления не нужен — программа уже
составлена под этот профиль, менять надо только то, что не прошло проверку.
Требование задачи «минимальный достаточный контекст + максимальная вероятность
валидного исправления» закрыто именно так.

Перечень разрешённых идентификаторов передаётся без описаний — только `external_id`
через запятую. Это ровно то, что нужно для замены ссылки, и в разы дешевле полного
блока safe pool.

Ограничение на предыдущий ответ (`MAX_PREVIOUS_RESPONSE_CHARS = 20_000`) —
защита от вырожденного случая, когда модель вместо программы вернула поток
текста.

### 3.3 Выдуманные идентификаторы называются прямо

Идентификаторы вынимаются из ответа регулярным выражением, а не парсингом JSON:

```python
def _used_exercise_ids(content: str) -> list[str]:
    return re.findall(r'"exercise_external_id"\s*:\s*"([^"]{1,200})"', content)
```

Причина: ответ может быть невалидным JSON, а назвать выдуманный идентификатор
нужно и в этом случае. Из найденных отбираются те, которых нет в разрешённом
наборе, и первые 20 попадают в отдельный блок «заменить обязательно».

### 3.4 Repair адресуется той же модели

Исправление своего ответа запрашивается у той модели, которая его выдала:
`generate_once(candidate, repair_request, chain)`. Отправлять чужой ответ другой
модели на правку бессмысленно — она его не писала и правила «сохрани то, что
прошло проверку» не выполнит осмысленно. Смена модели происходит на уровень
выше, после исчерпания repair-попыток.

### 3.5 Строгость валидации сохранена

Валидатор не менялся. `_parse_and_validate` по-прежнему выполняет:

1. извлечение JSON (`AIOutputParser`);
2. подстановку полей, за которые модель не отвечает (`profile_id`,
   `schema_version`, `version`, `status`);
3. подстановку `exercise_source` из каталога (`_apply_catalog_sources`) — модель
   источник не выбирает;
4. `validate_schema` — строгая Pydantic-схема;
5. `validate` — safe pool, каталог, дубликаты, число дней, диапазоны повторений.

Каталог для AI-вывода — это safe pool и только он (`pool.allowed_ids()`).
Выдуманный `external_id` даёт `exercise_not_found` и после трёх попыток, и после
тридцати. Тест `test_invented_exercise_is_still_rejected_by_validator`
фиксирует это свойство.

### 3.6 Промпт v1 усилен

В `prompts/program_generator/v1/system.txt` правило 2 стало конкретным:

```text
2. НЕ придумывай упражнения, которых нет в списке. external_id копируй из
   списка символ в символ: не переводи, не сокращай, не дополняй пояснениями
   вроде «(Generic)». Если подходящего упражнения в списке нет, возьми
   ближайшее из списка — выдуманный external_id делает всю программу
   недействительной.
```

Формулировка адресует наблюдавшуюся ошибку буквально: `(Generic)` — это ровно
тот суффикс, который модель дописала. Это не замена механизму исправления, а
снижение вероятности первой ошибки.

## 4. Model Fallback Changes

### 4.1 Целевой поток

```text
модель 1 (primary)
   ├── ответ валиден ─────────────────────────────── SUCCESS
   └── невалиден
         ↓ repair × N (по умолчанию 2), той же модели
         ├── валиден ───────────────────────────────  SUCCESS
         └── всё ещё невалиден
               ↓
модель 2 (fallback)
   ├── валиден ───────────────────────────────────── SUCCESS
   └── невалиден → repair × N → …
               ↓
модель N
               ↓
все AI-кандидаты исчерпаны
               ↓
ProgramGenerationOrchestrator → DeterministicProgramGenerator
```

### 4.2 Кто ведёт перебор

Перебор перенесён из `AIGateway` в `AIProgramGenerator`. `AIGateway` получил два
новых метода:

| Метод | Что делает |
|---|---|
| `prepare(request)` | проверяет, что задача настроена и включена; возвращает `PreparedChain` — конфигурацию задачи и упорядоченную цепочку кандидатов (primary → fallback) |
| `generate_once(candidate, request, chain)` | один вызов конкретного кандидата; сообщения берутся из переданного `request`, поэтому repair уходит той же модели без пересборки цепочки |

`generate(request)` сохранён без изменения поведения: он вызывает `prepare()` и
сам идёт по кандидатам, падая только когда не ответил ни один. Это нужно
вызывающим сторонам, которым достаточно первого транспортно успешного ответа.

Обоснование границы: решение «этот ответ бесполезен» требует схемы, safe pool и
каталога. Такой информации у Gateway нет и быть не должно — он работает с
транспортом и учётом вызовов. Поэтому перебор оказался в слое, который умеет
оценить результат.

### 4.3 Категории отказа различаются

Обе категории ведут к следующей модели, но в журнале сохраняются раздельно:

| Исход попытки | Что было | repair запрашивался |
|---|---|---|
| `success` | программа принята валидатором | возможно |
| `invalid_output` | ответ получен, но не прошёл схему/safe pool/каталог даже после исправлений | да |
| `provider_error` | сбой транспорта или API: таймаут, лимит, сетевой отказ, ошибка провайдера | нет — править нечего |
| `budget_exhausted` | общий бюджет генерации исчерпан, перебор прекращён | нет |

Транспортное поведение адаптера не менялось: повторы `429`/`5xx` с растущей
паузой, уважение `Retry-After`, отличие отказа защитного контура (HTML/пустое
тело) от отказа самого API (JSON) остаются внутри `OpenAICompatibleAdapter`.

Тип последней AI-ошибки выбрасывается наружу как есть:

```python
if last_error is not None:
    raise last_error
```

Это важно для классификации: `classify_error` различает `AITimeoutError`,
`AIRateLimitError`, `AIConnectionError` и даёт разные `AIFallbackReason`. Оборачивать
их в общий `ProgramGenerationError` значило бы потерять причину в журнале
fallback.

### 4.4 Бюджет времени распространяется на всю цепочку

`DEFAULT_TOTAL_BUDGET_SECONDS = 240` действует на генерацию целиком, включая
перебор моделей и repair. Две точки проверки:

1. перед переходом к следующей модели — если время вышло, попытка не начинается
   (исход `budget_exhausted`);
2. перед repair-запросом — если время вышло, исправление не запрашивается, и
   перебор прекращается совсем (`fatal=True`).

Без общего бюджета таймауты перемножались бы: модели × попытки × `timeout_seconds`.
При трёх моделях, трёх попытках и таймауте 120 с это 18 минут ожидания вместо
понятного отказа.

### 4.5 Deterministic fallback не изменён

Генератор по-прежнему только отказывает; переход на алгоритм выполняет
`ProgramGenerationOrchestrator` по своим правилам (`allow_fallback`, readiness
gate, строго один fallback без циклов). Разница в том, **когда** генератор
отказывает: раньше — после трёх попыток одной модели, теперь — после исчерпания
всей настроенной цепочки.

Для автогенерации после подтверждения анкеты (`allow_fallback=True`) поведение
пользователя не меняется: программу он получит в любом случае. Для явного запроса
администратора (`allow_fallback=False`) отказ по-прежнему приходит с причиной, а
не подменяется молча другой программой.

### 4.6 Телеметрия

Событие `ai_model_attempts` пишется в существующий журнал AI-контура (отдельной
таблицы не вводится). Одна запись = одна генерация, внутри — по строке на модель:

```json
{
  "task_type": "workout_generation",
  "models_tried": 2,
  "attempts": [
    {"priority": 1, "is_primary": true, "provider": "routerai",
     "model_id": "qwen/qwen3.8-flash", "model_pk": 2,
     "initial_valid": false, "repair_attempts": 2,
     "outcome": "invalid_output", "error_type": "ProgramGenerationError",
     "detail": "Program validation failed: exercise_not_found: ..."},
    {"priority": 2, "is_primary": false, "provider": "routerai",
     "model_id": "z-ai/glm-5.3-flash", "model_pk": 3,
     "initial_valid": true, "repair_attempts": 0,
     "outcome": "success", "error_type": null, "detail": null}
  ]
}
```

Поля отвечают на требования задачи: какая модель вызывалась (`model_id`,
`priority`, `is_primary`), прошёл ли первый ответ (`initial_valid`), запрашивалось
ли исправление (`repair_attempts`), почему модель оставлена (`outcome`,
`error_type`, `detail`), выбиралась ли следующая (`models_tried` и порядок
записей), использован ли deterministic fallback (существующий журнал
`ai_generation_fallback`).

Секретов в записи нет: `detail` проходит через `safe_error_message`, который
вычищает bearer-токены, `sk-…` и пары `api_key/authorization/token/secret/password`,
и обрезается до 300 символов. Промпты, ответы моделей, `profile_id` и содержимое
программы не сохраняются.

Сбой журнала не ломает генерацию — запись обёрнута в `try/except` с логированием
(`test_telemetry_failure_does_not_break_generation`).

## 5. Prompt Management

Инструкция для модели перестала быть деталью реализации. До этого её текст
существовал только в файлах образа и в таблице `prompt_templates`: чтобы
поправить формулировку, требовался SQL или пересборка контейнера. Промпт-инжиниринг
состоит из итераций, поэтому он сделан штатной операцией администратора.

### 5.1 Существующая архитектура расширена, а не продублирована

Параллельной подсистемы промптов не вводилось. Использованы существующие
`PromptTemplate` (домен), `PromptTemplateRepository` (persistence),
`ai_task_configs.prompt_version` (выбор версии) и `PromptLoader` (загрузка
DB-first, файловый fallback). Добавлены только отсутствовавшие операции чтения
одного промпта, правки и удаления.

### 5.2 Admin API

Все endpoint'ы под существующей защитой: чтение — `require_viewer`, запись —
`require_admin`.

| Операция | Endpoint | Ответ |
|---|---|---|
| список версий задачи | `GET /api/v1/admin/ai/prompts/{task_type}` | превью, длины, `in_use`, `next_version`, `active_version` |
| полный текст | `GET /api/v1/admin/ai/prompts/detail/{id}` | `system_prompt` и `user_template` целиком |
| создать | `POST /api/v1/admin/ai/prompts` | 201 с полным текстом |
| изменить | `PATCH /api/v1/admin/ai/prompts/detail/{id}` | 200 с полным текстом |
| удалить | `DELETE /api/v1/admin/ai/prompts/detail/{id}` | 204 либо 409 с блокерами |

Префикс `detail` нужен потому, что `GET /prompts/{task_type}` уже занят списком:
числовой id и тип задачи иначе разбирались бы одним маршрутом.

**Полный текст не усечён в детальном ответе** — это прямое требование задачи.
Список отдаёт `system_prompt_preview` (160 символов, схлопнутые пробелы) плюс
`system_prompt_length` и `user_template_length`: инструкция бывает в десятки
килобайт, и тянуть её в список незачем. Тест
`test_prompt_create_list_and_full_detail` сравнивает сохранённый и возвращённый
текст посимвольно и отдельно проверяет, что в списке полного текста нет.

### 5.3 Метаданные

Возвращаются: `id`, `task_type`, `version`, `name`, `enabled`, `in_use`,
`created_at`, `updated_at`. Отдельного поля «описание» не добавлялось — `name`
достаточно для различения версий, а второе текстовое поле «на будущее» не
требуется.

`in_use` вычисляется сравнением с `ai_task_configs.prompt_version`, а не хранится:
дублирующий флаг рассинхронизировался бы с настройкой задачи.

### 5.4 Версии и правка

`version` при создании необязателен — без него берётся следующий свободный номер
(`next_prompt_version`). Администратор правит текст, а не ведёт нумерацию.

Правка существующей версии **разрешена**, и это изменение прежнего поведения.
Раньше версия объявлялась неизменяемой, и на каждую формулировку требовалось
создавать новую. Обоснование: промпт-инжиниринг — это десятки мелких правок, и
нумерация под каждую превращает список в мусор, а задачу заставляет
переключаться после каждого шага. Полноценная система контроля версий с
diff'ами и откатами не вводилась: это несоразмерно задаче «администратор
итеративно доводит инструкцию».

`task_type` и `version` через `PATCH` не меняются — они образуют идентичность
промпта, на которую ссылается конфигурация задачи. Их подмена превратила бы
правку текста в незаметный перенос ссылки. Схема `PromptPatch` их просто не
содержит, поэтому попытка получает 422
(`test_prompt_version_cannot_be_moved_by_patch`); репозиторий дополнительно
отбрасывает эти поля, если они придут другим путём.

Дубликат существующей версии при явном указании `version` — 409
(`test_prompt_duplicate_version_is_conflict`).

### 5.5 Назначение промпта задаче

Отдельного механизма не создавалось: версия выбирается существующим полем
`prompt_version` в настройках задачи (`PUT /api/v1/admin/ai/tasks/{task_type}`),
и там же работает серверная проверка `validate_enable` — включить задачу с
несуществующей версией нельзя. Список промптов сообщает `active_version`, чтобы
интерфейс мог пометить используемую.

Тест `test_prompt_edit_is_visible_to_generation_loader` подтверждает замкнутость
цикла: текст, изменённый через API, `PromptLoader` возвращает генерации.

### 5.6 Admin Web

Новая вкладка `/ai/prompts` (`apps/web/app/ai/prompts/page.tsx`,
`components/ai/PromptsSection.tsx`). Отдельная вкладка, а не блок внутри «Задач»:
задача отвечает на вопрос «какие модели и с какими параметрами вызывать», а
инструкция — «что и в каком виде у них просить»; смешивать значит прятать текст
промпта под полем «версия инструкции».

Список: номер версии, название, состояние (`используется задачей` /
`не используется`, `выключена`), превью, длины текстов, дата изменения, действие
«Открыть полностью».

Карточка: название, `system` и `user` в больших `textarea` (20 и 14 строк,
монопространственный шрифт), полный текст без визуального усечения. Действия —
«Сохранить», «Отменить правки», «Удалить». Кнопка сохранения активна только при
реальных изменениях.

Создание: форма с теми же полями и предупреждением, что создание не переключает
задачу на новую инструкцию.

Удаление: `window.confirm` с номером и названием версии. Для активной инструкции
кнопка заблокирована, показано объяснение; если сервер всё же вернул 409,
блокеры разворачиваются в текст ошибки — та же схема, что уже используется для
провайдеров и моделей.

Состояния загрузки, ошибки и пустого списка реализованы существующими
примитивами (`Skeleton`, `Empty`, `Notice`). Ограничение прав для наблюдателя
(`canWrite=false`) убирает изменяющие действия; сам запрет обеспечивает сервер.

### 5.7 Политика удаления

**Выбрана hard delete.** Обоснование: внешних ключей на `prompt_templates` нет —
ни `ai_usage_records`, ни `ai_audit_events` текст инструкции или ссылку на неё не
хранят. Удаление не оставляет битых ссылок в базе и не разрушает историю разбора
инцидентов. Soft delete или флаг «архивная» потребовали бы миграции, нового
состояния в UI и фильтрации во всех выборках — без единой конкретной причины.

Единственный блокер — инструкция, выбранная в настройках задачи:

```text
DELETE /api/v1/admin/ai/prompts/detail/{id}
→ 409
{
  "detail": {
    "message": "Невозможно удалить инструкцию: инструкция №3 выбрана в настройках включённой задачи «workout_generation». Сначала выберите для задачи другую версию инструкции.",
    "blockers": [
      {"type": "ai_task_config", "task_type": "workout_generation",
       "task_enabled": true, "prompt_version": 3,
       "detail": "инструкция №3 выбрана в настройках включённой задачи «workout_generation»"}
    ]
  }
}
```

Проверка выполняется сервисным слоем (`prompt_dependencies`), а не базой:
`ai_task_configs.prompt_version` — это номер версии, а не внешний ключ. Без
проверки задача осталась бы с номером инструкции, которой больше нет, и генерация
молча уехала бы на файловый промпт — то есть на другой текст, о чём администратор
бы не узнал.

Блокируются и включённые, и выключенные задачи, ссылающиеся на версию: выключенная
задача — это конфигурация, которую администратор собирается включить, и терять её
инструкцию так же нельзя.

Формат 409 повторяет существующий `AIDependencyError` для провайдеров, эндпоинтов
и моделей, поэтому UI разбирает его уже написанным кодом.

Все три операции пишутся в audit-журнал: `ai_prompt_created`,
`ai_prompt_updated`, `ai_prompt_deleted`. Текст инструкции в metadata не
дублируется — только задача, версия и имена изменённых полей: журнал читается
администратором и попадает в бэкапы, а сам промпт всегда доступен через API.

### 5.8 Prompt testing usability (PART H)

Полноценный AI playground не вводился — задача прямо это допускает, а
существующей архитектуры для него недостаточно (потребовался бы отдельный контур
прогонов с хранением результатов). Реализован рабочий цикл, которого достаточно
для текущей фазы:

```text
создать/изменить инструкцию (/ai/prompts)
        ↓
выбрать её версию в настройках задачи (/ai/tasks)
        ↓
запустить генерацию (кнопка Generate Program или анкета в боте)
        ↓
посмотреть результат: программа + журнал попыток моделей (/ai/logs)
```

Журнал попыток моделей здесь работает как обратная связь по промпту: видно,
принимался ли первый ответ и сколько исправлений понадобилось. Это ровно тот
сигнал, который нужен для оценки формулировки.

## 6. Database Changes

**Миграций нет.** Схема `prompt_templates` (Alembic `0004`) уже содержала всё
необходимое: `id`, `task_type`, `version`, `name`, `system_prompt` (`Text`),
`user_template` (`Text`), `enabled`, `created_at`, `updated_at` и
`UNIQUE(task_type, version)`. Новые операции (чтение по id, `UPDATE`, `DELETE`)
работают по существующим колонкам и индексам.

Ссылочная целостность проверена: внешних ключей на `prompt_templates` в схеме нет
(поиск по `alembic/versions` и `models.py`), поэтому удаление строки не может
оставить висящих ссылок. Единственная связь — логическая
(`ai_task_configs.prompt_version`), и её защищает сервисный слой; тест
`test_prompt_used_by_task_cannot_be_deleted` проверяет и отказ удаления, и то, что
после переключения задачи она ссылается на существующую инструкцию.

Alembic head остался `0008`. Свежая установка и обновление с текущей схемы не
требуют дополнительных шагов.

Новое событие `ai_model_attempts` использует существующую таблицу
`ai_audit_events` (`metadata_json` — `JSONB`). Отдельной таблицы под попытки
моделей намеренно нет: журнал событий AI-контура должен быть один.

## 8. Risks / Remaining Limitations

1. **Стоимость и время выросли в худшем случае.** Раньше неудачная генерация
   стоила три вызова одной flash-модели. Теперь при трёх настроенных моделях это
   до девяти вызовов, причём repair несёт больший вход (предыдущий ответ +
   перечень идентификаторов). Ограничитель — общий бюджет 240 с: он обрывает
   перебор, но не является лимитом расхода. Если в цепочке стоит дорогая модель,
   стоит учитывать это при настройке.

2. **Repair не видит описаний упражнений.** В исправление уходят только
   `external_id` без мышц, оборудования и сложности. Для замены неверной ссылки
   этого достаточно, но осмысленно подобрать замену «по смыслу» модель на этом
   контексте не может — она видела описания в первом запросе и должна опираться
   на свой предыдущий ответ. Если практика покажет, что замены получаются
   неудачными, потребуется передавать краткие описания только для упомянутых
   упражнений.

3. **Успех остаётся вероятностным.** Изменения повышают шансы восстановления
   после единичной ошибки и задействуют резервные модели, но не гарантируют
   AI-генерацию. При полном отказе цепочки пользователь по-прежнему получает
   алгоритмическую программу — это заложенное поведение, а не дефект.

4. **Эффект не подтверждён на реальных моделях.** Все проверки — на фейках.
   Реальное поведение `qwen3.8-flash` на новом repair-промпте не измерялось,
   потому что это требует платных запросов. Следующий staging-прогон должен
   зафиксировать, что цепочка отрабатывает и что журнал попыток заполняется.

5. **Правка активной инструкции применяется без предупреждения на сервере.**
   Изменённый текст уходит в следующую генерацию сразу. UI об этом предупреждает,
   но серверного подтверждения нет. Это осознанно: администратор для этого и
   правит инструкцию, а лишний шаг мешал бы итерациям.

6. **`enabled=false` у промпта означает «не использовать»**, но задача может
   ссылаться на выключенную версию. `PromptLoader` в этом случае берёт файловый
   промпт (условие `template.enabled`), а `validate_enable` не даст включить
   задачу с такой версией. Поведение унаследовано и не менялось; тонкость в том,
   что уже включённая задача при выключении промпта тихо перейдёт на файловый
   текст. Отдельного предупреждения об этом нет.

7. **Журнал попыток не связан с конкретной программой.** В `ai_model_attempts`
   намеренно нет `profile_id` и `program_id` — это персональные и бизнес-данные.
   Сопоставление с генерацией выполняется по времени. Для разбора инцидента этого
   достаточно, для аналитики «какая модель чаще ошибается на каких профилях» —
   нет.

8. **`GenerateProgramRequest.prompt_version` по-прежнему не используется.**
   Версия берётся из настроек задачи. Поле принимается API и игнорируется —
   унаследованное расхождение; его удаление меняет публичный контракт и вынесено
   отдельно.

9. **AI playground не реализован.** Прогон инструкции требует переключения
   задачи на нужную версию, то есть затрагивает конфигурацию, которой пользуется
   и Telegram. Для параллельного сравнения версий без влияния на пользователей
   нужен отдельный контур прогонов; это за границей текущей задачи.

10. **Staging не обновлялся.** Изменения только в коде; инфраструктура, VPN,
    маршрутизация, firewall и конфигурация PostgreSQL не затрагивались.
