# Сетевая граница Telegram Gateway

**Дата:** 2–3 сентября 2026
**Ветка:** `feature/gateway-network-boundary`
**База:** `main @ 15bd8f2`
**Ревизия БД:** `0012 → 0013`
**Версии:** Backend 2.3.0, Gateway 1.0.0, Worker 1.0.0, контракт Telegram 1
**Staging:** развёрнуто и проверено 3 сентября (`0013 (head)`)

## Задача

Сделать Telegram Gateway независимой единицей развёртывания в EU: он должен
работать с Backend только по HTTP и не иметь доступа к PostgreSQL. Персональные
данные, включая данные о здоровье, должны храниться в RU.

## Что было

Аудит фактического состояния (не по документации):

- Gateway импортировал 27 модулей `src.*`, включая `QuestionnaireService`,
  `ProfileFinalizationService`, репозитории и декларацию вопросов;
- сам создавал session factory и писал `profiles`, `program_deliveries`, а через
  кросс-пакетный импорт `apps.backend.api.v1.dependencies`
  (`apps/telegram_gateway/pipeline.py`) — ещё `workout_programs` и
  `generation_jobs`;
- ответы анкеты целиком лежали в Redis EU: на момент аудита один живой ключ на
  4182 байта с именем, возрастом, ростом, весом, ограничениями движений и
  рекомендациями врача, **без TTL** (`ttl` = -1);
- фотографии оборудования Gateway скачивал из Telegram и писал на диск
  EU-контейнера через `LocalFileStorage`.

То есть Gateway был не транспортом, а вторым экземпляром приложения с общей
базой. Развернуть его отдельно было нельзя.

## Ключевые решения

### Server-driven view вместо передачи данных

Контракт (`src/domain/telegram_contract.py`) описывает не предметные данные, а
то, что показать: `TelegramView` = список сообщений с текстом, кнопками и типом
операции (отправить / заменить / удалить) плюс toast.

Альтернатива — отдавать шлюзу вопрос и варианты ответа, а рендерить в EU. Она
отвергнута: тогда Gateway снова знает, что такое вопрос, обязательность и
переход, и новый вопрос в анкете требует его развёртывания. Именно этого
независимость и должна была устранить.

Цена решения: контракт описывает отображение, поэтому новый тип элемента
интерфейса — это изменение контракта. Для текущего набора (текст, кнопки,
документ, toast) этого не требуется.

Типы лежат в домене, а не в слое API: у контракта две стороны в одном
репозитории, и общий тип — единственный способ не разойтись молча.

### Серверная сессия диалога: отдельная таблица

`telegram_sessions` (миграция `0013`) хранит позицию диалога, черновик профиля,
правящийся вопрос и ключ идемпотентности.

Колонки в `profiles` рассматривались и отвергнуты: сессия существует **до**
профиля. Диалог, брошенный на первом вопросе, не должен появляться в
`GET /profiles` и в аналитике, а строку-черновик пришлось бы фильтровать во всех
запросах администратора сразу.

Черновик пишется с первого ответа, а не при финализации: иначе прерванная анкета
теряется целиком, и человек, ответивший на тридцать вопросов, начинает заново.

Ключ — `telegram_user_id` с уникальным ограничением: у пользователя один
активный диалог, и без ограничения параллельные обновления создали бы две
сессии.

### Идемпотентность по `update_id` Telegram

Хранится не только номер обновления, но и отданный ответ (`last_view`).

Telegram переотправляет неподтверждённое обновление, а Gateway повторяет запрос
при таймауте. Без ключа один ответ пользователя продвинул бы анкету на два шага;
без сохранённого вида повтору нечего показать.

Использован `update_id` самого обновления, а не `message_id` кнопки: у нескольких
нажатий на одном сообщении (переключение дней недели) `message_id` совпадает, и
второе нажатие сочли бы дубликатом первого.

### Доставка: Gateway опрашивает Backend

Инициатором может быть только Gateway: EU за NAT, входящих подключений к нему
нет. Push от Backend требовал бы публичного порта с TLS либо обратного туннеля —
изменения сетевой схемы и firewall EU-узла.

Очередь — существующая таблица `program_deliveries`, а не новая сущность: у неё с
Phase 1.2-D уже есть аренда и `next_attempt_at`, а второе хранилище пришлось бы
синхронизировать с первым. `claim_for_send` берёт `pending` и созревшие `failed`
одним запросом с `FOR UPDATE SKIP LOCKED` — два экземпляра Gateway не отправят
файл дважды.

Файл в задании не передаётся: он запрашивается отдельным вызовом, живёт в памяти
процесса до отправки и в EU не сохраняется.

Счётчик попыток инкрементируется при приёме отчёта: попытка происходит в EU, и
Backend узнаёт о ней только оттуда. Без этого бюджет попыток не расходовался бы
никогда, и неотправляемая доставка повторялась бы бесконечно.

**Побочный эффект:** worker больше не обращается к `api.telegram.org`. Отправку
выполняет Gateway, поэтому правило `ip rule` для адреса worker'а не нужно — это
снимает ограничение, из-за которого в Phase 1.2-D стоял
`WORKER_DELIVERY_ENABLED=false`.

### Фотографии: байты в RU, запись в MinIO

Backend в RU скачать файл сам не может — Bot API доступен только из EU. Поэтому
Gateway качает файл в память и отдаёт байты Backend, который пишет их в MinIO
(`ObjectStoragePhotoStorage`). Диск EU не участвует.

Вариант «передавать только `file_id`» отвергнут: без доступа к Telegram из RU
файл по нему не получить, и генерация фотографии не увидит.

Новая реализация `FileStorage`, а не переиспользование медиа-репозитория
упражнений: у того своя доменная модель (метаданные в PostgreSQL, конвертация в
WebP, последовательность кадров), и фотографии анкеты в неё не укладываются.
Общее — только object storage, и он уже абстрагирован.

Тело запроса — сами байты, метаданные в query. `multipart/form-data` потребовал
бы новой зависимости (`python-multipart`) ради разбора конверта с одним файлом.
Чтение идёт потоком с проверкой лимита на каждом фрагменте: `Content-Length`
подконтролен клиенту.

### Уведомление администратора — тоже через Gateway

Backend в RU не имеет доступа к Bot API, а отправка сообщения в чужой чат для
Gateway — та же операция, что ответ пользователю. В `TelegramMessage` добавлены
`chat_id` (другой получатель) и `document` (JSON-профиль заявки). Формат тот же,
что был: сводка плюс приложенный JSON.

Отдельной очереди уведомление не требует: у него нет файла программы, а статус
доставки уже хранится в профиле.

### Redis остался, но с TTL и отдельным контейнером

FSM-middleware aiogram читает состояние на каждом обновлении, а изоляция
сериализует параллельные обновления одного пользователя — без Redis два быстрых
сообщения обрабатывались бы одновременно.

TTL обязателен (`GATEWAY_STATE_TTL_SECONDS`, сутки): EU не должен становиться
системой хранения. Потеря этих ключей анкету не теряет — позиция и ответы в RU.

Контейнер отдельный от Redis Backend: обращаться к хранилищам RU шлюз не должен.
Персистентность выключена намеренно.

### Независимые версии

`APP_VERSION` 2.3.0, `GATEWAY_VERSION` 1.0.0, `WORKER_VERSION` 1.0.0.
Совместимость решает `contract_version`, а не совпадение версий или git SHA:
иначе любое обновление Backend требовало бы переразвёртывания EU.

Закреплено `scripts/check_contracts.py` (статический gate) и тестом
`test_deployment_scenarios.py`, который проверяет, что расхождение версий само по
себе не блокирует развёртывание.

Свойства, доказанные на реальной PostgreSQL:

- анкета проходится целиком через HTTP-контракт;
- ответы лежат в `telegram_sessions`, а не в состоянии Gateway;
- повтор `update_id` не продвигает анкету и возвращает тот же вид;
- параллельные обновления одного пользователя не раздваивают сессию;
- повторная финализация (и по тому же `update_id`, и новым нажатием) даёт один
  профиль;
- повторная постановка того же файла в очередь возвращает существующую запись;
- два экземпляра Gateway не забирают одно задание доставки;
- файл не отдаётся по незахваченной доставке (409).

Пять сценариев отказа проверены через настоящий `Dispatcher` с реальными
хендлерами (имитирован только транспорт):

1. Backend недоступен — пользователь получает сообщение, polling продолжается,
   текст не предлагает начать заново (ответы в RU);
2. 4xx от Backend — не роняет обработку;
3. рестарт Gateway (очистка состояния) — диалог продолжается;
4. нажатие кнопки при недоступном Backend — приходит alert, кнопка не зависает;
5. переотправка обновления — тот же ключ идемпотентности, дубликата нет.

### Проверка отсутствия доступа к данным

Проверялось не по коду, а попыткой подключиться изнутри контейнера шлюза:

| Цель | Результат |
| --- | --- |
| PostgreSQL (три набора учётных данных) | `InvalidPasswordError: password authentication failed` |
| MinIO `GET /workout-media/` | `HTTP 403 Forbidden` |
| Redis Backend | TCP отвечает `+PONG` |

Сетевая достижимость (`postgres:5432`, `minio:9000`, `redis:6379` открыты)
сохраняется: все контейнеры находятся в одной docker-сети `workout_net`, потому
что связность Gateway → Backend по HTTP нужна. Доступа к данным при этом нет —
у шлюза нет ни пароля PostgreSQL, ни ключей MinIO.

**Открытый пункт:** Redis Backend отвечает на `PING` без аутентификации, то есть
сетевой доступ к нему у шлюза остаётся. Данных анкеты в этом Redis больше нет
(ключи с ПД удалены, см. ниже), а шлюз работает со своим `gateway-redis`, но
изоляция здесь пока сетевая, а не принудительная. Закрывается либо `requirepass`
на Redis Backend, либо разделением docker-сетей (Backend в двух сетях, шлюз
только во внешней) — то и другое требует правки инфраструктуры S1.

### Наследие: старые FSM-ключи с персональными данными

В Redis Backend оставались два ключа прежнего формата — 4182 байта
сериализованного профиля (имя, возраст, рост, вес, ограничения движений,
рекомендации врача), **без TTL**. Проверено, что анкета из них уже завершена
(`completion_status: confirmed`, `display_number: REQ-20260831-00062`, профиль
`6902efad…` существует в PostgreSQL со статусом `confirmed`), то есть потерять
было нечего. Ключи удалены; `dbsize` = 0.

Автоматической миграции незавершённых анкет не выполнялось и не требовалось:
незавершённых на момент развёртывания не было.

## Ограничения и что не проверено

1. **Сетевая достижимость PostgreSQL и MinIO из шлюза сохраняется.** Все
   контейнеры живут в одной docker-сети `workout_net`, потому что связность
   Gateway → Backend по HTTP нужна. Доступа к данным нет (пароля PostgreSQL и
   ключей MinIO у шлюза не существует, попытки дают `InvalidPasswordError` и
   `403`), но Redis Backend отвечает на `PING` без аутентификации. Это
   единственный оставшийся канал: изоляция здесь сетевая, а не принудительная.
   Закрывается либо `requirepass` на Redis Backend, либо разделением
   docker-сетей — то и другое правит инфраструктуру S1 и требует отдельного шага.

2. **Часть «шлюз скачивает фото из Telegram» проверена не живой отправкой.**
   Bot API не позволяет прислать сообщение от имени пользователя, поэтому байты
   подавались в контракт так же, как их подаёт шлюз (`POST /photo`, тело —
   содержимое файла). Проверено то, что дальше: Backend записал их в MinIO RU,
   на диске EU ничего не появилось, объект читается обратно. Скачивание из
   Telegram выполняет `message.bot.download_file` — единственная непроверенная
   вживую строка этого пути.

3. **Статус уведомления администратора ставится оптимистично.** Фактическую
   отправку выполняет Gateway, а отчёта об этом сообщении контракт не
   предусматривает: седьмая операция ради одного статуса не оправдана. Заявка
   видна в админке и без уведомления.

4. **`count_photos` и `delete_profile_files` не поддерживаются** в
   object-storage-реализации: листинг бакета по префиксу удалил бы файлы, о
   которых профиль не знает. Лимит на число фото проверяется по
   `equipment_photos` профиля — теперь одинаково для любой реализации хранилища.

5. **`ip rule` для адреса worker'а не снят.** Он больше не нужен (worker в
   Telegram не обращается, `api.telegram.org` из его контейнера недоступен), но
   удаление правила требует root на хосте, а `sudo` в неинтерактивном режиме
   недоступен. Правило безвредно: адрес `172.18.0.21` больше не назначается.

6. **Незавершённые анкеты прежнего формата не переносятся автоматически.** На
   момент развёртывания незавершённых не было (единственная живая сессия
   относилась к уже подтверждённой анкете), поэтому переноса не потребовалось.
   Если такая сессия появится при откате назад и вперёд, пользователь увидит
   входной экран, а не молчание.

## Откат

Код: `git revert` коммита, затем rsync и пересоздание сервисов. Схема: миграция
`0013` аддитивна (новая таблица), но код без неё не работает, поэтому порядок —
сначала код, затем при необходимости `alembic downgrade 0012`.

Резервные копии `staging-app.env` сохранены перед каждой правкой
(`staging-app.env.bak.*`, `staging-app.env.pre0013.*`); `staging-gateway.env`
создан заново и при откате просто не используется.

Незавершённые анкеты, начатые после развёртывания, при откате будут потеряны:
старый Gateway ищет их в Redis, где их нет. Завершённые профили не затронуты.
