# Пользователи и доступ

Внутренний интерфейс (`/`) закрыт авторизацией. Публичного самостоятельного
регистрации нет: учётные записи создаёт администратор.

## Два источника учётных записей

| Источник | Где хранится | Роль | Смена пароля |
|---|---|---|---|
| Пользователи БД (`admin_users`) | PostgreSQL, пароль как scrypt-хеш | `admin` или `viewer` | в интерфейсе |
| Аварийный администратор | `ADMIN_LOGIN` / `ADMIN_PASSWORD` в окружении | всегда `admin` | только правкой конфигурации сервера |

Аварийный вход оставлен намеренно: если таблица пользователей пуста или все
пароли утрачены, доступ к системе не теряется. При входе он помечается в
интерфейсе как «аварийный вход». Для повседневной работы им пользоваться не
следует — создайте обычного пользователя.

Порядок проверки при входе: сначала пользователи из БД, затем аварийный
администратор. Причина отказа наружу не детализируется: ответ не должен
подсказывать, существует ли логин.

## Роли

- **admin** — полный доступ: настройки AI, генерация программ, управление
  пользователями;
- **viewer** — только чтение: анкеты, программы, упражнения, состояние AI и
  журналы.

Ограничение viewer'а обеспечивает **сервер**, а не скрытая кнопка: все
изменяющие endpoint'ы зависят от `require_admin` и отвечают 403. Интерфейс
дополнительно скрывает недоступные действия, но это лишь удобство.

Роль попадает в JWT, поэтому после изменения роли пользователю нужно
**войти заново** — старый токен продолжает нести прежнюю роль до истечения
срока (12 часов).

## Пароли

- хеширование — `scrypt` из стандартной библиотеки (n=2^15, r=8, p=1),
  параметры хранятся внутри строки хеша, поэтому их можно усилить без
  инвалидации существующих паролей;
- минимальная длина — 10 символов; пароль не должен начинаться или
  заканчиваться пробелом;
- хеш никогда не возвращается через API: в ответах есть только признак
  `has_password`;
- ни пароли, ни временные пароли не попадают в журнал событий.

### Смена пароля пользователем

Раздел «Сменить пароль» в боковом меню. Требуется текущий пароль; новый
должен отличаться от текущего. В ответ выдаётся новый токен.

### Сброс пароля администратором

Восстановления по email нет — SMTP-инфраструктуры в проекте нет. Вместо этого:

1. администратор нажимает «Сбросить пароль» в разделе «Пользователи»;
2. система выдаёт **временный пароль и показывает его один раз** — значение
   больше не восстанавливается, в базе лежит только хеш;
3. администратор передаёт пароль пользователю;
4. при входе система требует сменить пароль: до смены остальное API закрыто
   (403 с `password_change_required`), работают только `/auth/me` и
   `/auth/change-password`.

Тот же механизм применяется к новым пользователям, если при создании оставить
галочку «требовать смену пароля при входе».

## Защита от потери доступа

Сервер не позволяет привести систему в состояние без администратора:

- нельзя понизить роль последнего активного администратора;
- нельзя отключить последнего активного администратора;
- нельзя удалить последнего активного администратора;
- нельзя удалить собственную учётную запись (даже если админов несколько);
- отключённый администратор не считается доступом.

Во всех случаях API отвечает 409 с объяснением. Аварийный env-администратор в
этих подсчётах не участвует: он не имеет записи в базе.

## Вход через Яндекс, VK, MAX

**Статус: подготовлено на уровне данных, OAuth-флоу не реализованы.**
`GET /api/v1/auth/providers` честно сообщает `available: false` — интерфейс не
предлагает неработающий способ входа.

Что уже сделано, чтобы подключение не потребовало переделки:

- пользователь и способ входа разделены. `admin_users` — человек с ролью,
  `admin_identities` — привязанный аккаунт внешнего провайдера
  (`provider` + `provider_user_id`, уникальная пара);
- один пользователь может иметь пароль и несколько внешних аккаунтов;
- пароль намеренно НЕ является идентичностью: он атрибут пользователя, так как
  проверяется локально. У пользователя только с внешним входом
  `password_hash = NULL`;
- `AdminUserService.authenticate_external(provider, provider_user_id)` уже
  реализован: OAuth-callback должен лишь получить идентификатор аккаунта и
  вызвать этот метод;
- токены провайдеров не хранятся: они нужны только на время флоу.

Что потребуется добавить при подключении конкретного провайдера: сам
OAuth-редирект и callback-роут, секреты приложения в конфигурации и кнопка на
странице входа. Схема БД и проверка прав при этом не меняются.

**Аккаунты не создают пользователей автоматически.** Привязка выполняется
администратором заранее (раздел «Пользователи» → «Внешние входы»). Иначе любой
владелец аккаунта у провайдера получил бы доступ к админке.

## API

| Endpoint | Кто | Назначение |
|---|---|---|
| `POST /api/v1/auth/login` | все | вход, возвращает токен, роль и признак обязательной смены пароля |
| `GET /api/v1/auth/me` | любой вошедший | кто вошёл, роль, права, аварийный ли вход |
| `POST /api/v1/auth/change-password` | любой вошедший | смена своего пароля |
| `GET /api/v1/auth/providers` | любой вошедший | доступные способы входа |
| `GET/POST /api/v1/admin/users` | admin | список и создание |
| `GET/PATCH/DELETE /api/v1/admin/users/{id}` | admin | просмотр, изменение роли/имени/активности, удаление |
| `POST /api/v1/admin/users/{id}/reset-password` | admin | временный пароль |
| `GET/POST /api/v1/admin/users/{id}/identities` | admin | внешние аккаунты |
| `DELETE /api/v1/admin/users/{id}/identities/{identity_id}` | admin | отвязать аккаунт |

Изменения состава пользователей пишутся в общий журнал событий
(`entity_type = admin_user`) без паролей и идентификаторов внешних аккаунтов.

## Осознанные ограничения

- **Нет rate limiting** на попытки входа — перебор пароля ничем не ограничен.
  Это задача Phase 1.3 (operations and security);
- **нет refresh-токенов**: срок жизни токена 12 часов, после чего нужен
  повторный вход;
- **роль в токене не инвалидируется**: понижение роли начинает действовать
  после следующего входа или истечения токена. Для немедленной блокировки
  используйте «Отключить» — проверка активности выполняется при входе;
- **нет восстановления пароля самим пользователем**: только сброс
  администратором (email-инфраструктуры в проекте нет);
- журнал событий физически лежит в таблице `ai_audit_events` — легаси-имя от
  этапа 3B. Это единый журнал административных событий проекта, а не
  AI-специфичный.
