# Текущий статус проекта

**Дата:** 30 августа 2026

## Кратко

Workout Bot — модульный монолит для Telegram: пользователь проходит анкету, система формирует профиль, отбирает упражнения с техническими safety-правилами, генерирует программу через AI или детерминированный генератор, валидирует её, сохраняет версию, собирает HTML с медиа и доставляет файл в Telegram.

## Phase 1.2 — Reliability: DESIGN BASELINE APPROVED

23.08.2026 зафиксирован архитектурный design review в `docs/architecture/PHASE_1_2_RUNTIME_RELIABILITY.md`.

Целевой runtime: Persistent FSM → Finalization → Generation Job → AI/Deterministic → Validation → persisted Program → Delivery Job → Telegram. PostgreSQL остаётся source of truth для бизнес-состояния, Redis используется для устойчивого runtime/transient state.

Ключевые решения:
- generation и delivery — отдельные persistent операции;
- единый `ProgramGenerationOrchestrator` для Telegram и Admin API;
- idempotency boundary для генерации и доставки;
- централизованные retry/recovery правила;
- stale `RUNNING` jobs должны восстанавливаться после restart/crash;
- веб-кнопка Generate Program должна использовать тот же orchestration path;
- Phase 1.2 разбита на 1.2-A…1.2-G: FSM, generation state, orchestrator, worker/retry/recovery, delivery, admin visibility, E2E acceptance.

**Следующий рабочий этап:** Phase 1.2-E — Delivery (отдельное persistent delivery state/job); очередь отправки и приём результата уже введены сетевой границей Gateway.

### Phase 1.2-A — Persistent FSM: ГОТОВО

- состояние анкеты хранится в Redis (`REDIS_URL`) вместо `MemoryStorage`:
  перезапуск процесса бота не сбрасывает анкету, несколько экземпляров
  приложения работают с общим состоянием;
- `src/infrastructure/telegram/fsm_storage.py` — aiogram `RedisStorage` и
  `RedisEventIsolation` с ключами, включающими `bot_id`; изоляция обновлений
  общая для всех процессов, поэтому один ответ не обрабатывается дважды;
- бот не запускается без `REDIS_URL`, доступность проверяется до старта
  polling, соединения закрываются при остановке (повторное закрытие безопасно);
- сбой Redis нормализуется в `FSMStorageError` и превращается в понятное
  сообщение пользователю; ответы анкеты и подключение не попадают в логи;
- PostgreSQL остаётся source of truth: в Redis лежит только черновик анкеты,
  профиль сохраняется при подтверждении, и сбой runtime state не портит
  бизнес-данные;
- Redis добавлен в `docker/docker-compose.yml`, `workout-manager.sh`
  (start/stop/status/doctor/logs/test) и в CI, поэтому FSM-тесты выполняются
  реально, а не пропускаются.

### Phase 1.2-B — Persistent generation state + idempotency: ГОТОВО

- таблица `generation_jobs` (Alembic `0008`) хранит operational-состояние одной
  логической генерации: статус, число попыток, timestamps, код ошибки и ссылку на
  созданную версию программы;
- state machine `PENDING → RUNNING → SUCCEEDED|FAILED`; переход выполняется
  условным `UPDATE ... WHERE status = :expected`, поэтому один job нельзя
  запустить или закрыть дважды, а запрещённый переход отклоняется;
- **одна логическая генерация = (profile_id, бизнес-событие, номер попытки)**:
  одна анкета законно имеет несколько версий программы, поэтому `profile_id`
  как ключ не подходит; автогенерация после подтверждения анкеты и явный запрос
  администратора — разные события;
- идемпотентность обеспечивает PostgreSQL: `UNIQUE(idempotency_key)` +
  `INSERT ... ON CONFLICT DO NOTHING`. Два параллельных запроса одной логической
  генерации создают ровно один job и ровно одну программу; повтор при активной
  генерации получает HTTP 409, повтор после успеха — уже созданную программу;
- `GenerationJob` и `WorkoutProgram` — разные сущности: при отказе программа не
  создаётся, фиктивной записи ради хранения ошибки нет;
- длительный AI-вызов вынесен за границы транзакции: состояние меняется
  короткими транзакциями до и после генерации;
- ошибки разделены на non-retryable (конфигурация, валидация, отсутствующие
  данные) и transient (сеть, таймаут, rate limit, сбой persistence); сам retry
  ещё НЕ реализован;
- в job не попадают промпт, ответ провайдера, ключи и PII: сохраняются только
  стабильный код ошибки и короткое описание, из которого вычищаются секреты;
- `POST /api/v1/profiles/{id}/programs/generate` принимает необязательный
  `idempotency_key` и возвращает блок `generation` (статус, попытки, код ошибки,
  признак повторного использования);
- существующие пути генерации сохранены: AI-генерация, deterministic fallback и
  автозапуск после финализации работают как раньше.

### Phase 1.2-C — Generation Orchestrator: ГОТОВО

- `ProgramGenerationOrchestrator` — единственная application-level точка
  генерации. Telegram (автогенерация после подтверждения анкеты) и Admin API
  (кнопка `Generate Program`) приходят в неё; второго pipeline больше нет;
- `ProgramService.generate`/`build_pools` удалены: сервис отвечает только за
  чтение сохранённых версий программ. До этого этапа Admin API шёл своим
  конвейером — без readiness gate и без fallback;
- вход — `GenerationRequest`, выход — `OrchestratorResult`. Различие вызывающих
  слоёв выражено только запросом:
  - автогенерация: стратегия из `PROGRAM_PRIMARY_GENERATOR`/
    `PROGRAM_FALLBACK_GENERATOR`, `allow_fallback=True` — неработоспособный ИИ
    не ломает пользовательский сценарий;
  - запрос администратора: генератор выбран явно, `allow_fallback=False` —
    подменять выбор молча нельзя, администратор должен увидеть причину;
- fallback выполняется внутри одного job и строго один раз: primary → fallback
  → окончательный отказ. Циклов «AI → fallback → AI» нет, вторая программа и
  второй job не создаются;
- результат самодостаточен: программа, состояние job, запрошенный и фактический
  генератор, признак fallback и его машиночитаемая причина. Внутренние
  исключения AI Gateway наружу не выходят — отказ приходит как
  `GenerationFailedError` со стабильным кодом (`GenerationErrorCode`), и по
  этому коду выбирается HTTP-статус: 409 (уже выполняется), 422 (ошибка данных
  или валидации), 502 (сбой ИИ);
- ответ `POST /api/v1/profiles/{id}/programs/generate` расширен полями
  `requested_generator`, `actual_generator`, `fallback_used`,
  `fallback_reason_code`; существующие поля сохранены. `generation.status`
  зафиксирован как non-nullable: успешный ответ всегда означает завершённую
  генерацию, остальные operational-поля остались nullable;
- клиентский `idempotency_key` — обещание «это тот же запрос». Повторное
  использование с другим генератором возвращает 409: отдать программу прежнего
  генератора значило бы отменить явный выбор администратора, а создать второй job
  под тем же ключом — разрушить идемпотентность. Серверный ключ попытки
  (`profile:trigger:attempt`) под это правило не попадает: его вызывающая сторона
  не выбирала, и повторный finalize по-прежнему получает готовую программу;
- классификация отказов единственная: `classify_error` → `GenerationErrorCode` →
  `AIFallbackReason`. Второй разбор иерархии исключений удалён, поэтому
  operational-запись и журнал администратора не могут описывать одну причину
  по-разному;
- границы транзакций и идемпотентность взяты из 1.2-B без изменений: короткая
  транзакция на создание/переход job, генерация (включая AI-вызов) вне
  транзакции, короткая транзакция на закрытие. Собственного lock оркестратор не
  вводит;
- граница закреплена архитектурным тестом `tests/unit/test_generation_boundary.py`:
  он статически запрещает Telegram gateway и Admin API обращаться к
  генераторам, validator, safety, записи программы и переходам job.

**Осознанное ограничение:** delivery остаётся отдельной операцией и в
оркестратор не входит (Phase 1.2-E). Retry, worker и stale-recovery закрыты в
Phase 1.2-D.

### Phase 1.2-D — Worker / retry / recovery: ГОТОВО

Подробности — `docs/reports/PHASE_1_2_D_WORKER_RETRY_RECOVERY_REPORT.md`.

- **отдельный контейнер-worker** (`apps/worker`, `python -m apps.worker.main`).
  Выбран вместо фоновой задачи внутри Backend и внешнего cron: перезапуск
  админского Backend не должен останавливать обработку повторов, а cron не
  отвечает на вопрос «работает ли обработка сейчас». Worker виден в compose и в
  Component Registry как самостоятельный компонент;
- **состояние процесса нулевое**: очередь повторов (`next_attempt_at`), номер
  попытки (`attempts`) и аренда (`lease_owner`/`lease_expires_at`) живут в
  PostgreSQL (миграция `0012`, аддитивная). Redis не используется вовсе — после
  его потери обработка продолжается;
- **единая политика повторов** `RetryPolicy` (`src/domain/retry.py`) на
  генерацию и доставку: 3 попытки всего, паузы 60 с → 240 с, потолок 900 с,
  аренда 1860 с. Значения из конфигурации, бесконечных повторов нет. Три попытки
  выбраны потому, что внутри одной попытки AI-контур уже перебирает все
  подключённые модели; внешние повторы лечат только недоступность провайдера;
- **повторяются только `transient`-коды** и только автогенерация. `admin_request`
  система сама не повторяет: администратор выбрал генератор и запретил fallback,
  ответ с причиной уже отдан, и молчаливая пересборка отменила бы его решение;
- **переход `FAILED → RUNNING` открыт**; `RETRY_WAIT` не введён — ожидание
  повтора это `FAILED` с заполненным `next_attempt_at`. Возврата в `PENDING` нет:
  повтор всегда выполняет тот, кто захватил job;
- **признак «застрял» — истёкшая аренда**, а не время в статусе: легальная
  AI-генерация занимает до 30 минут, и порог по `started_at` либо отбирал бы job
  у живого исполнителя, либо не отличал бы зависший job от работающего;
- **двойной захват исключён** `SELECT … FOR UPDATE SKIP LOCKED` в той же
  транзакции, что и перевод в `RUNNING`. Проверено на двух независимых engine;
- **идемпотентность**: повтор — это та же логическая генерация,
  `idempotency_key` не пересчитывается, второй job и вторая программа не
  создаются. Повтор доставки генерацию не запускает;
- **границы не обойдены**: повтор генерации идёт через
  `ProgramGenerationOrchestrator.retry`, повтор доставки — через существующий
  `ProgramDeliveryService.redeliver`. Архитектурный тест
  `tests/unit/test_generation_boundary.py` расширен на `apps/worker`;
- worker объявлен в `COMPONENT_REQUIREMENTS` и `deploy/release-manifest.json`,
  поэтому deployment safety gate судит о его совместимости, а не отвечает
  `UNKNOWN`.

**Осознанное ограничение (снято ниже):** `RUNNING` без аренды не восстанавливался,
потому что такой job создавал синхронный путь в другом процессе. После выноса
Gateway за сетевую границу генерацию запускает Backend фоновой задачей, и job
всегда принадлежит процессу, который его создал.

### Сетевая граница Telegram Gateway: ГОТОВО

Подробности — `docs/reports/GATEWAY_NETWORK_BOUNDARY_REPORT.md`.

Gateway стал независимой единицей развёртывания в EU: у него нет ни PostgreSQL,
ни ключей MinIO, ни знания о структуре анкеты. Раньше он импортировал 27 модулей
`src.*`, сам создавал session factory, писал `profiles` и `program_deliveries`, а
через `apps.backend.api.v1.dependencies` — ещё `workout_programs` и
`generation_jobs`. Ответы анкеты (имя, возраст, рост, вес, ограничения движений,
рекомендации врача) лежали в Redis EU **без TTL**, то есть постоянно.

- **контракт `/internal/v1/telegram/*`, шесть операций**: `contract`, `updates`,
  `photo`, `deliveries/claim`, `deliveries/{id}/document`,
  `deliveries/{id}/result`. Аутентификация — `X-Internal-Service-Token`, как у
  Component Registry: у шлюза нет пользователя и роли, и admin-JWT дал бы ему
  доступ ко всему Admin API;
- **server-driven view**: Backend отдаёт готовое описание того, что показать —
  текст, кнопки, тип операции (отправить/заменить), toast. Новый вопрос в анкете
  не требует обновления EU. Альтернатива (отдавать данные, а рендерить в шлюзе)
  вернула бы туда знание о структуре анкеты, то есть и повод для синхронного
  развёртывания;
- **серверная сессия диалога** — таблица `telegram_sessions` (миграция `0013`).
  Отдельная таблица, а не колонки в `profiles`: сессия существует до профиля, и
  брошенная на первом вопросе анкета не должна появляться в `GET /profiles` и в
  аналитике. Черновик пишется с первого ответа — иначе прерванная анкета
  теряется целиком;
- **идемпотентность по `update_id`** Telegram. Хранится и отданный ответ
  (`last_view`): Telegram переотправляет неподтверждённое обновление, а шлюз
  повторяет запрос при таймауте — без ключа один ответ продвинул бы анкету на два
  шага, а без сохранённого вида повтору нечего показать;
- **доставка: шлюз опрашивает Backend**. Инициатором может быть только он: EU за
  NAT, входящих подключений нет. Очередь — существующая таблица
  `program_deliveries`, у которой с 1.2-D уже есть аренда и `next_attempt_at`.
  `claim_for_send` берёт `pending` и созревшие `failed` одним запросом с
  `FOR UPDATE SKIP LOCKED`, поэтому два экземпляра шлюза не отправят файл дважды.
  Побочный эффект: worker больше не обращается к `api.telegram.org`, и правило
  `ip rule` для его адреса не нужно;
- **фотографии оборудования** уходят байтами в RU и пишутся в MinIO
  (`ObjectStoragePhotoStorage`). Диск EU не участвует. Backend скачать файл сам
  не может: Bot API доступен только из EU;
- **уведомление администратора** тоже идёт через шлюз: сводка и JSON-профиль
  передаются как сообщения в другой чат. Отдельной очереди оно не требует — у
  него нет файла программы;
- **Redis остался у шлюза**, но только для служебных нужд aiogram (изоляция
  параллельных обновлений одного пользователя) и **с TTL**
  (`GATEWAY_STATE_TTL_SECONDS`, сутки). Контейнер отдельный от Redis Backend:
  обращаться к хранилищам RU шлюз не должен;
- **независимые версии**: `APP_VERSION` 2.3.0, `GATEWAY_VERSION` 1.0.0,
  `WORKER_VERSION` 1.0.0. Совместимость решает `contract_version`, а не
  совпадение версий — иначе любое обновление Backend требовало бы
  переразвёртывания EU. Закреплено `scripts/check_contracts.py` и job `contracts`
  в CI;
- **фактическая изоляция**: у сервиса `telegram-bot` в compose нет `DATABASE_URL`,
  `MINIO_*`, `JWT_SECRET` и `AI_SECRETS_KEY` — переменные перечислены поимённо, а
  для staging заведён отдельный `staging-gateway.env`. Проверка независимости
  фактическая, а не по коду.

Удалён `ProgramPipelineService`: генерацию запускает Backend, отправку выполняет
шлюз по заданию из очереди, и промежуточный сервис перестал иметь вызывающих.

**Развёрнуто на staging 3 сентября** (`0013 (head)`). Проверено вживую:

- миграция и целостность данных (873 упражнения, 28 анкет, 28 программ — без
  изменений);
- отдельный `staging-gateway.env` из 12 переменных: у контейнера шлюза нет
  `DATABASE_URL`, `MINIO_*`, `POSTGRES_*`, `JWT_SECRET`, `AI_SECRETS_KEY`, тома
  тоже нет;
- изоляция проверена попыткой подключения изнутри шлюза: PostgreSQL —
  `InvalidPasswordError`, MinIO — `403`;
- egress: шлюз `31.58.181.202` (EU-туннель), worker и Backend `91.79.244.18`
  (локальный провайдер);
- E2E с реальным ИИ: анкета 31 вопрос → фото в MinIO → генерация (35.5 с,
  `status=success`) → файл доставлен (`message_id=796`);
- фото физически в MinIO RU (71 байт, подпись PNG, читается обратно), на диске
  EU пусто; файл 21 МБ отклонён с 413 до записи;
- рестарт шлюза посреди анкеты: ответы на месте, диалог продолжился;
- Backend остановлен на 14 с: шлюз выжил, после подъёма опрос возобновился сам;
- worker вернул в очередь застрявшие доставку и job генерации;
- независимый деплой: пересоздание шлюза не перезапустило Backend и наоборот;
- worker больше не нуждается в Telegram: `api.telegram.org` из его контейнера
  недоступен, `aiogram` в его сборочном коде отсутствует.

Из Redis Backend удалены два ключа прежнего формата с персональными данными
(4182 байта профиля без TTL). Анкета из них была уже подтверждена, поэтому
терять было нечего.

**Осознанные ограничения:**

1. Сетевая достижимость PostgreSQL, MinIO и Redis Backend из шлюза сохраняется:
   все контейнеры в одной docker-сети, потому что связность Gateway → Backend
   нужна. Доступа к данным нет, но Redis Backend отвечает на `PING` без
   аутентификации — изоляция здесь сетевая, а не принудительная. Закрывается
   `requirepass` либо разделением docker-сетей (правка инфраструктуры S1).
2. Статус уведомления администратора (`admin_notification_status`) ставится
   оптимистично: фактическую отправку выполняет шлюз, а отчёта об этом сообщении
   контракт не предусматривает. Заводить его значило бы добавить седьмую
   операцию ради одного статуса; заявка видна в админке и без уведомления.
3. `count_photos` и `delete_profile_files` у object-storage-реализации не
   поддерживаются: листинг бакета по префиксу удалил бы файлы, о которых профиль
   не знает. Лимит на число фото проверяется по `equipment_photos`.
4. Скачивание фото из Telegram (`download_file`) вживую не проверено: Bot API не
   позволяет прислать сообщение от имени пользователя. Всё, что после получения
   байтов, проверено на staging.

### AI reliability + prompt management: ГОТОВО

Работа по FINDING-1 из `docs/infrastructure/STAGING_FULL_E2E_ACCEPTANCE_REPORT.md`
(ИИ не собрал программу, сработал детерминированный fallback). Подробности —
`docs/reports/AI_RELIABILITY_AND_PROMPT_MANAGEMENT_REPORT.md`.

- **repair получает достаточный контекст**: исходный system-промпт (правила и
  схема), собственный предыдущий ответ модели, ошибки валидации и полный
  перечень разрешённых `exercise_external_id`; выдуманные идентификаторы
  называются в запросе прямо. Раньше уходило одно `user`-сообщение «исправь эти
  ошибки», вход сжимался с ~6700 до ~120 токенов, и модель деградировала;
- **невалидный вывод переводит генерацию на следующую модель цепочки**: перебор
  ведёт `AIProgramGenerator`, потому что транспортный успех (`200 OK` с
  выдуманным упражнением) не равен пригодному ответу. `AIGateway` получил
  двухшаговый контракт `prepare()` + `generate_once()`; прежний `generate()` с
  внутренним перебором сохранён;
- deterministic fallback остался последним рубежом и решает его по-прежнему
  оркестратор: генератор отказывает только после исчерпания всей AI-цепочки;
- валидатор не ослаблен: выдуманный `external_id` остаётся ошибкой
  `exercise_not_found`;
- **журнал попыток моделей** (`GET /api/v1/admin/ai/model-attempts`, событие
  `ai_model_attempts`): по каждой генерации видно, прошёл ли первый ответ модели,
  сколько было исправлений, почему модель оставлена и дошла ли очередь до
  резервной. Промптов, ответов моделей и PII в журнале нет;
- **управление инструкциями для ИИ** через Admin API и Admin Web: список версий
  с превью, полный текст без усечения, создание, правка, удаление. Вкладка
  `/ai/prompts`;
- **политика удаления промпта**: hard delete, потому что внешних ключей на
  `prompt_templates` нет и история не рвётся. Единственный блокер — инструкция,
  выбранная в настройках задачи: удаление отклоняется 409 со списком блокеров,
  так как ссылка логическая (`prompt_version`) и база её не защищает;
- правка существующей версии разрешена сознательно: нумерация новой версии на
  каждую формулировку превращает список в мусор. `task_type` и `version` при
  правке не меняются — это идентичность промпта;
- миграций нет: схема `prompt_templates` уже содержала всё необходимое.

### Жизненный цикл анкет и программ в админке: ГОТОВО

Раздел анкет накапливался: удаления не было вовсе, а по списку нельзя было
понять, исполнена ли анкета.

- **маркеры исполнения** в списке анкет: «программа собрана» (`has_program`) и
  «отправлена человеку» (`delivered` + дата). Вычисляются подзапросами `EXISTS` к
  фактическим данным, а не хранятся флагами: дублирующее поле рассинхронизировалось
  бы после удаления программы;
- **фильтры** `generated` и `delivered` и **сортировка** `sort` по дате и по обоим
  маркерам. Порядок принимается из белого списка значений, а не как имя колонки:
  подстановка поля в `ORDER BY` — это SQL-инъекция и утечка схемы в контракт;
- **удаление анкеты** (`DELETE /api/v1/profiles/{id}`) и **программы**
  (`DELETE /api/v1/programs/{id}`), admin-only;
- **границы удаления асимметричны по цене ошибки**: анкету с программами удалить
  нельзя (409 со списком блокеров) — её заполнял человек и восстановить её
  невозможно; у программы блокеров нет — она производна и собирается заново.
  Порядок: сначала программы, потом анкета;
- программа удаляется целиком, со всеми версиями и записями доставок: `program_id`
  и есть программа, а версии её история;
- история операций генерации сохраняется: ссылка в `generation_jobs` обнуляется
  (`ON DELETE SET NULL`), запись остаётся;
- контракт удаления с зависимостями вынесен в `src/application/deletion.py` и
  теперь общий для AI-конфигурации, анкет и программ. `AIDependencyError` оставлен
  псевдонимом `DeleteBlockedError`;
- миграций нет: удаление работает по существующей схеме.

**Маркера «скачано пользователем» нет намеренно.** Telegram Bot API не сообщает,
открыл ли человек присланный документ, — такого события не существует.
Достоверно известен только факт отправки, и показывается именно он: догадка в
этом месте вводила бы в заблуждение при решении, можно ли удалять анкету.

### Аналитика качества генерации: ГОТОВО

Журналы отвечали на вопрос «что произошло», но не на «насколько это работает», а
записи телеметрии нельзя было свести к конкретной генерации: событие попыток
моделей и запись вызова писались без ссылки на операцию.

- **корреляция телеметрии с операцией генерации**: `ai_usage_records.job_id`,
  `ai_audit_events.entity_id = generation_jobs.job_id`, версия инструкции в
  событии попыток. Идентификатор передаётся ambient-контекстом
  (`src/application/programs/generation_context.py`), а не аргументом: он нужен на
  трёх разных уровнях, а контракт `ProgramGenerator.generate` общий для AI- и
  алгоритмического генератора;
- `job_id` не внешний ключ: `generation_jobs` уходит каскадом вместе с анкетой, а
  журнал вызовов должен её удаление переживать. Backfill невозможен — связь по
  `profile_id` приписала бы вызовы не тем операциям;
- **единица анализа — операция генерации** (`generation_jobs`), а не программа:
  программа существует только при успехе, и по ней отказов не видно;
- **обращения к ИИ считаются отдельно** от генераций и не сводятся с ними в один
  показатель: одна генерация делает от нуля до нескольких вызовов (перебор
  моделей, repair), поэтому это разные величины;
- **доли равны `null`, а не нулю, при пустой выборке**: 0% означало бы «отказов не
  было», хотя генераций не было вовсе. Выдерживается от SQL до интерфейса;
- **достоверность выборки** (`src/application/ai/analytics_service.py`): выборка
  меньше 10 генераций помечается как ненадёжная, разница версий инструкции меньше
  5 п.п. не объявляется значимой. Автоматического переключения рабочей версии по
  статистике нет: цена ошибки — качество программ у живых пользователей;
- 8 endpoint'ов `GET /api/v1/admin/ai/analytics/*` (сводка, временной ряд, модели,
  версии инструкции, сравнение версий, список генераций, карточка, справочник
  фильтров), доступ `require_viewer`. Промптов и ответов моделей в выдаче нет;
- значения фильтров строятся по истории, а не по текущей конфигурации ИИ:
  удалённая модель остаётся в прошлых генерациях;
- разделы админки `/ai/analytics`, `/ai/generations`, `/ai/generations/{jobId}`;
- миграция 0010: `ai_usage_records.job_id` и индексы под пути доступа аналитики.

**Побочно исправлен дефект длительности генерации.** Время операции округлялось до
секунды, а `created_at` ставила база с полной точностью: у генерации короче
секунды длительность выходила отрицательной. Время хранится с микросекундами,
длительность считается от `started_at`.

### Обозреватель каталога упражнений: ГОТОВО

Из 873 упражнений интерфейс показывал 100: надпись «найдено: 100» означала предел
запроса, а не результат поиска.

- **фильтр по оборудованию не работал вовсе**: списочные поля объявлены типом
  `JSON`, для которого в PostgreSQL не определён оператор вхождения `@>`, и запрос
  падал с `operator does not exist: json ~~ text`. Исправлено приведением к
  `JSONB` в выражении запроса; тип колонки не меняется — на этом размере каталога
  выгоды нет, а таблица была бы перезаписана целиком;
- многозначные фильтры (внутри поля OR, между полями AND), фильтры по мышцам,
  усилию, работе мышц, состоянию и наличию фотографий;
- серверная сортировка по 7 полям; сложность сортируется по смыслу
  (`array_position`), а не по алфавиту — иначе «продвинутый» попадал между
  начальным и средним;
- пагинация с общим числом под фильтром;
- **счётчики значений считаются по текущей выборке**: счётчик, не зависящий от
  фильтров, обещал бы результаты, которых после уточнения нет;
- поиск экранирует `%` и `_`: без этого запрос «100%» возвращал весь каталог;
- обратная совместимость сохранена: вызов, используемый генерацией, остался
  рабочим; миграций не потребовалось.

### Frontend-тесты: ВВЕДЕНЫ

В проекте не было ни одного теста админки. Добавлены проверки форматирования
значений и сборки query-строк на встроенном test runner Node (`node --test` с
поддержкой TypeScript) — без установки тестового фреймворка. Покрыты два случая,
в которых интерфейс легко начинает врать молча: `null` вместо 0 и фильтр
`false`, отбрасываемый как «не задан». CI дополнен шагом `npm test`.

### Component Registry и совместимость компонентов: ГОТОВО

Backend, Admin Web и Telegram Gateway разворачиваются независимо (шлюз — в
EU-сегменте), но Backend не знал, какая версия шлюза фактически работает:
единственным источником была память того, кто деплоил. Обновление Backend
выполнялось без проверки — сломает оно шлюз или нет, выяснялось после деплоя.

- **совместимость определяется контрактом, а не версиями**: равенство версий или
  git SHA между компонентами не требуется нигде. Backend `2.2.0` и шлюз `1.8.2`
  совместимы, если шлюз поддерживает нужную версию контракта;
- Backend объявляет **множество** поддерживаемых контрактов, а не одно значение —
  это и есть модель EXPAND → MIGRATE → CONTRACT без отдельного migration
  framework: пока в множестве две версии, компоненты миграруют по одному;
- `component_instances` (миграция `0011`) хранит **только metadata**: содержимое
  строки целиком отдаётся Admin API, поэтому credentials там появиться не могут;
- уникален `component_id`, а не `component_type`: `telegram-eu-1` и
  `telegram-eu-2` сосуществуют, и этот же индекс делает heartbeat идемпотентным —
  компонент не помнит, регистрировался ли он раньше;
- **heartbeat не является условием работы бота**: недоступный Backend
  логируется, анкеты продолжают обслуживаться. Иначе мониторинг стал бы точкой
  отказа бизнес-функции;
- `/internal/v1` защищён отдельным service-токеном, а не admin JWT: у шлюза нет
  пользователя и роли, а admin JWT дал бы процессу доступ ко всему Admin API;
- **два разных состояния несовместимости**: `UPDATE_REQUIRED` — обновлять нужно
  компонент, `INCOMPATIBLE` — обновлять нужно Backend. Одно значение на оба
  случая направило бы администратора не туда. `UNKNOWN` не сводится к
  «совместим»: проверка не выполнялась;
- deployment safety gate отдаёт `SAFE`/`BLOCKED` машиночитаемо; офлайн-экземпляр
  деплой не блокирует — остановленный контейнер невозможно сломать обновлением;
- connector-контракт описан через capability, а не через тип компонента: MAX
  Gateway добавит capability, а не ветвление в вызывающем коде;
- `deploy/release-manifest.json` сверяется тестом с контрактами в коде, иначе
  манифест начал бы врать deployment tooling;
- раздел «Инфраструктура» в админке показывает готовый вердикт сервера; правила
  совместимости на фронтенде не дублируются.

EU routing, WireGuard/wstunnel и бизнес-логика шлюза не менялись. Отчёт —
`docs/infrastructure/COMPONENT_CONNECTOR_ARCHITECTURE_REPORT.md`.

## Открытые проблемы и риски

### P0 — до реального production
1. Production hardening: централизованные логи, error tracking/metrics,
   backup/restore, rate limits и эксплуатационные процедуры. Устойчивое FSM
   storage закрыто в Phase 1.2-A; backup/restore Redis не требуется — там
   только незавершённые анкеты.
2. **Нет rate limiting на вход в админку** — перебор пароля остаётся задачей Phase 1.3.
3. End-to-end verification на чистом окружении: миграции, импорт каталога/медиа, AI primary, deterministic fallback, delivery failure/retry.
4. Проверка безопасности production-конфигурации и секретов.
5. Часть интеграционных тестов требует каталога упражнений; CI засеивает его автоматически.
6. `alembic check` сообщает о косметическом расхождении ORM-моделей и миграций (`unique=True` против UniqueConstraint); это существовало до текущего этапа.
7. Job, оставшийся в `RUNNING` **без аренды**, никто не восстанавливает: такие job создаёт синхронный путь (Telegram-пайплайн, Admin API) в другом процессе, и worker не может отличить «процесс умер» от «запрос ещё выполняется». Job'ы, захваченные worker'ом, восстанавливаются по просроченной аренде (Phase 1.2-D). Ограничение снимается вместе с переносом генерации в worker.
8. `GenerateProgramRequest.prompt_version` не используется: поле принимается API, но никуда не передаётся. Версия инструкции берётся из настроек задачи (`ai_task_configs.prompt_version`), и этого достаточно для промпт-инжиниринга: администратор выбирает версию в задаче и запускает генерацию. Поле осталось со времён до Phase 1.2-C; удаление меняет публичный контракт, поэтому вынесено отдельно.
9. **Telegram Gateway всё ещё импортирует backend-код и работает с той же PostgreSQL напрямую.** Component Registry дал версионирование и контроль совместимости, но не сетевую границу: целевая topology (`DEPLOYMENT_AND_INTEGRATION_BASELINE.md`, раздел 4) требует, чтобы шлюз обращался к Backend только через API. Это остаётся deployment blocker для реального разделения RU/EU.
10. Deployment safety gate реализован и доступен по `/internal/v1/deployment-safety`, но **в CI ещё не подключён**: пока это ручная проверка перед деплоем backend.
