**Миграции:** `0017` (staging, provenance, наблюдения), `0018` (оборудование внешних источников)

Ограничение не в числе упражнений, а в единственности источника: пополнение

иметь, потому что работает с единственным доверенным источником.

## 2. Что дали источники

### 2.1 Источник A: каталог упражнений

`hasaneyldrm/exercises-dataset` — 1324 записи, каждая с инструкциями на 10 языках
(включая русский), фотографией 180×180 и анимацией выполнения.

| Показатель | Значение |
| --- | --- |
| записей | 1324 |
| с английской техникой | 1324 |
| с русской техникой | 1324 |
| с фотографией и анимацией | 1324 (2648 файлов) |
| уникальных ключей сопоставления | 1280 |
| оборудование приведено к словарю | 1254 |
| целевая мышца приведена к словарю | 1183 |

Данные распространяются по MIT. Медиа принадлежит Gym visual
(https://gymvisual.com/) и включено в репозиторий источника с разрешения
правообладателя; атрибуция сохраняется в метаданных каждого ассета
(`exercise_media.license`).

44 записи из 1324 различаются только пометкой съёмки — `(male)`, `(female)`,
`(back pov)`, `v. 2`. Это не разные упражнения, а один и тот же материал, снятый
с другой моделью или ракурса.

### 2.2 Источник B: датасет программ

Kaggle `600k-fitness-exercise-and-workout-program-dataset` — 605 033 строки, две
CSV-таблицы: сводка программ и их детализация по неделям и дням.

| Показатель | Значение |
| --- | --- |
| строк детализации | 605 033 |
| программ | 2 598 |
| уникальных названий упражнений | 3 211 |
| строк, где повторения означают удержание в секундах | 25 967 |
| техник, описаний, медиа | 0 |

Название источника обещает 600 тысяч упражнений. Фактически это 605 тысяч
**вхождений упражнений в программы**: 3 211 уникальных названий, каждое из
которых встречается в среднем 188 раз. Трактовать строки как упражнения нельзя —
это дало бы 605 тысяч дублей вместо 3 тысяч кандидатов.

Каталогом упражнений этот датасет не является: техники, описания и медиа в нём
отсутствуют, а из полей упражнения есть только название. Зато он содержит то,
чего нет ни в одном каталоге, — **программный контекст**: сколько программ
включают упражнение, с какими подходами, повторениями и интенсивностью, для каких
целей и уровней подготовки.

Отрицательные повторения (25 967 строк) — не ошибка данных: так источник
обозначает удержание в секундах. Складывать их с повторениями значило бы считать
среднее по двум разным величинам.

## 3. Архитектура: canonical сущность остаётся одна

Второго каталога упражнений нет. Canonical сущность — `exercises`, ключ — пара
`(external_id, source)`, и внешняя запись попадает в неё только через merge.
Генерация программ читает `exercises` и базу знаний об оборудовании; ни один
модуль ingestion не является её runtime-зависимостью.

Знание разложено на пять таблиц (миграция `0017`), каждая отвечает на свой
вопрос.

```
external_sources ──version──▶ external_source_versions
       │                        (commit SHA / хеш архива)
       │
       └──record──▶ external_exercise_records        (staging + решение)
                          │
                          ├──▶ exercises             (canonical, единственный)
                          │        ▲
                          │        │
                          ├── exercise_source_links  (origin | enrichment |
                          │                           duplicate_variant |
                          │                           observation)
                          │
                          ├── exercise_field_provenance   (откуда каждое поле)
                          │
                          └── exercise_program_observations
                                     (typical_* / source_* — наблюдение, не
                                      предписание)
```

| Таблица | На какой вопрос отвечает |
| --- | --- |
| `external_sources` | что за источник, чьи данные и медиа, на каких условиях |
| `external_source_versions` | из какого состояния источника взяты записи |
| `external_exercise_records` | что мы прочитали и что решили по каждой записи |
| `exercise_source_links` | из каких источников собрано это упражнение |
| `exercise_field_provenance` | откуда взято конкретное поле упражнения |
| `exercise_program_observations` | как упражнение используют в чужих программах |

Почему staging — таблицы, а не файл отчёта. Импорт обязан быть идемпотентным:
повторный запуск не должен ни создавать упражнения заново, ни терять прежние
решения. Для этого нужно состояние, переживающее процесс, и уникальный ключ
`(source_key, source_record_id)`, по которому повторная загрузка попадает в ту же
строку.

Почему `exercise_field_provenance` отдельно от `exercise_source_links`. Это
разные вопросы. Связь отвечает «какие источники участвуют в упражнении»,
provenance — «откуда именно это значение». У одного упражнения русская техника
может прийти из источника A, название остаться canonical, а медиа — из третьего
места; хранить это одной записью значило бы потерять различие.

FK на `exercises` нет — по той же причине, что в `exercise_media` и
`exercise_equipment_requirements`: составной внешний ключ привязал бы знание к
жизненному циклу строки каталога, а пересоздание каталога — штатная операция
импорта. Целостность измеряется счётчиками отчёта, где она видна администратору
(`/api/v1/admin/ingestion/health`).

## 4. Дедупликация: три исхода, а не два

Сопоставление обязано различать три случая, а не два: то же упражнение, другой
вариант того же движения, другое упражнение. Без среднего исхода дедупликация
либо теряет упражнения (объявляя вариант дублем), либо плодит их (объявляя
вариант новым).

Признаки названия разложены на три независимых набора
(`src/application/ingestion/normalization.py`):

1. **ядро движения** (`core_tokens`) — что за движение, без различителей и без
   названий мышц. `Dumbbell Biceps Curl` и `Dumbbell Curl` дают одно ядро: мышца
   записана полем, и повторять её в названии нечем;
2. **содержательные различители** (`semantic_variant_tokens`) — хват, стойка,
   угол, односторонность, амплитуда, облегчение, дополнительный вес. Их
   расхождение означает другое упражнение;
3. **снаряд** — сравнивается не по слову в названии, а по canonical ID словаря
   оборудования.

### 4.1 Тождество — предикат, не порог

Запись считается тем же упражнением, когда совпало ядро, совпали содержательные
различители и не противоречат оборудование и целевая мышца. Порог был бы неверным
инструментом: он позволил бы объявить тождеством запись, у которой различитель
разошёлся, но «набралось достаточно баллов» на совпадении мышц.

Уверенность (`confidence`) считается всегда и служит двум задачам: выбрать лучшего
кандидата среди нескольких и показать администратору, насколько близка запись,
которую система решением не объединила. Веса:

| Признак | Вклад |
| --- | --- |
| содержательные различители совпали | 0.40 |
| оборудование совпало (известно обеим сторонам) | 0.30 |
| оборудование неизвестно обеим сторонам | 0.25 |
| оборудование известно одной стороне | 0.15 |
| оборудование различается | 0 |
| целевая мышца совпала | до 0.22 |
| целевая мышца найдена среди дополнительных | 0.11 |
| целевая мышца известна одной стороне | 0.10 |
| дополнительные мышцы совпали | до 0.05 |
| `force` + `mechanic` совпали | 0.03 |

`MATCH_CONFIDENCE_FLOOR = 0.55` — тождество, набравшее меньше, не применяется
автоматически: совпадение, опирающееся только на неизвестность с обеих сторон,
должен подтвердить человек.

### 4.2 Проверенные случаи

Требование этапа названо дословно, и оба набора проверены тестами
(`tests/unit/test_ingestion_matching.py`):

```
Barbell Bench Press                    ─┐
Bench Press - Barbell                  ─┴─▶ одно упражнение
Barbell Bench Press - Medium Grip      ───▶ отдельное упражнение

Dumbbell Biceps Curl                   ─┐
DB Biceps Curl                         ─┼─▶ одно упражнение
Dumbbell Curl                          ─┘
```

Первые два совпадают: ключ сопоставления снимает порядок слов, ядро и различители
одинаковы. Третий отличается токеном `grip` — различие тренировочное, а не
орфографическое.

Во втором наборе `DB` раскрывается в `dumbbell`, `biceps` — название мышцы и в
ядро не входит. Все три дают ядро `curl`, снаряд `dumbbell` и пустой набор
различителей.

### 4.3 Что выяснилось на реальных данных

Пять решений приняты не из общих соображений, а после того как dry-run показал
ложное поведение. Каждое зафиксировано тестом.

**Пометки съёмки не различают упражнения.** `barbell full squat (male)` и
`barbell full squat` — один и тот же присед. Пометки (`(male)`, `(female)`,
`(back pov)`, `v. 2`) убираются из ключа сопоставления, но сохраняются в
`raw_name`: администратор должен видеть, откуда взялась запись.

**Слово-снаряд в названии не является различителем.** `Bench Press - With Bands`
и `Band Bench Press` объявляют полем одну и ту же резину. Различие слова — не
различие упражнения, поэтому снаряд сравнивается по canonical ID.

**Оборудование, названное в дополнение к объявленному, различителем является.**
`Cable Incline Fly (on stability ball)` объявляет полем только блок, а фитбол
существует лишь в названии — это второе оборудование, и упражнение оно различает.
Отличить один случай от другого можно только через отношение «частное — родовое»
словаря: `Smith Machine Bench Press` объявляет родовое `machine`, а названием —
`smith machine`, и это тот же снаряд, названный точнее.

**Источники расходятся в выборе главной мышцы.** Для приседа внешний каталог
называет целевой `glutes`, действующий — `quadriceps`; при этом `glutes` у
действующего в дополнительных, а `quadriceps` у внешнего — тоже. Набор
задействованных мышц один, различается только выбор главной. Поэтому «мышцы не
противоречат» означает: целевая мышца одной стороны есть среди задействованных
мышц другой. Полное совпадение даёт полный вес, совпадение через дополнительные —
половину.

**Совпадение только по ядру требует подтверждения фактом.** У `roller back
stretch` и `back pec stretch` ядро одинаково (`back`, `stretch`), различителей нет
ни у одной. Без требования подтверждения оборудованием или мышцей растяжка на
валике объявлялась бы растяжкой груди у стены. Неизвестность подтверждением не
является.

### 4.4 AI в сопоставлении не участвует

Это не осторожность, а требование воспроизводимости: результат импорта обязан
совпадать при повторном запуске на тех же данных, а вызов модели этого не
гарантирует. Веса и пороги — константы модуля, задокументированные выше.

## 5. Качество: отказ, а не низкий балл

Оценка (`src/application/ingestion/quality.py`) отвечает на конкретный вопрос:
можно ли добавить запись в canonical каталог без участия человека. Поэтому итог —
не только число, но и статус с перечислением причин: число без причин нельзя ни
проверить, ни исправить.

| Признак | Вклад |
| --- | --- |
| техника выполнения | 0.30 (обязательна) |
| русская техника | 0.20 |
| оборудование приведено к словарю | 0.18 |
| целевая мышца приведена к словарю | 0.14 |
| дополнительные мышцы | 0.06 |
| медиа | 0.08 |
| описание | 0.04 |

Пороги: `READY ≥ 0.70`, `REJECT < 0.40`, между ними — `REVIEW`.

**Отсутствие техники даёт `REJECT` независимо от остальных полей.** Это выражено
условием, а не весом. Иначе запись с полным набором мышц и медиа, но без техники,
набрала бы 0.70 и попала бы в каталог — то есть в программу пользователя попало бы
упражнение без объяснения, как его выполнять.

`QUESTIONABLE` — отдельное решение, а не низкое качество. Ставится, когда данные
внутренне противоречивы: mojibake в названии (`sled 45в° leg press`), техника
короче двух шагов, слишком короткое название. Такая запись может быть верной, но
проверять её должен человек.

## 6. Оборудование: словарь пополнен, второго не создано

Значения источника A отличаются от значений действующего каталога: `body weight`
против `body only`, `leverage machine` против `machine`. Словарь при этом не
создан заново — он пополнен, как и предусмотрено прошлым этапом (миграция `0018`).

Добавлено 3 единицы оборудования: `bosu_ball`, `upper_body_ergometer`,
`ski_ergometer`. Ни одна не выражается существующей записью: bosu-платформа
отличается от фитбола характером опоры, ручной и лыжный эргометры — типом
движения. Добавлено 17 синонимов для существующего оборудования.

Итог: словарь вырос с 74 до 77 записей, синонимов — с 172 до 197.

### 6.1 Что сознательно не сопоставлено

Пять значений источника синонимов не получили — по той же причине, по которой их
не получил `other` в прошлом этапе: это не названия оборудования.

| Значение | Записей | Почему не сопоставлено |
| --- | --- | --- |
| `weighted` | 36 | «с дополнительным весом» — пояс, диск или гантель |
| `assisted` | 15 | «с облегчением» — гравитрон либо резина |
| `rope` | 10 | канат для раскачивания, канат для лазания, скакалка, рукоять блока |
| `roller` | 8 | и валик для миофасциального релиза, и ролик для пресса |
| `hammer` | 1 | и кувалда, и хват «молот» (в каталоге есть `Hammer Curls` с гантелями) |

Выбрать «наиболее вероятный» вариант значило бы записать догадку как факт. Такие
значения видны в отчёте ingestion и закрываются человеком.

`sled machine` сопоставлен с `resistance_machine`, а не с `leg_press`, хотя все 15
упражнений источника с этим значением — вариации жима ногами и гакк-приседа.
Причина в семантике родового: требование `resistance_machine` закрывается любой
его специализацией, включая `leg_press` и `hack_squat`, а обратное неверно.
Назначить `leg_press` означало бы объявить упражнение невыполнимым в зале, где
есть гакк-машина, но нет жима ногами.

### 6.2 Поле `exercises.equipment` и словарь фильтра

Поле `exercises.equipment` — вход действующего детерминированного фильтра, и его
словарь задан кодом (`CATALOG_EQUIPMENT`, 12 значений). Записать туда формулировки
источника нельзя: фильтр не узнал бы ни `body weight`, ни `leverage machine`, и
все импортированные упражнения были бы исключены с причиной «нет оборудования» —
то есть импорт оказался бы бессмысленным для генерации.

Поэтому оборудование проходит два шага: формулировка → canonical ID (это делают
данные, `equipment_aliases`) → значение словаря поля (это делает таблица в
`src/application/ingestion/equipment_tags.py`). Второй шаг — код, а не данные,
сознательно: словарь поля задан кодом фильтра, и держать отображение в базе значило
бы разнести два конца одного соответствия. Таблица исчезнет вместе с полем, когда
фильтр начнёт читать нормализованные требования напрямую.

Потеря точности здесь есть и названа: `smith_machine`, `leg_press` и `treadmill`
дают одно значение `machine`, потому что более точного в словаре поля нет. Точное
знание не теряется — оно восстанавливается из того же canonical ID при построении
требований, а исходная формулировка источника сохраняется в staging и provenance.

## 7. Мышцы: четыре отношения вместо «нашлось / не нашлось»

Canonical словарь мышц задан действующим каталогом — 17 значений. Он не
расширяется: добавление мышцы меняет поведение генератора, который группирует
упражнения по мышцам, и делать это внутри импорта данных нельзя.

| Отношение | Что означает | Что делает система |
| --- | --- | --- |
| `EXACT` | то же понятие другими словами (`abs` → `abdominals`) | подставляет как факт |
| `BROADER` | часть canonical группы (`obliques` → `abdominals`) | подставляет, помечает выведенным |
| `AMBIGUOUS` | несколько кандидатов (`upper back` → `middle back` \| `traps`) | не подставляет, отдаёт в review |
| `UNMAPPED` | эквивалента нет (`serratus anterior`) | сохраняет как пробел словаря |

Соблазн свести всё к `EXACT` был: тогда мышцы заполнились бы у всех 1324 записей.
Но `upper back → middle back` — утверждение об анатомии, которого источник не
делал, и предъявлять его как факт нельзя.

Что осталось незакрытым по факту dry-run:

| Неоднозначное значение | Записей | Кандидаты |
| --- | --- | --- |
| `upper back` | 125 | `middle back`, `traps` |

## 8. Merge: ни одно поле не перезаписывается слепо

Политика по полям (`src/application/ingestion/merge_policy.py`):

| Поле | Правило |
| --- | --- |
| `external_id`, `source` | не меняются никогда |
| `name` | canonical сохраняется; внешнее название идёт в `aliases` |
| `technique` | берётся, если у canonical нет либо внешняя содержит больше шагов |
| `technique_ru` | то же правило |
| `description` | заполняется только пустое |
| `primary_muscles` | дополняются только там, где canonical их не знает |
| `secondary_muscles` | то же правило |
| `equipment` | не переписывается; знание идёт в `exercise_equipment_requirements` |
| media | добавляется, если её нет; существующая не удаляется |
| provenance | записывается всегда |

Равный по объёму текст техники не заменяется: «другой формулировкой» не значит
«лучше». Мышцы непустого списка не дополняются внешними значениями — генератор
относит упражнение к роли по основным мышцам, и добавленная мышца изменила бы роль
на основании значения, выведенного словарём.

Слепой overwrite не делается ни для одного поля не из осторожности: canonical
каталог билингвален и вычитан, а внешний источник содержит и mojibake, и
машинно-переведённые инструкции. Заменять проверенное непроверенным на основании
того, что оно новее, значило бы ухудшать базу, называя это обогащением.

## 9. Идемпотентность и сходимость

Импорт обязан сходиться за один прогон, а не «стабилизироваться со временем».
Проверено тремя последовательными применениями одного и того же источника.

| Прогон | Создано | Обогащено | provenance | Каталог после |
| --- | --- | --- | --- | --- |
| 1 | 953 | 319 | 5324 | 1826 |
| 2 | 0 | 0 | 0 | 1826 |
| 3 | 0 | 0 | 0 | 1826 |

Сходимость обеспечивают четыре механизма, а не осторожность.

**Связь источника как факт.** `exercise_source_links`, записанная предыдущим
прогоном, читается сопоставлением как самый сильный признак: упражнение,
импортированное из этой записи, будет найдено независимо от того, изменились ли
правила. Это делает повторный импорт идемпотентным по определению, а не по
совпадению правил.

**Роли `origin` и `duplicate_variant` не понижаются.** Обе описывают исторический
факт, которого повторный прогон уже не видит. На втором прогоне запись
опознаётся как существующая, и роль стала бы `enrichment`; после этого ответ на
вопрос «сколько упражнений пришло из источника» терялся бы, хотя ничего не
менялось.

**План перепроверяется против фактического состояния.** План строится от снимка
каталога, а применяется последовательно, и одно упражнение обогащают несколько
записей. Без повторной проверки порядок применения решал бы результат: запись с
двумя шагами техники, применённая после записи с пятью, затирала бы более полную
версию — и следующий прогон снова «улучшал» бы её.

**Дубли внутри источника обогащают сразу.** 21 запись — повтор другой записи того
же источника. Они не создают упражнение, но их данные не всегда беднее: у второй
записи бывает полнее техника и другое название. Если не взять их сразу, они будут
взяты на втором прогоне.

Отдельно обработан случай удаления упражнения администратором: связи, ведущие на
несуществующую строку каталога, отбрасываются при построении плана и показываются
счётчиком `orphan_source_links`. Иначе такая связь молча запрещала бы повторный
импорт — запись опознавалась бы как существующая, а упражнения в каталоге не было
бы.

## 12. Программное знание Kaggle: наблюдение, не предписание

305 упражнений каталога получили запись в `exercise_program_observations`. Каждая
содержит: сколько программ включают упражнение, сколько всего вхождений, медиану и
диапазон подходов, медиану и диапазон повторений, медиану удержания в секундах,
медиану интенсивности, распределения по целям, уровням и контексту оборудования.

Все поля названы `typical_*` и `source_*` не для красоты: это статистика чужих
программ, а не назначение нашей. Превращать «в источнике встречается 4×10» в
«назначить 4×10» нельзя — нагрузку определяет методология проекта, и запись этой
таблицы на неё не влияет. Ни один модуль генерации эту таблицу не читает.

Удержание отделено от повторений: в источнике отрицательное значение повторений
обозначает секунды, и усреднять их вместе значило бы считать среднее по двум
разным величинам.

Разные названия датасета, сопоставленные с одним упражнением (`Bench Press
(Barbell)` и `Barbell Bench Press`), объединяются по исходным наблюдениям, а не по
медианам: медиана от медиан не является медианой.

## 13. Admin API и интерфейс

Только чтение. Запуск ingestion остаётся операцией обслуживания
(`scripts/ingest_external_exercises.py`), потому что требует локальной копии
источника, которой у backend нет и быть не должно.

| Метод и путь | Что отдаёт |
| --- | --- |
| `GET /api/v1/admin/ingestion/sources` | источники с версией, условиями и счётчиками решений |
| `GET /api/v1/admin/ingestion/records` | страница внешних записей с решением, качеством, уверенностью |
| `GET /api/v1/admin/ingestion/records/{source_key}/{record_id}` | одна запись целиком, включая payload источника |
| `GET /api/v1/admin/ingestion/exercises/{external_id}/provenance` | происхождение полей, связи источников, наблюдения |
| `GET /api/v1/admin/ingestion/health` | счётчики, которыми проверяется результат импорта |

Все требуют роль наблюдателя. `payload` в списке не отдаётся: он содержит полные
инструкции источника на нескольких языках, и возвращать их страницей означало бы
мегабайты на каждый запрос. Отдельная запись отдаётся целиком — там это оправдано.

Фильтры серверные: по источнику, решению, качеству, статусу импорта, диапазону
уверенности и подстроке названия. Значения фильтров проверяются перечислениями, а
не подставляются в запрос: `?decision=whatever` даёт 422, а не тихий полный список.

Интерфейс — раздел «Внешние источники» с тремя вкладками:

- **Источники** — что за источник, версия, условия на данные и на медиа отдельно,
  разбивка решений;
- **Записи** — таблица с решением, качеством, уверенностью и причинами; серверные
  фильтры и пагинация; отклонённые записи не скрыты;
- **Полнота** — счётчики импорта и связей со справочником, с переходом к записям,
  ждущим проверки.

В карточке упражнения добавлен раздел «Откуда данные»: связи источников с ролью и
уверенностью, таблица полей с указанием источника и причины, программные
наблюдения. Пустой раздел означает, что упражнение пришло из исходного справочника
проекта, — это сказано прямо, а не показано пустотой.

Медиа в карточке теперь различает фотографию и анимацию: контракт получил поле
`media_type`, потому что статичный кадр показывает положение, а анимация —
движение, и выдавать GIF за фотографию нельзя. Лицензии перечисляются все: медиа
одного упражнения приходит из разных источников.

В интерфейсе нет английских кодов: каждое решение, статус, качество и причина
имеют русскую подпись (`apps/web/lib/labels.ts`), и это проверяется тестом.

## 14. Отвергнутые решения

**Второй каталог упражнений.** Отвергнут: две сущности «упражнение» означают два
ответа на вопрос «что можно выполнять», и генерация читала бы одну, а админка —
другую. Canonical остаётся `exercises`.

**AI для сопоставления и оценки.** Отвергнут: результат импорта обязан совпадать
при повторном запуске на тех же данных. Вызов модели этого не гарантирует, и
воспроизвести решение по 1324 записям стало бы невозможно.

**605 тысяч строк Kaggle как упражнения.** Отвергнуто по факту данных: это 3211
уникальных названий и 605 тысяч вхождений в программы. Трактовка строк как
упражнений дала бы 605 тысяч дублей.

**Отбрасывание значимых токенов ради роста числа совпадений.** Соблазн был: без
`medium grip` жим средним хватом совпал бы с обычным жимом, и число «уже
существующих» выросло бы. Но средний хват — отдельное упражнение каталога у любого
источника, и объявлять его дублем значит терять данные, называя потерю
дедупликацией.

**Сведение всех обозначений мышц к `EXACT`.** Отвергнуто: `upper back → middle
back` — утверждение об анатомии, которого источник не делал. 125 записей остались
без основной мышцы, и это честный результат.

**Порог вместо предиката для тождества.** Отвергнут: порог позволил бы объявить
тождеством запись с разошедшимся различителем, набравшую баллы на совпадении
мышц. Тождество решается предикатом, уверенность считается отдельно.

**Слепая перезапись полей более новыми данными.** Отвергнута: canonical каталог
вычитан и билингвален, внешний источник содержит mojibake и машинный перевод.

**Запуск ingestion из Admin API.** Отвергнут: чтение источника требует локальной
копии на 350 МБ, а backend к внешним источникам не обращается.

### 15.1 Найденный и устранённый дефект сортировки

Первая проверка генерации показала, что ни одно импортированное упражнение не
попадает в программу при трёх занятиях в зале. Причина не в фильтре: внешний
источник пишет названия строчными (`barbell bench press`), действующий каталог — с
заглавных (`Barbell Bench Press`), а детерминированный генератор сортирует
упражнения по названию. В Python строчные буквы идут после всех заглавных, поэтому
все 953 записи оказывались в конце каждой группы ролей — а пул урезается по
длительности занятия.

Причина устранена с двух сторон:

- сортировка сделана регистронезависимой в генераторе
  (`src/application/programs/generator.py`), в фильтре и в репозитории упражнений
  (`ORDER BY lower(...)` для текстовых полей);
- названия приведены к регистру каталога при импорте (`display_name`), потому что
  каталог показывается человеку и два стиля в одном списке читаются как дефект.

Регистронезависимая сортировка нужна и сама по себе: без неё порядок в Explorer был
порядком по источнику, а не по алфавиту.

После исправления первое импортированное упражнение появляется в группе `push` на
позиции 172 из 585 (зал) и на позиции 21 из 66 (дом, вес тела) — то есть в
достижимой части пула.

### 15.2 Почему импортированные упражнения ранжируются ниже

Генератор ставит выше `compound`-упражнения. Внешний источник поля `mechanic` не
сообщает, поэтому все 953 записи попадают в группу «не compound» и идут после
canonical compound-упражнений: 489 записей действующего каталога имеют
`mechanic = compound`.

Это не дефект импорта, а следствие отсутствия данных, и восполнять его выдумкой
нельзя: `mechanic` — классификация упражнения, а не производная от названия. То же
относится к `difficulty`: уровня подготовки источник не сообщает, поле оставлено
пустым, и фильтр трактует неизвестную сложность как допустимую — импортированные
упражнения доступны любому уровню, пока уровень не установлен человеком.

Практическое следствие: у профилей с большим пулом (зал) состав программы почти не
изменился, у профилей с малым пулом (дом) импортированные упражнения появляются в
программе. Это ожидаемое поведение при неполных данных, а не ошибка.

Дедупликация — оба направления ошибки, поскольку они несимметричны по
последствиям: ложное объединение молча уничтожает упражнение, ложное разделение
даёт дубль.

- порядок слов, сокращения (`DB` → `dumbbell`), транслитерация русских названий,
  синонимы, пометки съёмки;
- хват как различитель, различие ядра движения, расхождение оборудования,
  расхождение целевой мышцы при совпадении ядра, дополнительное оборудование в
  названии;
- связь предыдущего импорта как сильнейший признак, детерминированность повторного
  вызова, приоритет тождества над оценкой.

Качество — отказ при отсутствии техники независимо от остальных полей, обрезанная
техника как `questionable`, незакрытое оборудование против отсутствующего,
неоднозначные мышцы не подставляются.

Merge — заполнение пустого поля, замена более полным, отказ от замены равного,
сохранение мышц caталога, добавление синонима без дублирования.

Идемпотентность — второй прогон не создаёт упражнений, третий не меняет ничего,
роли `origin` и `duplicate_variant` не понижаются, обновление источника не
добавляет вторую запись.

Источники — агрегация 605 тысяч строк в 3211 названий, отрицательные повторения как
удержание, версия по содержимому и по commit SHA, явная ошибка при изменении
формата CSV.

Медиа — оба типа, идемпотентность по контрольной сумме, потеря файла, dry-run без
записи, детерминированный ключ хранения.

API — авторизация на всех маршрутах, серверные фильтры, серверная пагинация,
отклонённые записи в выдаче, отсутствие payload в списке, 422 на неизвестное
значение фильтра, пустое происхождение как ответ, а не ошибка.

## 17. Что осталось незакрытым

Перечислено как незакрытое, а не спрятано: каждый пункт виден в отчёте ingestion
или на странице полноты.

1. **`mechanic` и `difficulty` у 953 импортированных упражнений не заполнены.**
   Источник их не сообщает. Следствие: такие упражнения ранжируются ниже
   canonical compound-упражнений и доступны любому уровню подготовки. Заполнение
   требует классификации, а не вычисления, и вынесено отдельно.
2. **114 упражнений без основных мышц** — из-за неоднозначных (`upper back`,
   `core`, `hip flexors`) и незакрытых (`serratus anterior`, `feet`) обозначений.
   Закрывается решением человека о том, какой canonical мышце соответствует
   `upper back`, — это анатомическое решение, а не техническое.
3. **70 записей с оборудованием без canonical ID** (`weighted`, `assisted`,
   `rope`, `roller`, `hammer`). Значения родовые, и однозначного соответствия у них
   нет.
4. **178 значений `other` в `unmapped_equipment_values`** после пересчёта: 122
   были до этапа, 56 добавили импортированные упражнения. Означает «оборудование
   нужно, какое — источник не уточняет».
5. **5 записей `questionable` и 2 `unknown` ждут решения человека.** Интерфейса
   для принятия такого решения нет: этап даёт видимость, а не редактирование
   staging. Записи остаются в статусе `pending`, и повторный прогон их не меняет.
6. **2806 названий датасета программ не сопоставлены с каталогом.** Наблюдения по
   ним не создаются. Это мера покрытия, а не дефект.
7. **Русские названия импортированных упражнений отсутствуют** (`name_ru` пустое):
   источник даёт русскую технику, но не русское название. Программа показывает
   английское название с русской техникой.
8. **Запуск ingestion — операция обслуживания.** Ни расписания, ни кнопки в
   админке нет: требуется локальная копия источника (350 МБ для источника A,
   90 МБ для источника B).
9. **Отображение canonical ID в словарь поля `exercises.equipment` живёт в коде**
   (`equipment_tags.py`). Оно исчезнет, когда фильтр начнёт читать нормализованные
   требования напрямую, — это следующий шаг Gym Knowledge Base, а не этого этапа.

## 18. Обратная совместимость и откат

Существующие данные не изменены разрушительно. Миграция `0017` только создаёт
объекты: ни одна строка не изменяется и не удаляется. Миграция `0018` добавляет
оборудование и синонимы через `ON CONFLICT DO NOTHING` и при откате удаляет только
собственные вставки, и только если на них никто не ссылается.

Поле `exercises.equipment` сохранено: оно остаётся входом действующего фильтра и
повторного построения требований.

Откат данных импорта:

```sql
-- 1. Убрать созданные упражнения и их медиа
DELETE FROM exercise_media  WHERE exercise_source = 'workout_bot/external';
DELETE FROM exercises       WHERE source = 'workout_bot/external';

-- 2. Убрать знание об источниках
DELETE FROM exercise_program_observations;
DELETE FROM exercise_field_provenance;
DELETE FROM exercise_source_links;
DELETE FROM external_exercise_records;
DELETE FROM external_source_versions;
DELETE FROM external_sources;

-- 3. Пересчитать знание об оборудовании
-- python -m scripts.build_equipment_knowledge
```

Обогащённые поля caталога (техника у 12 упражнений, синонимы у 225) откатом не
восстанавливаются: они записаны в те же колонки, что и данные источника
`leszavr/workout`. Восстановление — повторный `import_exercises`, который
перезапишет записи каталога из его собственного источника; provenance показывает,
какие поля были изменены импортом.

Откат схемы: `alembic downgrade 0016`. Обе миграции имеют `downgrade`, цикл
`downgrade base` → `upgrade head` проверен.
