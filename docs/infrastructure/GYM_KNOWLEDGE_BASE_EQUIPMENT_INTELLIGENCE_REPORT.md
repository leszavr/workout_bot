# Gym Knowledge Base & Equipment Intelligence

**Дата:** 5 сентября 2026
**Ветка:** `feature/gym-knowledge-equipment-intelligence`
**Миграции:** `0014` (схема), `0015` (словарь), `0016` (импорт значений каталога)
**Проверено на staging** `192.168.1.3`.

## 1. Что было

Знание об оборудовании существовало в единственном виде — JSON-массив строк в
`exercises.equipment` со значениями источника каталога. Замер по рабочей базе до
изменений (873 упражнения):

| Значение источника | Упражнений |
| --- | --- |
| `body only` | 175 |
| `barbell` | 170 |
| `dumbbell` | 123 |
| `other` | 122 |
| `cable` | 81 |
| `machine` | 67 |
| `kettlebells` | 53 |
| `bands` | 24 |
| `medicine ball` | 17 |
| `exercise ball` | 12 |
| `foam roll` | 11 |
| `e-z curl bar` | 9 |
| пустой список | 77 |

Из такого представления нельзя ответить ни на один практический вопрос.

- `machine` не различает жим ногами и блочную тягу: 67 упражнений названы одним
  словом, и «у меня есть жим ногами» не сопоставимо ни с чем.
- `other` у 122 упражнений не означает ничего. При этом трактовать его как
  «оборудование не нужно» неверно: упражнение стало бы выполнимым где угодно.
- Пустой список у 77 упражнений одинаково читается как «оборудование не нужно» и
  как «неизвестно». Среди них есть и `Pushups`, и `Scapular_Pull-Up`, которому
  турник обязателен.
- Словарь синонимов жил в Python (`EQUIPMENT_ALIASES` в
  `src/application/programs/filtering.py`). Добавление тренажёра требовало правки
  кода и деплоя.
- Ни возможностей оборудования, ни различия «обязательно / желательно / одно из»,
  ни альтернативных упражнений не существовало.

## 2. Модель знаний

Знание разложено на четыре независимых уровня, каждый отвечает на свой вопрос.

```
Exercise ──requirement──▶ Equipment ──capability──▶ Capability
    │      REQUIRED                    │
    │      OPTIONAL                    └──specializes──▶ Equipment (родовое)
    │      ALTERNATIVE (группы)
    │
    └──alternative──▶ Exercise  (EXACT | SIMILAR | PARTIAL)

Profile ──item──▶ Equipment  (available | unavailable | unknown)
    │
    ▼
EquipmentCompatibilityService  ──▶  compatible | incompatible | unknown + причина
```

| Таблица | Отвечает на вопрос | Записей на staging |
| --- | --- | --- |
| `equipment_capabilities` | что объект умеет | 26 |
| `equipment_items` | что это за объект | 74 |
| `equipment_item_capabilities` | какое оборудование что умеет | 116 |
| `equipment_aliases` | как это называют | 172 |
| `exercise_equipment_requirements` | что нужно упражнению | 803 |
| `unmapped_equipment_values` | что не удалось сопоставить | 122 |
| `exercise_alternatives` | чем заменить | 4067 |
| `equipment_profiles` / `_items` | что фактически есть | по запросу |

### Почему возможности отдельной сущностью

Два тренажёра разных производителей называются по-разному, но функционально
совпадают. Упражнению нужна возможность («наклонная опора», «регулируемое
сопротивление»), а не бренд. Возможность — цель ссылок сразу из двух мест: из
оборудования и из требования упражнения, поэтому JSONB-список не подходит: он не
даёт ни ссылочной целостности, ни ответа «какие возможности вообще существуют».

### Почему строковые первичные ключи

На оборудование ссылаются данные, миграции, отчёты и админка. Ссылка
`cable_machine` читается, `17` — нет. Surrogate-ключ пришлось бы разыменовывать в
каждом отчёте и в каждой миграции.

### Почему специализация оборудования

`leg_press` → `resistance_machine`, `treadmill` → `cardio_machine`,
`lat_pulldown` → `cable_machine`. Всего 18 связей.

Отношение необходимо, потому что источник каталога говорит родовыми словами: у 67
упражнений оборудование указано как `machine`. Без связи человек, перечисливший
жим ногами, получал бы «не подходит» на упражнение «жим ногами» — система
противоречила бы сама себе.

Отношение направлено в одну сторону: частное закрывает требование родового,
обратное неверно. Упражнению, которому нужен именно жим ногами, абстрактный
«силовой тренажёр» не подходит — у человека может быть блочная тяга. Транзитивно
(`treadmill` закрывает требование `cardio_machine` через цепочку), цикл в данных
отклоняется сервисным слоем.

Взаимозаменяемость скамей через это отношение НЕ выражается: регулируемая скамья
не является частным случаем горизонтальной, и их отношение уже описано
возможностями. Два механизма для одного вопроса дали бы два разных ответа.

## 3. UNKNOWN ≠ INCOMPATIBLE

Главное свойство модели. Отсутствие знания о требованиях упражнения и отсутствие
ответа пользователя про тренажёр не являются доказательством несовместимости.
Превращать пробел в отказ значит вычёркивать упражнения по причине, которой никто
не устанавливал.

Различение проведено на всех уровнях:

| Уровень | Значения | Что означает третье значение |
| --- | --- | --- |
| наличие в профиле | `available` / `unavailable` / `unknown` | пользователь не отвечал про этот тренажёр |
| доверие к факту | `confirmed` / `inferred` / `unknown` | требование выведено правилом и требует проверки |
| результат проверки | `compatible` / `incompatible` / `unknown` | вывод сделать нельзя |

`assume_unlisted_unavailable` в профиле отвечает на вопрос, что означает
отсутствие позиции. Для домашнего профиля, где человек перечислил всё, что у него
есть, — «нет». Для зала, о котором известно только название, — «неизвестно»:
придумывать отсутствие тренажёра детерминированному слою запрещено.

Порядок решений: подтверждённое отсутствие сильнее неизвестности. Иначе
упражнение с недостающей штангой и неуказанной скамьёй выглядело бы «возможно
выполнимым».

Проверено на staging тремя случаями одного и того же набора упражнений:

```
# зал описан полностью (assume_unlisted_unavailable=true)
Barbell_Bench_Press_-_Medium_Grip  compatible    all_required_available
Leg_Press                          compatible    specialized_equipment_available
Smith_Machine_Squat                compatible    specialized_equipment_available
Cable_Crossover                    compatible    all_required_available
Atlas_Stones                       incompatible  required_equipment_missing  missing=[atlas_stone]

# домашний профиль: только гантели и коврик
Barbell_Bench_Press_-_Medium_Grip  incompatible  required_equipment_missing
Dumbbell_Bench_Press               compatible    all_required_available
Pushups                            compatible    no_equipment_needed

# про зал не сказано ничего
Barbell_Bench_Press_-_Medium_Grip  unknown       availability_unknown
Leg_Press                          unknown       availability_unknown

# требования упражнения не заполнены, набор оборудования полный
Anterior_Tibialis-SMR              unknown       requirements_unknown
Backward_Drag                      unknown       requirements_unknown
Bicycling                          unknown       requirements_unknown
```

Последний случай — ключевой: полный перечень оборудования не превращает
отсутствие требований в «подходит».

## 4. Отвергнутые решения

### Подмена оборудования по покрытию возможностей

Проверялось правило «доступное оборудование закрывает требование, если покрывает
его возможности». Отвергнуто: `dumbbell` покрывает `free_weight` штанги, и жим
штанги лёжа оказывался выполнимым с гантелями. Система выдавала бы другое
упражнение за то же самое.

### Подмена по совпадению категории и набора возможностей

Более строгий вариант того же правила. Отвергнут, потому что его результат
зависит от того, насколько подробно заполнен словарь: добавление возможности
одному тренажёру меняло бы совместимость другого. Совместимость должна зависеть
от фактов о зале, а не от полноты справочника.

### Что вместо этого

Взаимозаменяемость выражается в данных явно и остаётся проверяемой:

- требованием возможности — «нужна фиксированная траектория и регулируемое
  сопротивление» закрывает любой подходящий тренажёр, включая модель другого
  производителя;
- группой ALTERNATIVE — «`chest_press_machine` или `resistance_machine`»;
- специализацией — для родовых значений источника каталога.

Все три варианта редактируются в админке и видны администратору.

### EXACT по категории оборудования

Первая версия вывода альтернатив считала полной заменой упражнения с оборудованием
одной категории. Отвергнуто: `barbell` и `dumbbell` обе относятся к
`free_weight`, и жим гантелей объявлялся полной заменой жима штанги. Требуется
равенство набора оборудования. Результат изменения: EXACT 2726 → 2159, SIMILAR
962 → 1529.

## 5. Импорт существующих данных

Старое поле `exercises.equipment` **не удалено и не изменено**. Оно остаётся входом
для повторного сопоставления: после пополнения словаря импорт пересчитывается, и
результат воспроизводим. Удаление старого формата вместе с введением нового
означало бы одновременную смену формата и потребителя, и откат стал бы невозможен.

Разделение на миграцию и скрипт:

| Что | Где | Почему |
| --- | --- | --- |
| схема | миграция `0014` | схема и данные откатываются независимо |
| словарь и синонимы | миграция `0015` | без словаря compatibility engine не работает вовсе: это предпосылка работоспособности кода, а не прикладные данные |
| сопоставление значений каталога | миграция `0016`, SQL, только полное совпадение | значения каталога — контролируемый набор из 12 строк, угадывать нечего |
| вывод по названию упражнения и альтернативы | `scripts/build_equipment_knowledge.py` | результат зависит от текущего словаря и пересчитывается при его пополнении |

Итог импорта на staging:

| Категория | Упражнений | Источник |
| --- | --- | --- |
| подтверждённые требования | 674 | значение каталога → ровно один canonical ID |

Незакрытые значения: 122 записи, все — `other`, причина `ambiguous`
(«источник не уточняет оборудование»). Они сохранены в
`unmapped_equipment_values`, а не отброшены: иначе упражнение осталось бы без
требований и считалось бы выполнимым где угодно.

Вывод по названию не применяется к силовым категориям, если оборудование не
указано: пропущенная штанга или турник в силовом упражнении опаснее пробела в
данных. Поэтому `Scapular_Pull-Up`, `Inverted_Row`, `Decline_Push-Up` и
`Prone_Manual_Hamstring` остались UNKNOWN, а не получили выдуманный «собственный
вес».

Распределение выведенных требований (129 строк): `bodyweight` 65,
`weight_sled` 9, `weight_plate` 7, `suspension_trainer` 5, `resistance_band` 4,
`wall` 4, далее по 2–3.

Идемпотентность проверена: повторный `alembic upgrade head` ничего не дублирует
(вставки через `ON CONFLICT DO NOTHING`), повторный запуск скрипта даёт те же
числа. Прежний результат правила снимается по источнику (`name_inference`,
`derived`) до пересчёта; требования, заведённые администратором (`source=admin`),
и импортированные из каталога не затрагиваются.

## 6. Альтернативные упражнения

Простое «A заменяет B» недостаточно: пользователю нужно знать, насколько замена
равноценна. Тип замены хранится, а не вычисляется на чтении.

| Тип | Условие | Связей |
| --- | --- | --- |
| EXACT | те же основные мышцы, тот же паттерн (`force` + `mechanic`), тот же набор оборудования, тот же характер стабилизации | 2159 |
| SIMILAR | те же мышцы и паттерн, но другое оборудование или другая стабилизация | 1529 |
| PARTIAL | совпадают основные мышцы, но паттерн или механика отличаются | 379 |

Всего 4067 связей для 860 упражнений, не более 5 на упражнение.

Признаки, участвующие в сравнении, — только те, что фактически есть в каталоге:
основные и дополнительные мышцы, `force`, `mechanic`, `difficulty`,
`exercise_type`, набор требуемого оборудования и характер стабилизации
(возможности `unstable_support` / `fixed_path` / `free_weight`).

Ограничение зафиксировано, а не скрыто: **EXACT означает «неотличимо по признакам,
которые есть в каталоге», а не «физически идентично»**. Угол наклона, диапазон
движения, положение тела и unilateral/bilateral в каталоге отдельными полями не
представлены, поэтому `Barbell_Bench_Press` и `Barbell_Incline_Bench_Press`
получают EXACT. Выводить эти признаки из названий значило бы строить догадку и
предъявлять её как факт.

Равенство основных мышц требуется, а не пересечение: упражнение на грудь и трицепс
не заменяет упражнение только на грудь. Если требования одного из упражнений
неизвестны, EXACT не назначается никогда — иначе пробел в данных превратился бы в
утверждение о полной эквивалентности.

## 7. Admin API и интерфейс

Префикс `/api/v1/admin/knowledge`. Чтение — `require_viewer`, изменение —
`require_admin`: словарь определяет, какие упражнения система считает выполнимыми,
и правка его наблюдателем меняла бы результат подбора.

| Метод | Путь | Назначение |
| --- | --- | --- |
| GET | `/equipment` | страница словаря с фильтрами и числом связанных упражнений |
| GET | `/equipment/categories` | категории со счётчиками |
| GET | `/capabilities` | список возможностей |
| GET | `/equipment/{id}` | запись словаря |
| POST | `/equipment` | создание |
| PATCH | `/equipment/{id}` | изменение |
| POST | `/equipment/{id}/deactivate` | вывод из обращения без разрыва ссылок |
| DELETE | `/equipment/{id}` | удаление (только при отсутствии ссылок) |
| GET/PUT | `/exercises/{external_id}/requirements` | требования упражнения целиком |
| GET | `/exercises/{external_id}/alternatives` | альтернативы |
| GET/PUT/DELETE | `/profiles[/{key}]` | профили доступного оборудования |
| POST | `/compatibility` | проверка «упражнения × оборудование» |
| GET | `/health` | полнота и целостность базы знаний |
| GET | `/unmapped` | незакрытые значения источника |

Решения контракта:

- **удаление и деактивация — разные операции.** Удалить можно только запись, на
  которую никто не ссылается (иначе 409 с числом ссылок). Всё остальное выводится
  деактивацией: требования упражнений, ссылающиеся на запись, остаются
  историческим фактом. Проверка серверная, интерфейс её не дублирует;
- **требования заменяются набором, а не по одной строке.** Набор требований —
  единое утверждение об упражнении, и «добавить строку» без удаления
  противоречащей дало бы невыполнимую комбинацию;
- **невыполнимые комбинации отклоняются на записи** (422), а не обнаруживаются
  потом метрикой: упражнение не может одновременно требовать снаряд и его
  отсутствие;
- **ответ проверки объясним**: не только статус, но и причина, недостающее,
  закрытое, неустановленное и разбор каждого требования. Без этого администратор
  не может ни проверить решение, ни исправить данные;
- строки БД наружу не возвращаются: surrogate `id`, метки времени и внутренние
  источники записи клиенту не нужны и не входят в публичный контракт.

Интерфейс — раздел «База знаний» (`/knowledge`, `/knowledge/health`,
`/knowledge/unmapped`) и расширенный каталог упражнений.

Exercise Explorer стал equipment-aware при сохранении серверной фильтрации:
фильтры по canonical ID словаря, по возможностям, по характеру требования и по
состоянию знания сводятся к набору идентификаторов и попадают в тот же
SQL-запрос. Отсеивать строки после выборки страницы нельзя — «первые 50»
перестали бы быть первыми пятьюдесятью подходящими.

Два исключения из этого правила названы в интерфейсе прямо:

- статус совместимости считается только для показанной страницы (считать его для
  всего каталога ради 50 строк незачем), поэтому фильтр по статусу возвращает
  `filtered_page_count` и подпись объясняет, к чему относится общее число;
- пустой набор идентификаторов отличается от отсутствия фильтра: фильтр без
  совпадений даёт ноль строк, а не весь каталог.

Столбцы «оборудование в справочнике» и «требования» показаны отдельно и не
дублируют друг друга: первое — значение источника, второе — нормализованное знание
системы. Расхождение видно сразу, и это нужно: пока требования не заполнены,
подбор по оборудованию для упражнения не работает.

Названия оборудования и возможностей приходят из базы (`name_ru`) — словаря
подписей в коде фронтенда нет. Словарь пополняется через админку, и дублировать
его в коде значило бы гарантированно с ним разойтись. В коде остались только
подписи закрытых наборов: статусов, причин, типов замены и уровней доверия.

Три последние метрики — проверки целостности, нарушение которых делает результат
подбора неверным, а не просто неполным. Orphan-ссылка возможна потому, что
составного FK к каталогу нет намеренно: ссылка на упражнение — каноническая пара
(`external_id`, `source`), как в `exercise_media`, а пересоздание каталога —
штатная операция импорта. Целостность измеряется и видна администратору вместо
падения импорта.

36 неиспользуемых записей словаря — не дефект: словарь описывает мир, а не только
текущий каталог. Метрика существует, чтобы забытая запись была видна.

## 9. Роль AI

AI в вычислении совместимости не участвует ни на одном шаге. Результат зависит
только от данных базы знаний и воспроизводим: тесты движка работают без
PostgreSQL.

AI не создаёт идентификаторы оборудования и возможностей: любая ссылка обязана
существовать в базе, иначе запись отклоняется (422). Модель данных допускает путь
«фотография → кандидат → подтверждение человеком»: позиция профиля хранит
`source=photo`, `confidence=inferred` и `source_ref` со ссылкой на объект
хранилища, и подтверждение человеком меняет `confidence` на `confirmed`. Сам
распознаватель в объём этапа не входит — это отдельная работа, и заявлять
computer vision реализованным было бы неверно.

## 11. Что осталось незакрытым

1. **Pipeline генерации не подключён к базе знаний.** Фильтр
   (`src/application/programs/filtering.py`) по-прежнему работает на значениях
   каталога и словаре `EQUIPMENT_ALIASES` в коде. Переключение меняет состав пула
   упражнений у всех существующих пользователей, поэтому выделено в отдельный шаг
   с собственной приёмкой, а не сделано вместе с введением модели.
2. **Ответы анкеты не нормализованы в `equipment_profiles`.** Сопоставление
   свободного текста реализовано и проверено на реальных данных, но автоматической
   записи профиля при финализации анкеты нет: это меняет поведение
   пользовательского сценария.
3. **72 упражнения без требований и 122 значения `other`.** Закрываются вручную
   через админку либо расширением правил вывода. Пробел видим и измерим, а не
   спрятан за ложным «оборудование не нужно».
4. **Распознавание оборудования по фотографии не реализовано.** Модель данных
   путь поддерживает, распознаватель — отдельная работа.
5. **Признаки, отсутствующие в каталоге**, в оценку альтернатив не входят: угол
   наклона, диапазон движения, положение тела, unilateral/bilateral. Поэтому EXACT
   означает «неотличимо по имеющимся признакам».
6. **Знание об экземплярах зала не наполнено.** Схема профилей и
   `extra_capabilities` готовы, конкретные залы не описаны.

## 12. Обратная совместимость и откат

- `exercises.equipment` не изменялся: существующий фильтр и генерация работают как
  раньше.
- Ответ `GET /api/v1/exercises` расширен полем `compatibility`, которое равно
  `null`, когда доступное оборудование не передано. Существующие поля сохранены.
- Откат данных: `alembic downgrade 0013` удаляет только объекты базы знаний;
  каталог, профили и программы не затрагиваются (проверено на staging).
- Откат словаря: `downgrade 0015` не удаляет оборудование, на которое ссылаются
  требования или профили, — правки администратора важнее полноты откатa.
- Откат кода: revert коммита ветки, rsync, пересборка образов. База знаний при
  этом остаётся в БД и никем не читается.
