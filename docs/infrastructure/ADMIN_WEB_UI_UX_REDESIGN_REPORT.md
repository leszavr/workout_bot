# Admin Web UI/UX Redesign Report

**Проект:** Workout Bot / «Форма»  
**Ветка:** `feature/admin-web-voxlibrix-style`  
**Задача:** `.tmp/Admin_UI/Admin_Web_UI_UX.md`  
**Дата проверки:** 8 сентября 2026

## 1. Состояние до изменений

Административные страницы собирали каркас интерфейса самостоятельно: навигация,
проверка токена и шапка повторялись между страницами. Списки имели разную
разметку, а фильтры и состояния загрузки не были единым паттерном. Dashboard
показывал продуктовые счётчики, но не давал быстрого ответа о готовности ИИ,
состоянии компонентов и безопасности развёртывания.

## 2. UX-ориентиры

Из VoxLibris взяты не код и не визуальная копия, а рабочие паттерны:

- постоянная навигация слева и рабочая область справа;
- компактная информационная плотность;
- единые таблицы, фильтры и действия CRUD;
- вложенные экраны как вкладки раздела, а не разрастающееся меню;
- системное состояние выше вторичных продуктовых метрик;
- раскрытие редко используемых фильтров вместо вытеснения списка за нижнюю
  границу экрана.

## 3. Новая архитектура Admin UI

Все административные маршруты перенесены в route group `app/(admin)` и
обёрнуты единым `AdminShell`.

- `AdminShell` централизует проверку токена, состояние sidebar и mobile drawer.
- `Sidebar` строится из `lib/nav.ts`; пункты разделены на «Обзор», «Данные
  продукта», «База знаний» и «Система».
- `Header` содержит путь до раздела, текущего пользователя и действия сессии.
- `PageHeader` задаёт единый заголовок, описание, вкладки и действия страницы.

Разделение продуктовых данных и инфраструктуры сохранено как в навигации, так
и в dashboard: отсутствие программы у пользователя не смешивается с проблемой
готовности ИИ или совместимости компонентов.

## 4. Общие UI-компоненты

Введены и применены повторно:

- `DataTable`: колонки, сортировка, pagination, loading/error/empty states;
- `FilterBar`, `SearchInput`, `FilterGroup`, `FacetFilter`;
- `PageTabs` и `LocalTabs`;
- `Card`, `Field`, `Status`, `Tag`, `Notice`, `KeyValue`, `Skeleton`,
  `ErrorState`, `Empty`;
- `ConfirmDialog` для необратимых действий;
- `Metric` и `Pagination`.

Некоторые небольшие примитивы намеренно сгруппированы в одном файле, а не
разнесены по одиночным модулям: это сохраняет единый паттерн без искусственного
усложнения структуры.

## 5. Изменённые страницы

- **Сводка:** проблемы компонентов, readiness, deployment safety, результаты
  генераций за семь дней и продуктовые показатели; независимые запросы не
  скрывают доступные блоки при отказе одного источника.
- **Анкеты, программы, пользователи, инфраструктура:** единые page headers,
  таблицы, карточки и состояния списков.
- **ИИ:** единые вкладки раздела, страницы провайдеров, задач, логов,
  аналитики, операций генерации и инструкций.
- **Внешние источники и база знаний:** вкладки вместо дополнительных пунктов
  sidebar, общие таблицы и фильтры.

## 6. Exercise Explorer

Каталог упражнений стал рабочим инструментом, а не первой страницей выборки:

- серверные поиск, сортировка, pagination и facets;
- фильтры по данным каталога, оборудованию, возможностям, мышцам, сложности,
  типу нагрузки, медиа, состоянию и знанию об оборудовании;
- дополнительный набор фильтров раскрывается только по необходимости;
- значения `compatible`, `incompatible` и `unknown` остаются разными;
- detail screen разделён на локальные вкладки: характеристики, требования,
  замены, технику, медиа и provenance;
- требования показываются отдельно как обязательные, желательные и группы
  «одно из вариантов».

Пустые требования явно означают неизвестность знания, а не отсутствие
оборудования.

## 7. Equipment Knowledge Base

Интерфейс использует существующую модель `Exercise → requirement → Equipment →
Capability`, не создавая отдельную UI-модель. Раздел оборудования, health и
unmapped values вынесены в «Базу знаний». В фильтрах и detail-экране явно
показаны capability, тип требования, совместимость и источник знания.

## 8. Prompt Management

Управление инструкциями ИИ приведено к общему CRUD-паттерну:

- таблица версий с текущей версией, статусом, размером и датой;
- просмотр полного текста без усечения;
- создание чистой версии и копии существующей;
- редактирование и контролируемое удаление через подтверждение;
- создание версии не переключает задачу автоматически.

Существующая модель версионирования и backend API не изменялись.

## 9. Responsive и доступность

Desktop остаётся основной компоновкой. Sidebar можно свернуть с сохранением
выбора в `localStorage`; на узком экране он становится выдвижной панелью со
scrim. Заголовки и действия переносятся, таблицы остаются в scrollable
container, а фильтры переходят в одну колонку. Для reduced motion отключён
переход sidebar.

Для доступности добавлены видимые состояния фокуса, `aria-sort` в таблице,
семантические `fieldset`, нативные `details`, `role="alert"` для ошибок и
клавиатурное закрытие confirm dialog по Escape.

## 10. Границы этапа

Сознательно не менялись:

- Telegram Gateway, WireGuard, wstunnel, EU/RU network boundary и nftables;
- Docker topology, PostgreSQL, Redis и MinIO architecture;
- схема Exercise Knowledge Base;
- AI generation pipeline и административные backend API.

Новый frontend использует существующие endpoint'ы и модели.

## 11. Проверки

Локально выполнены после исправления типизации frontend-тестов:

```text
npm run lint
npx tsc --noEmit
npm test
npm run build:check
```

`npm test` включает проверки форматирования, query-параметров, навигации и
группировки требований оборудования. Полный runtime smoke-test и staging
deployment не выполнялись в рамках локальной проверки: они требуют запущенный
backend и согласованный доступ к staging.

## 12. Производительность

Новые UI-компоненты не добавляют внешних библиотек. Поиск, фильтрация,
сортировка и pagination каталога выполняются сервером. Dashboard делает
несколько независимых запросов только при открытии и по явной кнопке
«Обновить», без постоянного polling.

## 13. Рекомендации следующего этапа

1. Выполнить staging smoke-test ключевых маршрутов под ролями administrator и
   viewer.
2. Добавить browser/component-тесты для sidebar, фильтров, таблиц, prompt CRUD
   и Exercise Explorer, если в проект будет введён соответствующий test runner.
3. При расширении диалогов добавить общий focus trap и уникальные ID заголовков.
4. Создать PR в `main` после просмотра итогового diff; PR не мержить до
   отдельной приёмки.
