# AI subsystem

## Назначение

AI Gateway отделяет бизнес-логику от конкретного провайдера и модели. Программа использует AI только как один из генераторов; результат всё равно проходит parser и validator.

## Цепочка

`AIProvider → AIEndpoint → AIModel → AITaskConfig → model bindings → ModelSelector → Adapter → AIProgramGenerator`

Реально используемая задача: `workout_generation`. Остальные типы задач — enum-задел, код их не вызывает; в UI они помечены как «не вызывается кодом».

## Поддержанный рабочий путь

Фактически реализован только OpenAI-compatible adapter (`build_default_registry`). Протоколы `anthropic` и `custom` адаптера не имеют: в UI они помечены и недоступны для выбора, а включить задачу на таком протоколе сервер не даёт.

Единственный источник истины о поддержке — реестр адаптеров: `AIReadinessService` спрашивает `ProviderAdapterRegistry.protocols()`, а не хардкод в интерфейсе.

## Как получить рабочую AI-генерацию

Быстрый путь (`/ai` → «Быстрое подключение AI»): название сервиса, базовый URL и API-ключ. Список моделей запрашивается у самого сервиса (`POST /api/v1/admin/ai/probe-models`), модель выбирается из списка — вводить идентификатор руками не нужно. Мастер создаёт провайдера, эндпоинт с ключом и модель, выполняет проверку подключения и включает задачу **только если проверка прошла**.

Экспертный путь (те же admin-endpoint'ы по шагам):

1. Создать провайдера с поддерживаемым протоколом.
2. Создать и включить endpoint.
3. Сохранить API key.
4. Получить список моделей сервиса (`GET /api/v1/admin/ai/endpoints/{id}/available-models`) и добавить выбранные (`POST .../models/bulk`). Уже добавленные модели помечаются `already_added`, повторный выбор попадает в `skipped`, а не в ошибку.
5. Выполнить connection test.
6. Для `workout_generation` выбрать модель, включить задачу и сохранить порядок fallback моделей.
7. Убедиться, что `PROGRAM_PRIMARY_GENERATOR=ai`.
8. Выполнить тестовую генерацию и проверить `GenerationInfo`.

## Требования к OpenAI-совместимому сервису

Адаптер не содержит настроек под конкретных поставщиков — правила общие:

- **`base_url`** — префикс до `/chat/completions`, обычно оканчивается на `/v1`. Ответ 404 или текстовый 400 на этом адресе трактуется как неверный адрес, и сообщение об этом прямо говорит.
- **`GET /models`** — если сервис его поддерживает, модели выбираются из списка. Если нет — остаётся ручной ввод идентификатора, интерфейс предлагает его сам после неудачной попытки.
- **`User-Agent`** — адаптер всегда отправляет свой (`workout-bot/...`). Дефолтный `python-httpx/...` часть сервисов за Cloudflare режет ещё до API.
- **Ответ не от API.** OpenAI-совместимый API отвечает JSON. HTML-страница или пустое тело означают, что до API запрос не дошёл: его отклонил защитный контур (WAF, прокси, балансировщик). Такие отказы (`400`, `401`, `403`, `405`, `406`, `408`, `421`, `429` без JSON) считаются случайными и повторяются; JSON-ошибка того же кода — отказ самого API, повтор не выполняется. Это отличие важно: неверный ключ повторять бессмысленно, а срабатывание защиты — полезно.
- **Сообщения об ошибках** разбираются из стандартных форм JSON (`error.message`, `error.code`, `error`, `message`, `detail`); сырой HTML в интерфейс не попадает. К типовым кодам добавляется подсказка, что проверить.
- **Повторы.** `429` и `5xx` повторяются с растущей паузой (2/4/8 с, потолок 20 с) и уважают `Retry-After`.

## Семантика: enabled, readiness, health

Три понятия намеренно разделены и не подменяют друг друга.

| Понятие | Что означает | Где вычисляется |
|---|---|---|
| `enabled` (configuration state) | AI **разрешён** администратором для задачи/провайдера/эндпоинта/модели. Это разрешение, а не гарантия доступности | флаги `ai_*.enabled` |
| readiness | Конфигурация **достаточна**, чтобы AI-вызов имел смысл: провайдер с адаптером, включённый эндпоинт, успешная проверка подключения, вызываемая модель, существующий промпт, включённая задача | `AIReadinessService` |
| health / availability | Провайдер, эндпоинт и модель **фактически** доступны прямо сейчас | `AIInfrastructureHealthService` |

`task.enabled = true` не означает, что AI будет вызван: решение принимает
runtime по актуальному readiness. Обратное тоже верно — `enabled = false`
это запрет использовать AI, а не признак поломки, поэтому в журнале fallback
он отражается отдельной причиной `task_disabled`.

Отключённая модель остаётся в конфигурации и показывается как `disabled`, а не
`unavailable`: её выключил администратор.

## Готовность конфигурации (health/status)

`GET /api/v1/admin/ai/readiness?task_type=workout_generation` (admin-only) возвращает:

- `checks` — шаги настройки: провайдер, эндпоинт, API-ключ, проверка подключения, модель, модели задачи, включённость задачи, промпт, стратегия генерации. У каждого шага статус (`ok` / `warning` / `missing` / `failed`), человекочитаемая причина, следующее действие, признак `blocking` и машиночитаемый `reason_code`;
- `ready` — все блокирующие шаги выполнены (иначе AI фактически не будет вызван);
- `chain` — эффективная цепочка кандидатов (основная модель → резервные) с учётом enabled-флагов **и** наличия адаптера протокола;
- `protocols` — какие протоколы реально поддержаны;
- `generation` — фактическая стратегия генерации программ из конфигурации сервера (`PROGRAM_PRIMARY_GENERATOR`, `PROGRAM_FALLBACK_GENERATOR`, `AUTO_GENERATE_PROGRAM_AFTER_FINALIZE`).

Отчёт не делает запросов к провайдеру: он читает конфигурацию и сохранённый результат последней проверки подключения. `api_key` — единственный неблокирующий шаг: часть self-hosted эндпоинтов ключа не требует. Проверяется не только ссылка на ключ у эндпоинта, но и наличие самого ключа в хранилище: ссылка может остаться без ключа (очистка хранилища, смена ключа шифрования), и тогда шаг показывает `failed`, а не «ключ сохранён».

## Проверка подключения

`POST /api/v1/admin/ai/endpoints/{id}/test` выполняет минимальный нейтральный запрос (без персональных данных) и **сохраняет результат** в `ai_endpoints.last_test_at / last_test_status / last_test_error_type`. Хранится только время, статус и класс ошибки — ни ключей, ни тела ответа провайдера.

Случайные отказы защитного контура повторяются внутри одной проверки, поэтому «связи нет» означает устойчивую проблему, а не однократное срабатывание Cloudflare.

Благодаря этому различаются три состояния: «подключение не проверялось», «проверка провалилась (класс ошибки)» и «проверка успешна». Непроверенное подключение делает конфигурацию не готовой.

## Защита от нерабочей конфигурации

`PUT /api/v1/admin/ai/tasks/{task_type}` с `enabled=true` проходит серверную проверку `AIReadinessService.validate_enable` и возвращает 422, если:

- не выбрана ни одна модель;
- ни одна из выбранных моделей не может быть вызвана (модель, эндпоинт или провайдер отключены, либо протокол без адаптера);
- указана версия промпта, которой нет ни в базе, ни в файлах.

Требование минимально достаточное: достаточно одной работоспособной модели, потому что именно так выбирает кандидата `AIGateway`.

**Осознанное ограничение.** Экспертный `PUT` не требует успешного connection test: синтетический ping (`max_tokens=1`, `temperature=0`) отвергается частью моделей, и жёсткая блокировка могла бы запретить включение рабочей конфигурации. Требование «тест до включения» закрыто мастером (не включает задачу без успешной проверки) и статусом готовности (непроверенное подключение = «не готово»).

## Fallback

Есть три независимых уровня. Первый добавлен в Phase 1.1.1.

**1. Configuration fallback (readiness gate).** Перед AI-попыткой
`ProgramGenerationOrchestrator` спрашивает `AIReadinessService.runtime_gate()`.
Если конфигурация заведомо нерабочая, AI-запрос **не выполняется вообще** —
система сразу берёт `DeterministicProgramGenerator`:

```text
ProgramGenerationOrchestrator
        |
        v
AI readiness gate
        |
   +----+----+
   |         |
 READY     NOT READY
   |         |
   v         v
 AI       Deterministic
 Generator Generator
```

**2. Runtime fallback.** AI был признан готовым, попытка сделана, но
завершилась ошибкой (таймаут, сбой провайдера, некорректный ответ, провал
валидации) — тогда тоже deterministic.

**3. Fallback модели внутри AI-задачи.** AI Gateway перебирает кандидатов
(основная модель → резервные) до первого успешного.

Fallback выполняется ограниченно: primary → fallback → окончательная ошибка.
Бесконечных циклов и retry-петель нет. Generation и delivery остаются
независимыми процессами.

### Причины fallback

Причина сохраняется машиночитаемо в `program.generation.fallback_reason_code`
(значение `AIFallbackReason`), человекочитаемая версия — в `fallback_reason`.

Configuration (AI не вызывался):

| Код | Когда |
|---|---|
| `ai_not_configured` | провайдера/эндпоинта нет вообще |
| `provider_unavailable` | все подходящие провайдеры отключены |
| `endpoint_unavailable` | включённого эндпоинта нет либо проверка подключения провалилась |
| `connection_not_tested` | подключение ни разу не проверялось |
| `model_unavailable` | модели задачи не выбраны или ни одна не вызываема |
| `unsupported_protocol` | у протокола провайдера нет адаптера |
| `task_disabled` | задача выключена администратором |
| `task_not_ready` | прочая незавершённая настройка (например, нет версии промпта) |
| `generator_not_configured` | AI-генератор не собирается или AI вне стратегии генерации |

Runtime (AI вызывался):

| Код | Когда |
|---|---|
| `ai_timeout` | превышен таймаут запроса |
| `ai_runtime_failure` | прочий сбой вызова |
| `ai_invalid_response` | ответ не соответствует ожидаемой структуре |
| `ai_validation_failed` | программа от AI не прошла валидацию |

Источник истины один: `runtime_gate()` берёт причину из того же чек-листа,
который показывает панель готовности. Админка и runtime не могут разойтись.

## AI Infrastructure Health Dashboard

`GET /api/v1/admin/ai/infrastructure-health` (admin-only) отдаёт дерево,
построенное **динамически** из фактической конфигурации:

```text
AIProvider → AIEndpoint → AIModel → task bindings
```

Собственного списка провайдеров и моделей ни backend-дашборд, ни frontend не
хранят. Поэтому новый провайдер или модель появляются в админке автоматически,
а безопасно удалённые — исчезают, без изменений в коде UI.

Три независимых измерения состояния:

- **configuration state** — `enabled` / `disabled`;
- **infrastructure health** провайдера и эндпоинта — `healthy`, `degraded`,
  `unavailable`, `not_tested`, `disabled`, `unsupported`;
- **model availability** — `available`, `degraded`, `unavailable`,
  `not_tested`, `disabled`, `unsupported`.

Provider может быть `healthy`, а его модель — `disabled`. Если provider
`unavailable`, ни одна его модель не показывается как `available`.

Health эндпоинта выводится из двух дешёвых источников, без запросов к
провайдеру:

1. сохранённый результат connection test (`ai_endpoints.last_test_*`);
2. последний реальный AI-вызов из журнала usage.

Второй источник закрывает сценарий «провайдер работал, потом отвалился»: если
тест успешен, а последний вызов упал, эндпоинт помечается `degraded`.

Provider агрегируется по эндпоинтам: хотя бы один `healthy` делает провайдера
`healthy`.

### Стратегия обновления health

Планировщика и фоновых воркеров в проекте нет, отдельную подсистему под
health-опрос вводить не стали. Выбрана комбинация:

- **чтение состояния** (`GET`) дешёвое, поэтому админка обновляет его
  автоматически раз в минуту и после каждой CRUD-операции. Так подхватываются
  и изменения из другой сессии, и результаты реальных AI-вызовов;
- **активная проверка** (`POST /infrastructure-health/refresh`, кнопка
  «Проверить подключения») выполняется только по требованию администратора.
  Она использует существующий connection test — минимальный ping
  (`max_tokens=1`), а не генерацию программы, и результат сохраняется в
  `last_test_*`;
- проверяются только эндпоинты, которые могут работать: отключённые и
  протоколы без адаптера пропускаются, чтобы не создавать бесполезную
  нагрузку. Неактивные модели отдельно не пингуются — их availability
  выводится из состояния эндпоинта.

В ответе нет ключей, secret_reference и тел ответов провайдера — только
признак `has_api_key`.

## Lifecycle конфигурации и safe delete

Для провайдера, эндпоинта и модели доступны view, create, edit, enable,
disable и safe delete (Admin API + UI на `/ai`).

Перед удалением сервер сам собирает зависимости и объясняет, что мешает:

```text
Provider → Endpoint → Model → Task binding
```

Модель, привязанная к задаче, блокирует удаление и самой модели, и её
эндпоинта, и всего провайдера (иначе каскад обошёл бы привязку). API
возвращает 409 с машиночитаемым списком блокеров:

```json
{"detail": {"message": "Невозможно удалить провайдера: ...",
            "blockers": [{"type": "ai_task_config",
                          "task_type": "workout_generation"}]}}
```

Предпочтительная стратегия — сначала отключить (`enabled=false`); hard delete
разрешён только при отсутствии зависимостей. Broken references не создаются.

Исторические usage/audit-записи ради удаления конфигурации не удаляются: FK
`ON DELETE SET NULL` сохраняет запись вызова и обнуляет ссылку на удалённую
модель. Секреты удаляемых эндпоинтов, наоборот, удаляются из SecretStore
явно — включая эндпоинты, удаляемые каскадом вместе с провайдером, чтобы не
оставлять осиротевшие шифрованные записи.

Все изменения AI-конфигурации попадают в существующий audit-механизм.

## Наблюдаемость

- `GET /api/v1/admin/ai/usage` — последние вызовы: задача, провайдер/эндпоинт/модель, токены, задержка, статус, класс ошибки. Prompt, ответ и персональные данные не хранятся;
- `GET /api/v1/admin/ai/audit` — изменения конфигурации: событие, актор, объект. Секретов в metadata нет;
- `GET /api/v1/admin/ai/fallback-events` — журнал fallback: запрошенный и фактический генератор, `reason_code`, признак `ai_attempted` (вызывался ли AI), время.

Журнал fallback отвечает на эксплуатационный вопрос «почему программа
сгенерирована детерминированным генератором, хотя AI включён?». Отдельной
таблицы под него нет: события пишутся в существующий журнал AI-контура с типом
`ai_generation_fallback`. В metadata нет profile_id, содержимого программы и
любых персональных данных.

Все журналы отображаются на `/ai`. Connection test записей usage не создаёт: это конфигурационная проверка, а не выполнение задачи.

## Промпты

`PromptLoader`: сначала версия из `prompt_templates` (БД), затем файловый промпт `prompts/program_generator/v{N}`. В UI видно, какие версии есть в базе; отчёт готовности показывает, откуда фактически будет взят промпт. Несуществующую версию сервер не принимает.

## Безопасность данных

Generation context намеренно не содержит Telegram ID, имени и profile ID. Секреты хранятся в зашифрованном виде и не должны возвращаться через API или попадать в логи/audit.
