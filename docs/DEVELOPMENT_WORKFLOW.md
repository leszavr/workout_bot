# Workflow дальнейшей разработки

## Перед началом задачи

1. Прочитать `AGENTS.md`.
2. Прочитать `docs/PROJECT_STATUS.md`.
3. Найти соответствующий пункт в `docs/DEVELOPMENT_ROADMAP.md`.
4. Изучить релевантный код и тематическую документацию.
5. Сформулировать критерии готовности до начала изменений.

## Во время работы

- не обходить filtering/safety/validation;
- не дублировать AI-контур;
- не смешивать generation и delivery retry;
- не объявлять работу завершённой только по наличию кода;
- добавлять тесты на новый путь и на failure path.

## Перед завершением

- [ ] тесты пройдены локально (`pytest` на реальной PostgreSQL);
- [ ] проверены негативные сценарии;
- [ ] миграции проверены, alembic head один;
- [ ] frontend: lint, typecheck, production build;
- [ ] открыт Pull Request и **CI на нём завершился успешно**;
- [ ] обновлён `PROJECT_STATUS.md`;
- [ ] обновлён `CHANGELOG.md`;
- [ ] обновлён roadmap;
- [ ] обновлена архитектурная/AI/operations документация, если затронута;
- [ ] подготовлен короткий итог: что сделано, что проверено, что осталось.

## CI как часть Definition of Done

Работа ведётся в отдельной ветке и попадает в `main` только через Pull
Request. CI (`.github/workflows/ci.yml`) запускается на каждый PR и проверяет
backend-тесты, цепочку миграций и сборку frontend. Состав джоб — в
`OPERATIONS.md`.

- «код написан» и «CI зелёный» — разные состояния; задача не завершена, пока
  хотя бы один реальный прогон CI на PR не прошёл успешно;
- локальный прогон тестов не заменяет CI: локальная БД может быть уже
  наполнена, а CI поднимает окружение с нуля;
- падение CI на PR автоматически создаёт issue с меткой `ci-failure` — его
  нужно разобрать, а не перезапускать прогон вслепую;
- зелёный CI не отменяет ручную проверку сценариев, которые CI не покрывает
  (реальный провайдер AI, доставка в Telegram, production-сборка Docker).

## Definition of Done

Задача считается завершённой только когда код, тесты, CI, документация и фактический статус согласованы между собой.
