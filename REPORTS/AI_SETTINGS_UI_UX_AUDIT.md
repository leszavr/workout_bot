## 1. Executive Summary

Страница `/ai` — служебный экран внутренней админки для настройки AI Gateway. Она реализована как **прямое отражение технической архитектуры backend** (Provider → Endpoint → Model + Task → Bindings) и даёт полный контроль над сущностями, но **не даёт пользователю ментальной модели того, что он делает и к какому результату должен прийти**.

Ключевые выводы:

1. **Нет onboarding и нет индикации «что ещё не настроено».** Первый запуск показывает пустые списки и 6 задач с выключенными чекбоксами. Нигде не сказано, что для работающей AI-генерации нужно: провайдер → эндпоинт с ключом → модель → привязка модели к задаче `workout_generation` → включение задачи. Пользователь должен реконструировать эту цепочку сам из названий секций.
2. **Реальная конфигурация генерации программ разорвана между тремя местами**, и страница `/ai` покрывает только одно из них: выбор AI-моделей для задачи. Стратегия «AI → детерминированный fallback» задаётся переменными окружения `PROGRAM_PRIMARY_GENERATOR`/`PROGRAM_FALLBACK_GENERATOR` (`.env`), а кнопка «Generate Program» на странице профиля вообще использует третий код-путь (`ProgramService` без оркестратора и без fallback). Из `/ai` ни то, ни другое не видно и не управляется.
3. **UI позволяет создать заведомо нерабочую конфигурацию**: протоколы «Anthropic» и «Произвольный» доступны в выпадающем списке, но адаптеров для них в backend нет — любой запрос упадёт с `AIUnsupportedProtocolError`. Никакого предупреждения в UI.
4. **Backend богаче UI**: удаление сущностей, управление промптами (`prompt_templates`), журнал использования (`ai_usage_records`: токены, латентность, ошибки) и журнал аудита (`ai_audit_events`) реализованы в API, но в UI отсутствуют полностью. Сценарий «понять, какая модель реально сработала и сколько токенов потрачено» через `/ai` невыполним.
5. **Фактическое состояние БД на момент аудита подтверждает проблемы на практике**: единственный созданный через UI эндпоинт получил в поле «Название» значение URL (`https://api.tokenrouter.com/v1` — пользователь перепутал поля), эндпоинт и модель в итоге **отключены**, конфигурация задачи `workout_generation` отсутствует (0 строк в `ai_task_configs`). То есть живой пользователь прошёл путь до конца, но рабочая AI-конфигурация не сложилась, и система сейчас при генерации молча уходит в детерминированный fallback.

Итог: страница функционально почти полная для CRUD сущностей, но как инструмент «настроить AI, чтобы программы генерировались нейросетью» — не работает без внешнего знания архитектуры.

## 2. Что представляет собой страница /ai

`/ai` — одна из пяти страниц внутреннего веб-интерфейса (Next.js 14, app router, единственный файл `apps/web/app/ai/page.tsx`, ~600 строк, без подкомпонентов из других файлов). Доступ только по JWT администратора (`workout_admin_token` в localStorage; при отсутствии — редирект на `/login`).

Назначение страницы — администрирование AI Gateway (этап 3B): провайдеры, эндпоинты, модели, секреты, задачи и привязки моделей к задачам. Страница обращается к `/api/v1/admin/ai/*` (backend `apps/backend/api/v1/ai_routes.py`, все роуты за `require_admin`).

Реально используемая AI-задача в системе одна — `workout_generation` (генерация программы тренировок через `AIProgramGenerator`). Остальные 5 типов задач (`program_adjustment`, `profile_analysis`, `exercise_explanation`, `user_chat`, `feedback_analysis`) существуют как enum-задел: код их не вызывает (это прямо указано в докстринге `src/domain/ai/enums.py`: «Сейчас реально используется только workout_generation»).

## 3. Структура интерфейса

Общий layout: слева фиксированный сайдбар `AppNav` (бренд «🏋️ Workout Bot» и 5 ссылок: Панель, Профили, Программы, Упражнения, AI-конфигурация), справа основная область.

Сверху вниз:

1. **Заголовок** `h1` «AI-конфигурация». Под ним — зоны для красной плашки ошибки (`div.error`) и зелёной плашки-уведомления (`badge confirmed`, живёт 4 секунды после каждого действия).
2. **Карточка «Провайдеры»** (секция 1):
   - **Форма создания провайдера** — горизонтальная строка (`toolbar`) из четырёх элементов: текстовое поле «Название» (placeholder «например, RouterAI»), текстовое поле «Идентификатор slug» (placeholder «например, router-ai»), выпадающий список «Протокол» (OpenAI-совместимый / Anthropic / Произвольный), кнопка «Создать провайдера».
   - **Список провайдеров.** Пустое состояние — фраза «Провайдеров пока нет.». Каждый провайдер — строка: имя (жирный), бейдж протокола, приглушённый текст `slug: …`, кнопка «Отключить»/«Включить».
   - **Вложенный блок «Эндпоинты»** (с отступом 16px внутри каждого провайдера):
     - Форма создания: «Название эндпоинта», «Базовый URL» (placeholder `https://example.com/v1`), «API-ключ» (тип password, placeholder «необязательно»), «Таймаут, с», «Повторные попытки», кнопка «Создать эндпоинт». Пустое состояние — «Эндпоинтов нет.».
     - Каждый эндпоинт — вложенная карточка: имя, base URL, «таймаут N с · повторы M», бейдж ключа («ключ: ****XXXX» зелёный либо «ключ не задан» серый), кнопки «Отключить»/«Включить» и «Проверить подключение». Под строкой — результат последней проверки: «✓ Подключение успешно (N мс, модель: X)» или «✗ ТипОшибки: сообщение». Ниже — строка ротации ключа: password-поле «Новый API-ключ (ротация)» + кнопка «Сохранить ключ».
     - **Вложенный блок «Модели»** внутри каждого эндпоинта: форма создания (Идентификатор модели, Отображаемое имя, Контекстное окно, Макс. токенов ответа, три чекбокса: «JSON-схема», «структурированный вывод», «потоковый вывод», кнопка «Создать модель»). Пустое состояние — «Моделей нет.». Список — таблица с колонками ИДЕНТИФИКАТОР / ИМЯ / КОНТЕКСТ / МАКС. ОТВЕТ / ВОЗМОЖНОСТИ / СТАТУС / кнопка «Отключить»/«Включить».
3. **Карточка «AI-задачи»** (секция 2):
   - Состояние загрузки — «Загрузка...» (единственный loading state страницы).
   - Всегда отображаются **все 6 типов задач** (даже не сконфигурированные — backend возвращает дефолты). Каждая задача — вложенная карточка: русское название + технический идентификатор в скобках (например, «Генерация программы тренировок (workout_generation)»), чекбокс «включена», числовые поля «Температура», «Макс. токенов», «Версия промпта», блок «Модели (порядок: основная → резервные)» — нумерованный список выбранных моделей с кнопками ↑ / ↓ / «убрать» (пустое состояние «Модели не выбраны.»), выпадающий список «Добавить модель...» (все модели всех эндпоинтов одним списком), кнопка «Сохранить задачу».

Модальных окон нет — все формы инлайн. Вкладок нет. Пагинации нет (списки загружаются целиком). Подтверждений опасных действий нет (впрочем, удалять в UI нечего — см. раздел 13).

## 4. Карта пользовательского пути

Путь пользователя выглядит так:

1. Вход на `/login` (форма логин/пароль) → JWT в localStorage.
2. Переход на `/ai` (ссылка «AI-конфигурация» в сайдбаре).
3. Секция «Провайдеры»: заполнить название + slug + протокол → «Создать провайдера» → плашка «Провайдер создан», список обновляется.
4. Внутри карточки провайдера: заполнить форму эндпоинта (название, base URL, опционально API-ключ, таймаут, повторы) → «Создать эндпоинт».
5. В карточке эндпоинта: при необходимости ввести ключ в поле ротации → «Сохранить ключ». Нажать «Проверить подключение» и прочитать результат.
6. Внутри карточки эндпоинта: создать модель (идентификатор, имя, опционально контекст/лимит токенов, чекбоксы возможностей) → «Создать модель».
7. Прокрутить страницу вниз до «AI-задачи», найти карточку «Генерация программы тренировок», в селекте «Добавить модель...» выбрать модель, при необходимости задать порядок (↑/↓), отметить «включена», нажать «Сохранить задачу».
8. **Разрыв пути:** после шага 7 интерфейс никак не сообщает, что AI-генерация теперь «вооружена». Нет ни сводного статуса («задача workout_generation: primary X, fallback Y, детерминированный fallback из .env»), ни ссылки на проверку. Более того, реальное поведение при генерации зависит ещё и от переменных окружения, которые на странице не видны.

Onboarding-элемента (подсказка, мастер, чек-лист «1. провайдер 2. эндпоинт 3. ключ 4. модель 5. привязка 6. включить») на странице **нет**. Единственная навигационная подсказка — сами заголовки секций и порядок их следования (провайдеры выше задач), который случайно совпадает с правильным порядком настройки.

## 5. Provider

**Форма создания** (3 поля):

| Поле | Обязательное | Ограничения backend | Пояснение в UI |
|---|---|---|---|
| Название | да (min 1) | 1–100 символов | только placeholder «например, RouterAI» |
| slug | да (min 1) | 1–64, regex `^[a-z0-9_-]+$` | только placeholder «например, router-ai» |
| Протокол | да (дефолт openai_compatible) | enum: openai_compatible / anthropic / custom | выпадающий список с русскими подписями |

Поля `enabled` и `priority` при создании не задаются (дефолты `true` и `100`). После сохранения провайдер появляется в списке; доступны только переключение «Отключить/Включить» и (не в UI, но в API) редактирование/удаление.

**Ошибки:** невалидный slug → 422 с текстом Pydantic-валидации (английский технический текст в красной плашке); дубликат slug → 409.

**Ответ на вопрос «понятно ли человеку без знания архитектуры, что такое Provider?»:** частично. Слово «Провайдер» и placeholder «RouterAI» намекают на вендора API, но страница нигде не объясняет, что провайдер — это лишь группировка эндпоинтов с общим протоколом, и что сам по себе (без эндпоинта, ключа и модели) он ничего не делает. Пользователь, создавший провайдера, не получает ни подсказки «теперь создайте эндпоинт», ни визуального признака неполноты (карточка провайдера без эндпоинтов выглядит «готовой»: имя, бейдж, кнопка).

Отдельная проблема: **выбор протокола не ограничен реально работающими адаптерами**. В `src/infrastructure/ai/adapters.py` зарегистрирован только `OpenAICompatibleAdapter`; `anthropic` и `custom` — задел без реализации (докстринг `enums.py`: «адаптера пока нет»). Создание провайдера с этими протоколами проходит успешно, но все запросы и проверка подключения завершатся `AIUnsupportedProtocolError` («Для протокола 'anthropic' не зарегистрирован адаптер»). UI эту ситуацию не предотвращает и не объясняет.

## 6. Endpoint

Эндпоинт создаётся **внутри карточки провайдера** (вложенная форма), связь 1:N отображается вложенностью блоков. Поля:

| Поле | Обязательное | Ограничения backend | Комментарий |
|---|---|---|---|
| Название | да | 1–100 символов | свободный текст |
| Базовый URL | да | 8–500 символов | здесь задаётся адрес API |
| API-ключ | нет | ≤500 символов | password-поле, шифруется при сохранении |
| Таймаут, с | нет (дефолт 60) | 1–600 | в UI это text-input, не number |
| Повторные попытки | нет (дефолт 2) | 0–5 | в UI text-input |

`enabled`/`priority` — дефолты `true`/`100`, в форме отсутствуют. Несколько эндпоинтов у одного провайдера поддерживаются (и формой, и backend), но сценарий их использования (например, основной и резервный URL одного вендора) никак не объяснён.

**Наблюдение из реальной БД (подтверждает запутанность формы):** единственный живой эндпоинт (id=82) имеет `name = "https://api.tokenrouter.com/v1"` — то же значение, что и `base_url`. Пользователь вставил URL в оба поля: поле «Название эндпоинта» не несёт понятной семантики, и URL оказался самым «логичным» значением для него. В списке эндпоинт теперь отображается как «https://api.tokenrouter.com/v1 https://api.tokenrouter.com/v1» (имя + URL рядом).

**Проверка подключения** (`POST /endpoints/{id}/test`) — удачное решение: минимальный нейтральный запрос (`"ping"`, max_tokens=1) без персональных данных, с замером латентности. Детали реализации, влияющие на UX:
- тестируется **первая модель эндпоинта**; если моделей нет, отправляется модель `"ping"`, что даёт ошибку «model not found» от провайдера — сообщение выглядит как проблема ключа/сети, хотя проблема в отсутствии модели;
- тест работает даже для **отключённого** эндпоинта (статус `enabled` не проверяется) — это скорее плюс для диагностики;
- результат показывается строкой под карточкой и **не сохраняется** после перезагрузки страницы.

**Ответ на вопрос «не избыточна ли модель Provider → Endpoint?»:** для текущей задачи (один OpenAI-совместимый агрегатор и одна модель) — избыточна. Пользователь вынужден трижды создавать сущности, чтобы описать по факту одну вещь: «адрес API + ключ». Уровень провайдера несёт только протокол (который всегда `openai_compatible`, других рабочих нет), уровень эндпоинта — URL/таймаут/ключ. В продуктовой модели это одна форма «Подключение к AI-сервису». Вместе с тем backend-архитектура (адаптеры протоколов, несколько эндпоинтов на провайдера) рассчитана на рост — вопрос в том, чтобы не вываливать эту гибкость в UI раньше времени (см. раздел 18).

## 7. API Keys / Secrets

**Путь ключа:**

```
страница /ai
→ карточка эндпоинта
→ (а) поле «API-ключ (необязательно)» в форме создания эндпоинта
   или (б) поле «Новый API-ключ (ротация)» + кнопка «Сохранить ключ»
→ PUT /api/v1/admin/ai/endpoints/{id}/secret  (или POST .../endpoints при создании)
→ AIConfigurationService.rotate_endpoint_secret / create_endpoint
→ SecretStore.put: шифрование Fernet (AES-128-CBC + HMAC),
  ключ шифрования из AI_SECRETS_KEY или (dev) JWT_SECRET
→ PostgreSQL, таблица ai_secrets (reference, encrypted_value)
```

Свойства (проверено по коду `src/infrastructure/ai/secrets.py`, `admin_service.py`):

- **После сохранения ключ не отображается никогда** — только бейдж «ключ: ****XXXX» (последние 4 символа) либо «ключ не задан». В API нет поля для чтения секрета (`EndpointOut` намеренно без `api_key`).
- **Замена ключа** — да, в любой момент через поле ротации (атомарная замена по той же ссылке).
- **Удаление ключа** — в UI нет (нет кнопки «удалить ключ»; можно только заменить). В backend удаление секрета происходит автоматически при удалении эндпоинта.
- **Привязка** — ключ принадлежит **эндпоинту** (не провайдеру и не модели). В UI это видно: поле ротации находится в карточке эндпоинта, рядом с его URL. Перепутать привязку сложно — форма одна и она в контексте конкретного эндпоинта.
- **Несколько ключей** — нет, один ключ на эндпоинт (замена перезаписывает).
- **Индикация «ключ настроен»** — зелёный бейдж «ключ: ****XXXX». Этого достаточно.
- **Проверка работоспособности** — кнопка «Проверить подключение» (см. раздел 6). Успех: «✓ Подключение успешно (N мс, модель: X)». Ошибка: «✗ ТипОшибки: сообщение» (красным). Типы ошибок — имена Python-классов (`AIAuthenticationError`, `AITimeoutError` и т.п.), не локализованы.

**Ответ на вопрос «может ли пользователь сохранить ключ не туда?»:** риск низкий для ключа (форма одна, контекст очевиден), но есть смежный риск: пользователь может не понять, что ключ без созданной модели и без привязки к задаче ничего не делает — ключ «настроен» (бейдж зелёный), проверка проходит, а генерация всё равно не работает, потому что не сконфигурирована задача. Разрыв между «ключ проверен» и «AI реально используется» никак не подсвечен.

**Наблюдение из БД:** в `ai_secrets` 3 строки при 1 живом эндпоинте — две записи-сироты (`ai-endpoint-07ed…`, `ai-endpoint-2864…`) без соответствующих эндпоинтов. Вероятно, остались от удалённых ранее эндпоинтов (удаление шло не через `delete_endpoint`, либо записи созданы тестами). На UI это не влияет, но показывает, что инвентаря секретов в интерфейсе нет и «хвосты» никто не видит.

## 8. Models

Модель создаётся **внутри карточки эндпоинта** (вложенность Provider → Endpoint → Model отражена вложением блоков). Поля формы:

| Поле | Обязательное | Ограничения | Комментарий |
|---|---|---|---|
| Идентификатор модели | да | 1–200 | строка, которой модель зовётся в API провайдера (например `qwen/qwen3.8-max-free`) |
| Отображаемое имя | да в backend; UI подставляет model_id, если пусто | 1–200 | для списков |
| Контекстное окно | нет | 1–10 000 000 | число |
| Макс. токенов ответа | нет | 1–1 000 000 | число |
| JSON-схема / структурированный вывод / потоковый вывод | нет (чекбоксы) | bool | capabilities |

`enabled`/`priority` — дефолты, в форме отсутствуют. Несколько моделей одного провайдера — да (через один или разные эндпоинты). Список моделей — таблица со статусом («включена»/«отключена») и кнопкой переключения.

**Приоритеты и порядок выбора.** У модели есть поле `priority` (дефолт 100), но **оно не используется нигде при выборе** — `ModelSelector` сортирует кандидатов по приоритету **привязки к задаче** (`ai_task_model_bindings.priority`), а приоритеты провайдера/эндпоинта/модели не читает (`src/application/ai/selection.py`). То же касается capabilities: задача `workout_generation` не передаёт `requirements` (в `AIProgramGenerator` запрос создаётся без них), поэтому чекбоксы «JSON-схема/структурный вывод/поток» сейчас носят информационный характер и на отбор не влияют. Пользователь заполняет поля, которые ни на что не влияют, и не может об этом узнать.

**Главный вопрос: как пользователь поймёт, какая модель реально будет использоваться?** По интерфейсу — **частично и только для AI-уровня**: в карточке задачи список «Модели (порядок: основная → резервные)» показывает порядок перебора внутри AI Gateway (первый элемент — primary). Но:
- если задача выключена или список пуст — реально используется **детерминированный генератор**, и об этом на странице нет ни слова;
- стратегия «AI в принципе включён как primary» определяется `PROGRAM_PRIMARY_GENERATOR` в `.env` — вне UI;
- страница профиля с кнопкой «Generate Program» использует отдельный код-путь с radio-кнопкой «детерминированная/AI» и без fallback-оркестратора (см. раздел 11.4).

Прямо указываю: **определить из `/ai`, какая модель и при каких условиях реально сгенерирует программу, невозможно**.

## 9. AI Tasks

Секция «AI-задачи» всегда показывает 6 карточек (backend `list_tasks` возвращает все типы enum + дефолты для отсутствующих конфигураций). Для каждой задачи:

- чекбокс «включена» (для не сконфигурированных — выключен);
- параметры: Температура (дефолт 0.7), Макс. токенов (пусто), Версия промпта (пусто);
- список привязанных моделей с порядком (основная → резервные), кнопки ↑/↓/убрать;
- селект «Добавить модель...» — **плоский список всех моделей всех эндпоинтов** (без указания провайдера/эндпоинта; формат «Отображаемое имя (идентификатор)»);
- кнопка «Сохранить задачу» (PUT всего состояния карточки одним запросом).

Для `workout_generation` это означает:

- включить/выключить — да (чекбокс);
- назначить модели — да, несколько, порядок задаётся кнопками ↑/↓ (при сохранении backend заменяет привязки атомарно, priority = позиция, первая = `is_primary`);
- fallback внутри AI — да (вторая и далее модели);
- понять порядок выбора — да, по нумерации списка («Основная: …», «Резервная 1: …»);
- увидеть активную конфигурацию — частично: видно привязки и флаг «включена», но не видно итоговое поведение системы (см. ниже).

**Сценарий «Primary: Qwen 3.8 Max, Fallback: Deterministic Generator»:**

1. **Можно ли сделать это полностью через `/ai`?** Нет.
2. **Где разрыв?** Через `/ai` настраивается только первая половина: модель Qwen как primary задачи `workout_generation` (и, при желании, резервные AI-модели). Переход «AI не справился → детерминированный генератор» реализован в `ProgramGenerationOrchestrator` и управляется переменными `PROGRAM_PRIMARY_GENERATOR=ai` / `PROGRAM_FALLBACK_GENERATOR=deterministic` (в `.env` сейчас так и задано). В UI этих переменных нет, как и нет индикации, что они существуют.
3. **Что делать вне UI?** Убедиться, что в `.env`/окружении заданы `PROGRAM_PRIMARY_GENERATOR=ai` и `PROGRAM_FALLBACK_GENERATOR=deterministic`, и что процесс перезапущен. Плюс обязательные вещи, которые тоже вне страницы: наличие провайдера/эндпоинта/модели/привязки и включённая задача.
4. **Понятно ли это из интерфейса?** Нет. В карточке задачи нет ни поля «fallback-генератор», ни текста «при недоступности AI программа будет сформирована детерминированно». Пользователь, настроивший Qwen, не узнает из UI, что при её ошибке сработает детерминированный генератор (и не узнает, когда это произойдёт — usage/audit в UI отсутствуют).

Дополнительно: **поле `timeout_seconds` задачи (дефолт 120) в UI отсутствует**, но DTO `TaskConfigPut` имеет дефолт `timeout_seconds=120`, и фронтенд его не отправляет — значит, **каждое сохранение задачи молча сбрасывает timeout на 120**, даже если ранее он был изменён через API. Это скрытая потеря конфигурации.

## 10. Model Bindings и Priority

Привязки «задача ↔ модель» — центральный механизм выбора модели:

- создание/замена — только через «Сохранить задачу» (`PUT /tasks/{task_type}` с `model_ids` в нужном порядке); отдельного CRUD привязок в UI нет;
- priority привязки = позиция в списке (0 → priority=1, `is_primary=true`);
- удаление привязки — кнопка «убрать» + «Сохранить задачу»;
- `ModelSelector` отбрасывает привязки, у которых выключена модель, эндпоинт или провайдер, либо модель не проходит по capabilities; оставшиеся сортируются по priority — так получается цепочка primary → fallback1 → fallback2…

Что **не видно** в UI:
- эффективный список кандидатов после фильтров (например, что отключённый эндпоинт вычеркнул модель из цепочки);
- приоритеты провайдера/эндпоинта/модели (существуют в БД, редактируются через API, но не используются селектором — «мёртвый» конфиг, который разработчик может принять за рабочий рычаг);
- предупреждение «задача включена, но все её модели отфильтрованы» — состояние, при котором генерация гарантированно упадёт в fallback/ошибку.

## 11. Реальные пользовательские сценарии

### 11.1 Подключение Qwen 3.8 Max (Сценарий A)

Дано: API-ключ TokenRouter, цель — модель Qwen 3.8 Max для генерации программ.

| Шаг | Действие | Сущность | Где ошибиться |
|---|---|---|---|
| 1 | Создать провайдера: имя, slug (латиница/цифры/`-_`), протокол | `ai_providers` | выбрать «Anthropic»/«Произвольный» → нерабочий провайдер без предупреждения; невалидный slug → 422 |
| 2 | Создать эндпоинт: название, base URL `https://api.tokenrouter.com/v1`, ключ, таймаут, повторы | `ai_endpoints` + `ai_secrets` | перепутать «название» и URL (уже случилось в реальной БД); забыть ключ — бейдж «ключ не задан» подскажет, но проверка подключения упадёт с ошибкой авторизации |
| 3 | «Проверить подключение» | — | при отсутствии модели тест шлёт `model="ping"` → «model not found», можно решить, что ключ неверен |
| 4 | Создать модель: идентификатор `qwen/qwen3.8-max-free`, имя, контекст, чекбоксы | `ai_models` | неверный `model_id` (не совпадает с именем модели в API) → ошибки при реальной генерации; проверка подключения этого не ловит, если тест прошёл по другой (первой) модели |
| 5 | В «AI-задачи» → «Генерация программы тренировок»: добавить модель, включить, сохранить | `ai_task_configs` + `ai_task_model_bindings` | забыть включить задачу; сохранить задачу с выключенной моделью |
| 6 | (вне UI) Убедиться, что `PROGRAM_PRIMARY_GENERATOR=ai` в окружении | `.env` | не знать о существовании переменной |

Итого: **4 сущности, 4 формы, ~12–15 действий**, минимум 3 точки тихого провала (протокол, название эндпоинта, переменная окружения). Живой прогон пользователем (audit-события 2026-08-20 04:31–04:44 UTC: создание провайдера → эндпоинта → модели, затем отключение модели и эндпоинта) показывает, что путь проходится, но рабочая конфигурация не складывается: сейчас эндпоинт и модель отключены, привязок нет.

### 11.2 Замена модели (Сценарий B)

«Заменить Qwen на другую модель»:

- модель у того же провайдера/эндпоинта: создать новую модель (шаг 4 из 11.1) → в задаче «убрать» старую, добавить новую, при необходимости поднятьть ↑, «Сохранить задачу». Provider/endpoint не трогаются. ~4 действия;
- модель другого провайдера: новый провайдер + эндпоинт (+ключ) + модель, затем перепривязка задачи. ~10 действий;
- старую модель можно оставить отключённой (кнопка «Отключить») — тогда она исключится из цепочки, но останется в списке привязок; удалить через UI нельзя (кнопки удаления нет), попытка удалить через API упрётся в 409 «Модель используется в конфигурации задачи. Отключите её…».

Подводный камень: порядок в списке привязок — единственный способ задать primary; при замене важно не просто добавить модель, а поставить её на первое место и сохранить. UI это позволяет (↑/↓), но не проверяет и не подсвечивает, что первая позиция особая, кроме подписи «Основная:».

### 11.3 Отключение неработающей модели (Сценарий C)

«Qwen перестала работать, временно отключить»:

- действие: кнопка «Отключить» у модели (или у эндпоинта/провайдера — любой уровень). Сохранение задачи не требуется — селектор читает `enabled` в момент запроса;
- эффект: `ModelSelector` исключит модель из кандидатов. Если других привязок нет → AI Gateway бросит `AIConfigurationError` («нет доступных моделей») → в Telegram-pipeline оркестратор перейдёт на детерминированный генератор (пользователь получит программу без AI), при генерации через API/веб — ошибка 422;
- **понятно ли из UI?** Нет: после отключения модели интерфейс не сообщает последствий. Ни в карточке модели, ни в карточке задачи не появляется предупреждение «задача осталась без моделей — сработает fallback/ошибка». Фактическое поведение (fallback) видно только в логах backend и в `GenerationInfo.fallback_used` сохранённой программы, но не на `/ai`.

### 11.4 Primary / Fallback configuration (Сценарий D)

Конфигурация «Primary: Model A → Fallback: Model B → Final fallback: Deterministic»:

- **Что поддерживает backend:** полностью. Уровень 1 — несколько привязок у задачи (A priority=1, B priority=2): `AIGateway` перебирает кандидатов при ошибках. Уровень 2 — `ProgramGenerationOrchestrator` (ai → deterministic) с конфигурацией из env.
- **Что позволяет настроить UI:** только уровень 1 (список моделей задачи с порядком). Уровень 2 существует лишь в `.env`; более того, оркестратор используется **только в Telegram-pipeline** (автогенерация после подтверждения анкеты). Кнопка «Generate Program» на странице профиля вызывает `POST /profiles/{id}/programs/generate` → `ProgramService` с явно выбранным генератором (radio «детерминированная/AI», дефолт — детерминированная) — **без оркестратора и без fallback вообще**: если выбрать «AI» при нерабочей конфигурации, будет просто ошибка 422.

Таким образом, одна и та же операция «сгенерировать программу» имеет в системе **три разных пути** (Telegram-автогенерация с оркестратором; кнопка в вебе без fallback; прямой вызов API), и страница `/ai` не отражает ни одного из них целиком.

### 11.5 Анализ использования AI (Сценарий E)

«Понять: какая модель использовалась, сколько длилась генерация, сколько токенов, были ли ошибки, был ли fallback»:

- через `/ai` — **нет**. На странице нет ни журнала вызовов, ни счётчиков, ни статусов;
- backend при этом всё пишет: `ai_usage_records` (task, provider/endpoint/model, profile/program, input/output/total tokens, latency_ms, status success/error, error_type) доступен через `GET /api/v1/admin/ai/usage`; `ai_audit_events` — через `GET /api/v1/admin/ai/audit`. Оба endpoint'а работают (проверено: usage пуст — AI ещё не вызывался, audit содержит 5+ событий конфигурации), но UI их не потребляет;
- косвенно результат виден на странице программы (`generation.provider`, `generation.model`, `generation.prompt_version`) — но только факт успешной генерации, без токенов/латентности/ошибок/fallback-цепочки.

## 14. Что есть в UI, но вызывает вопросы

1. **Поле «Версия промпта» в карточке задачи.** Число, которое подставляется в `PromptLoader`: сначала поиск в `prompt_templates` (БД), затем файл `prompts/program_generator/v{N}`. В БД промптов нет (0 строк), файловая версия одна — v1. Если администратор впишет `2` и сохранит, генерация упадёт с «Промпты для задачи … v2 не найдены». UI не показывает доступные версии и не предупреждает.
2. **Чекбоксы возможностей модели** (JSON-схема, структурированный вывод, поток). Заполняются пользователем, но единственная реальная задача не передаёт `requirements`, поэтому флаги ни на что не влияют. Либо это лишние поля сейчас, либо недостающая логика требований.
3. **Протоколы «Anthropic» и «Произвольный»** в селекте создания провайдера — выбираемые, но нерабочие (нет адаптеров).
4. **Шесть карточек задач**, из которых пять — фикция («задел»). Они создают впечатление, что система умеет «Анализ профиля», «Чат с пользователем» и т.д. Настройка этих задач ни на что не влияет: код их не вызывает.
5. **Селект «Добавить модель...» без контекста провайдера/эндпоинта.** При нескольких провайдерах список станет плоской мешаниной; уже сейчас модель отображается как «qwen3.8-max-free (qwen/qwen3.8-max-free)» без указания, откуда она.
6. **Text-input'ы для числовых полей** (таймаут, повторы, температура, токены) — ввод нечисла молча превращается в дефолт (`Number(x) || 0`), валидации нет.
7. **Плашка-уведомление живёт 4 секунды** и не отличает успех от информации; ошибки показываются сырым текстом backend (часто английским Pydantic/Python-текстом).

## 15. UX-анализ

### Developer

Понимает Provider/Endpoint/Model/Fallback/Priority. Ему страница даёт быстрый CRUD всех сущностей, вложенность отражает связи данных, проверка подключения и маскирование ключей — на месте. Но:
- он не увидит в UI эффективную цепочку кандидатов (придётся читать `selection.py` или лезть в `ai_usage_records`);
- «мёртвые» приоритеты провайдера/эндпоинта/модели введут в заблуждение при отладке порядка выбора;
- разрыв между тремя путями генерации (оркестратор/env/кнопка в вебе) обнаружится только при чтении кода;
- нет доступа к usage/audit из UI — отладка «почему сработал fallback» требует psql.

Оценка: работать можно, но страница экономит ему лишь половину пути.

### Technical Administrator

Понимает API-ключ и модель, не знает архитектуру приложения. Сможет ли самостоятельно подключить новую модель?
- создать провайдера, эндпоинт с ключом, модель и даже привязать её к задаче — **скорее да**, форма ведёт по шагам сверху вниз, проверка подключения даёт обратную связь;
- но: выбор протокола (3 варианта без пояснений), бессмысленное «Название эндпоинта» (живой пример с URL в этом поле), отсутствие чек-листа и итоговой индикации «AI готов к работе» — высокие шансы оставить конфигурацию неполной (что и произошло в реальной БД: всё создано, всё отключено, задача не сконфигурирована);
- диагностировать проблему («почему программы генерируются не через AI») без разработчика не сможет — usage/audit/переменные окружения вне UI.

Оценка: PARTIAL — довести до «всё создано» сможет, до «всё работает и я могу это проверить» — нет.

### Product Owner

Хочет: «Вот ключ, вот Qwen, она генерирует программы». Не должен знать про Endpoint/Binding/Selector.
- страница требует от него ровно того, что он не должен знать: slug, протокол, таймауты, повторы, capabilities, привязки, приоритеты;
- концепция «задача» (6 штук) и «версия промпта» для него — шум;
- результат своих действий он проверить не может: нет ни статуса «AI подключён и готов», ни пробной генерации, ни журнала.

Оценка: NO — без сопровождения разработчика не настроит и не проверит.

## 16. Сильные стороны

Что сделано хорошо и не должно переписываться без необходимости:

1. **Безопасность секретов — образцовая.** Fernet-шифрование at rest, ключ никогда не возвращается API/фронту, masked-представление `****XXXX`, ротация атомарна, audit-события не содержат секретов, удаление эндпоинта чистит секрет. Это нельзя ломать при UX-упрощениях.
2. **Проверка подключения эндпоинта** — быстрая, безопасная (нейтральный запрос без персональных данных), с латентностью и именем модели. Один из лучших элементов страницы.
3. **Вложенность блоков Provider → Endpoint → Model** визуально точно отражает связи данных; пользователь никогда не потеряет, к какому провайдеру относится эндпоинт.
4. **Атомарное сохранение задачи** (`PUT` сразу с привязками) исключает рассинхрон «конфиг сохранён, привязки нет».
5. **Защита от удаления модели с привязкой** (409 + человекочитаемое сообщение «Отключите её вместо удаления») — правильный guardrail, хоть и не доступен пока из UI.
6. **Полнота backend-модели данных**: раздельные таблицы для providers/endpoints/models/tasks/bindings/secrets/usage/audit/prompts закрывают практически все будущие продуктовые сценарии. UI отстаёт от backend, а не наоборот — хорошая стартовая позиция.
7. **Русскоязычные подписи** задач и протоколов (`labels.ts`), все надписи консистентны.
8. **Идемпотентность и версионирование промптов в backend** (версии неизменяемы, `next_version` считается автоматически) — грамотная основа для будущего UI промптов.

## 18. Архитектурный анализ текущей модели AI Settings

**1. Какая модель сейчас реализована?** Техническая:

```
Provider → Endpoint → Secret → Model → Task → Binding → Priority
```

Страница — почти дословный CRUD-обход этой цепочки: каждая сущность получила свою форму/список, связи показаны вложенностью.

**2. Насколько она соответствует архитектуре backend?** Почти на 100% — UI является тонкой оболочкой над `/api/v1/admin/ai/*`, который в свою очередь зеркалит таблицы БД. Расхождения только в сторону отставания UI (раздел 13) и одной рассинхронизации DTO (timeout).

**3. Насколько соответствует способу мышления администратора?** Слабо. Администратор думает задачей и результатом:

```
«Генерация программ» → Qwen 3.8 Max → ключ TokenRouter → fallback: детерминированный
```

Интерфейс же требует сначала построить инфраструктурную пирамиду (провайдер → эндпоинт → модель), а потом ещё одну (задача → привязки → порядок), и при этом ключевая часть реальной стратегии (fallback на детерминированный генератор) вообще лежит вне страницы.

**4. Где возникает когнитивная сложность?**
- три уровня вложенности до того, как появится «полезная» сущность (модель);
- две независимые системы приоритетов (приоритеты сущностей — не используются; приоритеты привязок — используются) — пользователь видит слово «priority» в API/БД и делает неверные выводы;
- два уровня fallback (модели внутри AI; AI→deterministic между генераторами) настроены в разных местах и ни один не отображён целиком;
- три пути генерации программы (Telegram-оркестратор, веб-кнопка, API) с разным поведением.

**5. Какие сущности пользователь вынужден понимать зря?**
- **Provider** в текущих реалиях (один протокол, один вендор) — чистая группировка; продуктовый смысл появится при нескольких протоколах/вендорах;
- **priority провайдера/эндпоинта/модели** — не используются селектором;
- **capabilities-чекбоксы** — не используются отбором;
- **5 неиспользуемых типов задач** — шум;
- **версия промпта** — без управления промптами это опасный рудимент.

## 19. Что выглядит концептуально неправильно

Только подтверждённое анализом:

1. **Страница настроек не отражает объект управления.** Объект управления для бизнеса — «как генерируются программы» (какой генератор, какая модель, какой fallback, работает ли). Страница управляет строительными блоками, а итоговое состояние системы нигде не собрано. Это не косметический недостаток: живая БД показывает конфигурацию, которая создана, но не работает, и никто этого не видит.
2. **Селект протоколов продаёт будущее, которого нет.** «Anthropic» и «Произвольный» — это обещание функциональности, завершающееся ошибкой runtime. Либо адаптеры, либо один пункт в списке.
3. **Поле «Версия промпта» без управления промптами** — интерфейс даёт крутить параметр, цена ошибки в котором — упавшая генерация, а средства управления (список версий, создание) спрятаны в API.
4. **Три пути генерации с разной семантикой fallback** — архитектурная рассинхронизация: оркестратор (env-конфиг) для Telegram, «честный» выбор генератора radio-кнопкой в вебе без fallback, и дефолт `deterministic` в API. Пользователь не может держать в голове три модели поведения одной операции, и UI не помогает.

## 20. Предварительные направления улучшения

Без изменения кода и без детального дизайна, как ориентир для следующего этапа:

1. **Сводный статус AI-готовности** вверху страницы: для `workout_generation` показать цепочку «задача включена → primary-модель (endpoint, ключ) → резервные модели → fallback-генератор (из env)» с подсветкой недостающих звеньев. Это закрывает Critical №1 минимальными средствами.
2. **Журнал использования и аудита** на странице (backend уже отдаёт `/usage` и `/audit`) — таблица последних вызовов: время, задача, модель, статус, токены, латентность, ошибка.
3. **Сократить/упростить первый запуск**: мастер или одна форма «Подключить AI-сервис» (URL + ключ + модель), которая сама создаёт провайдера/эндпоинт/модель за кулисами; экспертный CRUD оставить как есть ниже или за переключателем.
4. **Убрать нерабочие опции**: протоколы без адаптеров, неиспользуемые задачи (или пометить их «скоро»), неиспользуемые поля (priority сущностей, capabilities — до появления requirements).
5. **Синхронизировать пути генерации**: как минимум отобразить в UI текущую env-стратегию; как максимум — единая точка генерации через оркестратор и для веб-кнопки.
6. **Добавить в UI то, что уже есть в backend**: удаление сущностей, редактирование (PATCH), управление промптами, timeout задачи.
7. **Локализация ошибок**: словарь человекочитаемых русских сообщений для типовых AI-ошибок вместо имён классов.

| Действие | Оценка | Пояснение |

| Подключить нового провайдера | **PARTIAL** | Форма простая, но нет объяснения роли провайдера; можно выбрать нерабочий протокол без предупреждения |

## Приложение A. Что реально проверено
